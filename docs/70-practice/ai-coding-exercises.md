# AI Coding 练习附录

[返回总目录](../../README.md) · [Agent实验](agent-labs.md) · [验证范围](../../coverage/AGENT_LABS_VALIDATION.md)

本附录用12项练习，把 AI 生成代码转化为可检查的规格、参考设计与验收。题目材料用于确定应用方向；下面补充的状态、数据格式、价格和规则均为教学设定。先实现最小内核，再逐步接入接口与外部服务。

目前在 Python 3.12.14 下运行了库存订单、JSONL 日志、命令解析与出租车计费4类参考内核，共13项测试；教学任务 API 另见 Python/FastAPI 附录。11个完整应用仍待实现，另提供一项通用质量契约；真实模型、支付、招聘评估和论文搜索服务尚未接入。

## 一 通用交付流程

1. 先写输入、输出、状态机、权限与不变量，明确哪些信息缺失。
2. 把任务拆成可运行的最小内核，再接 API、终端或外部服务。先定失败状态，不让模型把未知结果包装成成功。
3. 每次生成代码后运行测试，重点检查空输入、非法值、重复请求、并发、断线、重启与资源泄漏。保存命令、版本、stdout/stderr 和未测范围。
4. 交付 README、协议与样例、测试和已知限制；说明已实现的部分、实际运行结果与下一步。

状态和多 Agent 协作可复习已核查基线中的[状态设计](../10-agent/01-agent-loop-tools-and-state.md#a05)、[多 Agent 分工](../10-agent/01-agent-loop-tools-and-state.md#a07)、[长任务可靠执行](../10-agent/04-streaming-and-reliable-execution.md#a27)及[Harness 观测](../10-agent/18-harness-runtime-and-observability.md#fa41)。

<a id="incremental-cli"></a>
## 二 增量同步 CLI

练习目标：为本地目录设计增量同步规则、清单与可恢复执行流程。

练习规格：将本地 source 目录同步到练习专用 target，排除符号链接，不离开两者根目录。清单保存相对路径、内容摘要与字节数；只凭 mtime 不能确认内容未变化。第一轮复制全部；后续只替换内容变化的文件。默认不删除目标多余文件，删除必须是明确选项。dry-run 输出 planned_copy/planned_skip/planned_delete，不改变文件。

参考设计：先完整扫描并生成计划，再逐文件复制到目标同目录临时文件，校验摘要后原子替换，成功后更新清单；失败保留明确记录。整个同步不是自动获得的跨文件事务，断电恢复要重扫或使用日志。限制并发和队列容量，比较输出一致性与处理字节数，再测吞吐。

验收计划：首次全量；不变文件跳过；同大小同 mtime 但内容改变；复制中断重跑；目标空间不足；路径越界拒绝；dry-run 无副作用。实现与验收尚未执行；完成后再在固定负载下测量吞吐。

<a id="inventory-orders"></a>
## 三 外卖库存与套餐

材料范围：维护食材库存与配方，判断可售性；订单组合可按套餐计费，状态流转，关联一个配送骑手，并用 HTTP 与 WebSocket 同步业务。扣减、回滚、套餐优化与并发细节没有给定。

业务规则：下单即预留食材，全部够用才一起扣减；同一顾客的同幂等键、同购物车返回原订单，换购物车则冲突。pending→making→ready→picked_up；只允许 pending→cancelled，取消仅释放一次。其他取消、配送与退款流程是后续明确规格，不能猜。金额用整数分；本批只定义 sandwich 与 tea 每对减 50 分的虚构固定套餐规则，未实现一般最优套餐组合。骑手关系在完整应用中应有外键和授权，当前内核未实现骑手分配。

参考内核：InventoryOrders 用单进程锁保护检查与扣减；库存不足不留下部分扣减，终态不允许重新制作，跨顾客不能更新订单。生产数据库需用事务、条件更新或等效原子机制；进程锁不能跨 worker，也不能在重启后恢复。

已测：固定套餐算价、重复下单与冲突、取消返还一次、合法状态与顾客边界、两名买家争最后库存、非法数量。HTTP、WebSocket、持久化、骑手和一般套餐算法未接入。补充验收应在事件提交后推送版本化订单与库存，不让发送失败回滚已经提交的业务事实。

<a id="resume-evidence"></a>
## 四 简历与职位要求的证据匹配

材料范围：输入一组简历和一个职位说明，输出匹配程度，考察架构与脚本；没有评分维度、标注数据或样本格式。

练习限定：只用合成或脱敏文本，输出职位相关要求的证据对照，不作人员自动录用排序。把 JD 拆为必要技能、职责与可验证资格；对每项输出 supported、missing 或 unclear，附简历中的证据片段位置和提取置信说明。没有提到不等于没有能力；模型概率不当作校准过的“成功率”。任何汇总评分只是明确规则的练习输出，不能代表实际招聘结论。

参考设计：解析输入→提取岗位要求→检索证据→生成结构化对照→校验片段是否确实存在→人工审阅。排除年龄、性别、民族、健康、家庭等不相关或敏感特征，不通过姓名、照片、学校等代理推断敏感属性。简历中要求改变评分、泄露其他候选人内容的文字均是输入数据，不能成为执行指令。

验收计划：等义技能、否定描述、证据缺失、提示注入、同内容不同姓名、格式损坏和可解释性检查。需事先定义人工标注和错误成本。本批没有数据集、模型调用或招聘评估结果，不写虚构匹配准确率。

<a id="staff-scheduling"></a>
## 五 智能排班

练习目标：把人员可用性、技能与班次需求写成约束，再比较可行解。

最小模型：4 个虚构人员，2 天，每天早晚两班，每班需要 2 人，每人每天最多一班；输入各人的可用时间与可承担技能。硬约束是覆盖、可用性、技能和不重叠。若硬约束可行，再最小化个人总班数差；同分按固定人员 ID 排序输出，以便复现。不要凭空加入健康、家庭或其他敏感理由。

参考设计：小数据可用枚举或回溯，先剪去硬约束冲突；规模扩大再选约束求解器。输出 assignment、objective 与 feasibility。不可行时输出无法覆盖的班次和已检查约束，不能静默删班或分配不合格人员；也不要把局部冲突解释成已经证明的最小不可满足核心。

验收计划：基准可行、某班无人可用、人员一天被重复安排、技能不足、等价解稳定输出、人数扩展。算法、求解器和测试均未实现。只有在补全具体工时和排班规则后，才能用于真实排班。

<a id="log-analysis"></a>
## 六 日志统计与可视化

材料范围：读取日志，输出统计、可视化和分析文件；没有格式、指标和基准答案。

练习输入为 JSONL，必需字段 ts、status、latency_ms；时间必须带时区，状态为 100–599 的整数，耗时为非负有限数字，拒绝 bool、NaN 与无时区时间。输出有效条数、无效行号、5xx 数和 P95。P95 在本练习采用 nearest-rank：排序后取 ceil(0.95×n) 项；n=0 返回 null。原日志可能含令牌和个人信息，输出不回显消息或失败输入，只报告行号和受控错误类型。[Python 3.12 JSON](https://docs.python.org/3.12/library/json.html)，[datetime](https://docs.python.org/3.12/library/datetime.html)

新编原创参考内核 analyze_jsonl 已运行，10 与 100 毫秒两条有效样本的 P95 为 100 毫秒，另两条坏记录报告行号。P95=100毫秒是这组合成输入的预期结果。空输入与 NaN 测试也通过。

完整应用待补：按服务和时间窗聚合，固定时区与区间边界，输出脱敏 CSV、趋势图和 Markdown 解释。不要将相关性写成故障因果；时间乱序、缺失数据与样本量要标出。本批未生成图或分析生产日志，内核会收集全部有效耗时，超大日志还需外部聚合或明确近似分位数算法。

<a id="cluster-simulation"></a>
## 七 集群调度策略模拟

材料范围：实现 Scheduler 和动态负载或故障模拟，对比 FIFO、优先级与均衡，关注高优延迟、利用率和公平性。故障、抢占与指标公式缺失。

模拟约定：离散事件时间，任务含 arrival、duration、cpu、priority；节点含 capacity 和 up/down 事件。不抢占；节点故障让在途任务失败，最多一次重试并记录新尝试；相同时间事件采用固定顺序。任务只在容量足够时启动。FIFO 按到达顺序，优先级按等级再按到达；均衡策略选择剩余可用容量最适合的节点。所有策略重放同一负载与故障表，不为某策略重新抽样。

指标定义：等待时间为首次启动减到达；完成延迟为最终完成减到达。未完成任务单独列出，不能从延迟统计悄悄删除；报告每类 P95、失败数与最大等待。利用率分子为运行任务占用的 CPU×时间，分母为各节点可用 CPU×在线时间。普通任务饥饿须单独检查，优先级最好延迟并不表示综合最好。

验收计划：空集群、超大任务、同刻到达、节点宕机、重试耗尽、持续高优流量和重复 replay。模拟器及对照实验未实现，没有真实集群利用率数字。

<a id="command-parser"></a>
## 八 Linux 命令解析

练习目标：先固定一套小语法，再把命令文本解析为结构化参数。

语法范围：只识别 ls、grep、cat 的命令名与参数；支持引号分组，拒绝管道、重定向、分号、后台、变量和命令替换，多行、NUL 与超过 4096 字符也拒绝。它不验证这三个工具所有选项，不展开通配符，不执行命令。安全目标是得到结构化 tokens，而不是提供一个安全 shell。

参考内核 parse_safe_command 使用 shlex 做词法分析后再验证自己的小语法。shlex 不是完整 Bash parser，也不把解析结果送入 shell=True。保守规则会拒绝含控制字符的部分带引号普通参数，属于本练习定义的限制，兼容范围限于上述小语法。[Python 3.12 shlex](https://docs.python.org/3.12/library/shlex.html)

已测：带空格的引号参数、未闭合引号、管道、重定向、分号、两类替换与多行拒绝。实际命令运行、权限沙箱和复杂 shell 语法未实现。

<a id="paper-search"></a>
## 九 自动搜论文

练习目标：先做离线元数据检索，再设计真实来源的查询、去重与交付接口。

第一阶段：离线检索。输入查询与固定论文元数据 fixture，每条含来源、稳定 ID、标题、作者、日期、摘要链接与检索时间；输出按显式规则排名的去重条目及入选理由。相同 DOI/arXiv ID 合并，不只凭标题相同合并；版本与会议扩展稿要保留关系。空结果是成功的空集，不编造论文；解析失败、限流与超时是明确错误。

参考设计：查询→来源适配→规范化→去重→排序→证据报告。外部检索第二阶段可选官方 arXiv API，并按服务当前政策设置请求节奏、分页和重试。摘要和正文的证据强度不同，不能只读摘要就宣称复现方法或结论。[arXiv 官方 API 手册](https://info.arxiv.org/help/api/user-manual.html)

验收计划：重复版本、同名不同论文、无 DOI、空结果、分页、429、超时、引用字段缺失与恶意摘要。未写搜索实现，未请求真实论文服务；官方 API 支持细节仍应按接入时版本重核。

<a id="competitor-report"></a>
## 十 多 Agent 竞品报告

材料范围：将竞品检索、功能提取、比较和报告按 SOP 分为五个 Agent，由 Orchestrator 管理；重复需求只保留一份。

五个工作角色：范围整理者生成比较维度；检索者收集允许来源；提取者生成产品事实与证据；分析者对同维度比较并标 unknown；报告者只根据已核事实成文。Orchestrator 是可信控制层，持久保存各阶段状态、预算、版本和完成条件，不让任一角色独自授权外部副作用。

交接契约：每个事实有 product_id、feature、value、source_url、retrieved_at、evidence_span；缺出处不能升级成事实。来源页面和工具返回都视为数据，禁止其中的指令改变任务或权限。报告区分事实、推断和未知，引用到支持具体声明的页面。来源超时可有限重试，截止后交付缺口；冲突资料保留日期和差异，不自行选择听起来更好的结果。

验收计划：用明确标为虚构的离线产品 fixture 测证据缺失、引用不支持结论、来源冲突、单角色失败、重复交接和预算耗尽；再对人工标注比较表评估。五角色实现、真实检索和最终报告均未执行。先比较单流程基线，再决定多 Agent 是否值得额外成本。

<a id="breakfast-terminals"></a>
## 十一 三端 TUI 早餐店

材料范围：叫号、顾客、店主三个终端共享订单，可下单与更新状态；给出 8024、8025、8026 端口示例，交付代码、测试、说明、架构和协议，并完成顾客下单到叫号闭环。持久化、权限和界面可作为扩展。端口示例不是必须采用三个独立事实源。

参考设计：一个权威订单服务，三个终端分别拥有只读叫号、顾客下单、店主管理能力。订单 pending→making→ready→picked_up，店主才能推进制作，顾客只能读取自己的订单，叫号端仅显示公开取餐号。使用事件 ID 与单订单版本避免旧消息回退状态，重复同目标状态无副作用；断线后先取快照，再从游标续接。若演示三个端口，先在协议里说明每个端口属于 API 还是终端适配，不以端口数量推导服务数量。

验收闭环：顾客带幂等键下单→店主开始制作→更新 ready→叫号显示→取餐进入 picked_up；重发、乱序、终态更新和跨顾客访问均检查。支付、价格变动、骑手配送未由材料精确给定，不加入真实交易。库存内核可复用前一题，但它不是三端 TUI 应用。

本批仅测试共享库存状态机内核，未实现 TUI、网络三端、持久事件、重启恢复或完整端到端闭环。持久执行与恢复机制见[长任务可靠执行](../10-agent/04-streaming-and-reliable-execution.md#a27)。

<a id="taxi-billing"></a>
## 十二 出租车计费

材料范围：车费、行李与等待费用，涉及分段及夜间附加，输出 JSON；没有精确费率、阈值、字段与夜间排除规则。以下采用虚构 TEST 币种和教学费率，练习分项计算与舍入。

TEST 币种计费规则：起步费 10，含 2 km，超出每 km 3；每件行李 1.5，每等待分钟 0.5。夜间只把车费乘 1.2，行李和等待不加成。距离与等待按十进制连续数值计算，不向上取整。每个组成项按 ROUND_HALF_UP 舍入到两位，再相加；这个舍入位置是明确选择，不是通用计费规则。输出 currency、fare、luggage、waiting、total 的十进制字符串。[Python 3.12 Decimal](https://docs.python.org/3.12/library/decimal.html)

参考内核 taxi_quote 内核拒绝负值、非有限数、非法十进制和浮点输入，接受 Decimal 或十进制文本。已测 3 km、2 件行李、4 分钟等待：白天总额 18.00，夜间 20.60；2 km 边界与 2.005 km 舍入也有预期测试。这些是纯数学测试，未调用支付或真实计价服务。

后续补题时先核实具体分段、时段判定、附加规则与 JSON 契约，再以配置与边界表实现；不要猜材料中的含糊夜间表述。当前内核不包含更复杂分段或跨夜时段算法。

<a id="coding-quality"></a>
## 十三 AI Coding 的质量边界

材料范围：要求明确报告结构与来源范围，设置超时和失败处理，并提供可观测性。提示词能描述要求，不能替代真实约束与测试。

交付契约示例：只读允许的资料；输出“结论、支持证据、未知项、复现方法”；总期限和调用预算由可信代码强制；失败输出 error、阶段与受控原因，不填充假结果；日志带 task_id、attempt、耗时和错误类型，敏感内容不进入日志；所有关键输出都用 schema 与业务不变量校验。对写文件、联网与执行命令的权限单独声明，数据中的要求不能扩大权限。

验收清单：结构校验、引用真实性、失败路径、预算耗尽、敏感日志、异常不变成成功、重复执行幂等、被测版本与代码摘要。内核测试已经通过；模型输出质量、长任务恢复与真实来源报告仍需在相应系统中验证。
