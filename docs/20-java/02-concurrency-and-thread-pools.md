### J09 JMM 和 JVM 内存区域是一回事吗

优先级：P0。

**知识点详解** ：JMM 是 Java 内存模型，规定多线程之间对共享变量的读写允许观察到什么结果，核心是可见性、原子性和顺序约束。JVM 的堆、栈、方法区是在描述运行时存储和执行结构。前者回答“另一个线程能否看到更新”，后者回答“运行数据如何组织”。CPU 缓存与编译器优化是需要内存模型的背景，但不能把 JMM 简化成每个线程一份实体主存副本。

**具体例子** ：共享对象即使已在堆里，线程 A 改了它的字段，线程 B 也不能因此自动获得正确同步保证。两个线程必须通过锁、volatile 或并发工具建立通信规则。

**30 秒面试答法** ：JMM 描述线程间共享内存的语义，JVM 运行时区域描述存储布局；对象在堆上不代表字段更新对所有线程立即可见。

**追问** ：局部变量为什么通常不需要同步？变量本身线程隔离，但它引用的对象可能仍被共享。

**误区** ：回答 JMM 时只背堆、栈、元空间。

来源：[J-S10](../../sources/catalog.md#j-s10)、[J-S11](../../sources/catalog.md#j-s11)。

### J10 happens before 和 volatile 如何保证可见性

优先级：P0。

**知识点详解** ：happens-before 是可见性与顺序的保证关系，不是简单的墙上时钟先后。线程内程序顺序、同一锁的释放与后续获得、volatile 写与后续读，以及 start/join 都能建立相应关系；关系可传递。因此先准备普通字段，再写 volatile 标记，读线程读取标记后可获得前面准备结果的可见性。volatile 不提供互斥，一个 x++ 包含读、加、写，仍可能丢失更新。

**具体例子** ：以下是一次性发布的教学代码；data 在发布后不再修改。

```java
int data;
volatile boolean ready;
// 线程 A
data = 42;
ready = true;
// 线程 B
if (ready) {
    System.out.println(data); // 观察到此次 true 时，前面的 42 可见
}
```

**30 秒面试答法** ：volatile 提供相关读写的可见性和顺序约束，不让复合操作自动原子。我要保证计数正确会用 AtomicInteger 或锁；发布只读状态可以考虑 volatile 引用。

**追问** ：睡一秒能建立 happens-before 吗？不能。volatile 引用指向的所有字段之后任意修改都安全吗？不自动安全。

**误区** ：把“禁止重排序”说成所有指令都完全不能重排；把 volatile 当轻量版万能锁。

来源：[J-S10](../../sources/catalog.md#j-s10)、[J-S07](../../sources/catalog.md#j-s07)、[J-S12](../../sources/catalog.md#j-s12)、[J-S71](../../sources/catalog.md#j-s71)。

### J11 synchronized 锁住了什么

优先级：P0。

**知识点详解** ：synchronized 获取某个对象的监视器。同一时刻只能由一个线程持有同一个监视器，但持锁线程可重入。实例同步方法锁 this，静态同步方法锁对应 Class 对象，代码块锁括号里的对象。正常或异常退出块时都会释放锁。不同锁对象之间没有你期待的互斥，因此首先要检查所有访问同一状态的路径是否采用同一把锁。

**具体例子** ：每次在方法内 new Object() 再 synchronized(lock)，多个调用拿到的是不同对象，无法保护共享库存。应使用稳定的私有 final 锁对象，且读写共同遵守规则。

**30 秒面试答法** ：它同时提供同一监视器上的互斥和内存可见性，具有可重入和异常自动释放特性。要先讲锁对象和临界区，再谈 JVM 优化。

**追问** ：为何不把外部可访问的字符串常量当锁？可能与别处意外共享，扩大竞争或产生死锁。

**误区** ：把“偏向锁→轻量锁→重量锁”背成所有现代 JDK 的固定路径；具体优化要按版本确认。

来源：[J-S10](../../sources/catalog.md#j-s10)、[J-S13](../../sources/catalog.md#j-s13)、[J-S70](../../sources/catalog.md#j-s70)。

### J12 synchronized 和 ReentrantLock 如何选择

优先级：P0。

**知识点详解** ：两者都能实现可重入互斥。ReentrantLock 适合需要可中断获取、限时尝试、多个 Condition 或明确公平策略的场景；必须在 finally 解锁。synchronized 语法更直接，退出自动释放。公平锁主要影响竞争者的获取次序，不保证线程调度完全公平，也不保证吞吐更高；不应脱离测试比较谁永远更快。

**具体例子** ：某工具只允许同一租户一个任务修改索引，可限时 tryLock，超时返回“处理中”，避免让请求无限等锁。普通短临界区不需要这些能力时，synchronized 就能清晰表达。

**30 秒面试答法** ：从功能要求选，而不是按名字选快慢。简单互斥用 synchronized；需要超时、可中断或多个条件队列时考虑 ReentrantLock，并保证 finally 解锁。

**追问** ：tryLock 失败后能否 unlock？不能，只有成功获得锁才释放。持锁做网络请求有什么问题？延迟不受本地控制，竞争被放大。

**误区** ：拿到锁后在异常分支漏掉 unlock；把公平锁说成消除所有饥饿问题的万能方案。

来源：[J-S13](../../sources/catalog.md#j-s13)。

### J13 CAS 是什么 为什么还有 ABA 问题

优先级：P0。

**知识点详解** ：CAS 比较当前位置是否仍等于预期值，相等才原子更新。失败通常意味着其他线程修改过，调用方可重新读取后重试。它适合单个状态的无锁协调，但高竞争时频繁失败会消耗 CPU。ABA 指状态从 A 变成 B 又回到 A，普通值比较发现不了中间变化；若业务关心历史，应一起比较版本号或使用带标记的引用。

**具体例子** ：AtomicInteger.incrementAndGet 可避免普通 count++ 丢更新；但“账户余额检查＋扣款＋写流水”涉及多个状态，不能因为用了一个原子整数就保证全流程一致。

**30 秒面试答法** ：CAS 是比较后原子更新，通常用重试处理冲突。它有竞争重试开销、ABA 与多变量一致性边界，不等于任何业务都无锁更好。

**追问** ：LongAdder 适合精确抢占最后一个名额吗？其分散计数适合统计吞吐，求和不是这种配额决策的原子检查更新。

**误区** ：认为 CAS 永不阻塞就意味着无等待、一定比锁快。

来源：[J-S12](../../sources/catalog.md#j-s12)、[J-S14](../../sources/catalog.md#j-s14)、[J-S65](../../sources/catalog.md#j-s65)。

### J14 AQS 是一把锁吗

优先级：P1。

**知识点详解** ：AQS 是构建同步器的框架。它提供一个可原子修改的状态值，以及在获取失败后管理等待线程、阻塞和唤醒的机制。子类定义状态表示什么、什么条件下可获取和释放；因此同一个框架能支撑独占锁与共享同步器。等待队列与 Condition 的条件等待队列也不要混为一谈，await 后通常要在条件成立及重新获得锁后继续。

**具体例子** ：在可重入锁里，状态可以表达持锁计数；在信号量里，状态可以表达剩余许可证。这解释了它为什么是机制复用，而不是某个具体业务锁。

**30 秒面试答法** ：AQS 是状态管理加等待队列的同步器基础框架，具体语义由子类定义。ReentrantLock、Semaphore 等利用它实现不同协调方式。

**追问** ：有队列是否必然公平？不是，获取逻辑是否允许插队由实现策略决定。为什么不要让业务直接继承 AQS？正确实现需要处理释放、取消、中断等复杂边界。

**误区** ：把 AQS 叫作“CAS 自旋锁”，忽略它的排队和阻塞能力。

来源：[J-S15](../../sources/catalog.md#j-s15)、[J-S64](../../sources/catalog.md#j-s64)。

### J15 线程池七个参数和任务提交顺序是什么

优先级：P0。

**知识点详解** ：corePoolSize 是常规线程数阈值，maximumPoolSize 是上限；keepAliveTime 与 unit 控制空闲回收时间；workQueue 保存等待任务；threadFactory 创建线程；handler 处理拒绝。经典 ThreadPoolExecutor 正常运行时的路径是：不足核心数先建线程→否则尝试入队→队列放不下才尝试扩到最大→仍不行则拒绝。状态切换时还有复核逻辑。核心线程是否可超时可额外配置。

**具体例子** ：假设核心数 2、最大数 4、队列容量 2，所有任务持续阻塞。前两项运行，第 3、4 项排队，第 5、6 项新增线程运行，第 7 项拒绝。顺序说明最大线程数不是一有排队就生效。

**30 秒面试答法** ：我会按核心、队列、最大、拒绝这条提交路径解释七参数。业务配置要让线程、队列和下游容量匹配，并监控队列等待时间。

**追问** ：无界队列下最大线程数为何常常不起作用？正常入队一直成功，就走不到因队满而扩线程的分支。

**误区** ：误答为先扩到 maximumPoolSize，再入队；把配置数直接等同于启动时实际创建的线程数。

来源：[J-S16](../../sources/catalog.md#j-s16)、[J-S17](../../sources/catalog.md#j-s17)。

### J16 怎么给 LLM 调用配置线程池和拒绝策略

优先级：P0。

**知识点详解** ：线程池是资源隔离和过载处理边界，不能制造下游不存在的容量。先测请求速率、服务时间、CPU 占比及下游并发/速率上限，再设上限和有界队列。AbortPolicy 显式失败；CallerRunsPolicy 让提交线程执行，可能形成反馈，也可能堵住 Web/EventLoop 线程；Discard 类策略会丢任务，不能悄悄用于必须完成的业务。任务超过截止时间后应从等待/执行链路尽早取消。

**具体例子** ：假设测得平均每秒 10 次调用、每次在途 2 秒，则稳定平均并发约 20，这是估算起点，不是容量保证；若提供方只许 8 并发，应在准入处限流、排短队或拒绝，不能开 200 线程硬顶。

**30 秒面试答法** ：按测量和下游限制定并发，用有界队列、截止时间和显式过载响应。慢模型与普通业务线程池隔离，拒绝不能默默丢失用户任务。

**追问** ：Executors 工厂能否无脑使用？要检查它使用的队列和线程上限。线程池扩容后 p99 更差怎么办？检查下游排队、连接池竞争和切换开销。

**误区** ：把 CPU 核数乘固定倍数当所有 IO 业务的正确答案；认为大队列只会增加吞吐。

来源：[J-S16](../../sources/catalog.md#j-s16)、[J-S18](../../sources/catalog.md#j-s18)。并发估算和参数选择为工程示例。

### J17 CompletableFuture 能解决什么 不能解决什么

优先级：P1。

**知识点详解** ：它描述异步结果和后续处理依赖。thenApply 做值变换，thenCompose 把返回另一个异步结果的步骤接平，thenCombine 合并独立结果。Async 方法未显式指定 executor 时可能使用公共池，阻塞网络调用会相互影响。超时使 Future 结果完成为失败，不等于远端工作或底层网络请求已经停止；取消传播要由实际客户端和业务协议配合。

**具体例子** ：同时查知识库和用户可见配置，再合并上下文，可以降低串行等待。但必须让两个调用都带剩余 deadline，任何分支失败都有明确处理，不要异常时返回空串冒充成功。

**30 秒面试答法** ：CompletableFuture 管理异步依赖与合并，我会显式选择执行器、处理异常与超时，并验证取消能否传到底层 IO。

**追问** ：在同一小线程池的任务里 join 等待另一个排队任务会怎样？可能线程饥饿，甚至形成互等。allOf 会直接收集所有值吗？不会，仍需取得各结果。

**误区** ：认为加了 Async 就自动获得无限并发；认为 orTimeout 会立即终止外部模型生成。

来源：[J-S19](../../sources/catalog.md#j-s19)。

### J18 ThreadLocal 为什么会泄漏和串用户

优先级：P0。

**知识点详解** ：ThreadLocal 是按线程关联值，不是按 HTTP 请求。线程池复用线程时，上一次请求留下的用户信息可能被下一次读到；只要线程及相关条目仍持有值，业务对象就可能被长期保留。OpenJDK ThreadLocalMap 的键使用弱引用，但 value 并不是因此自动成为弱引用，不能依赖偶然清理。异步换线程后，原线程上的上下文也不会自然正确传播。

**具体例子** ：入口设置 currentUser 后，必须在 finally 中 remove。模型工具的 tenantId 更适合显式从可信请求上下文传入，而不是指望在任意异步线程读到 ThreadLocal。

**30 秒面试答法** ：线程池生命周期通常长于请求，ThreadLocal 必须清理，否则既可能内存滞留，也可能串用户。异步上下文需要显式传递或受控的上下文传播方案。

**追问** ：set(null) 和 remove 一样吗？语义不同，remove 删除当前线程的值并使后续 get 可重新初始化。

**误区** ：因为 key 是弱引用就认为不可能泄漏；把 ThreadLocal 当跨线程数据共享工具。

来源：[J-S20](../../sources/catalog.md#j-s20)、[J-S21](../../sources/catalog.md#j-s21)。

### J19 wait 和 sleep 有何区别 怎么防死锁

优先级：P1。

**知识点详解** ：wait 必须在持有对象监视器时调用，等待期间释放该监视器，醒来后需重新竞争获得它；sleep 暂停当前线程，但不释放已持有的监视器。wait 可能虚假唤醒，故要用 while 重查条件。死锁常见于互相持有对方需要的资源；工程上用一致锁顺序、缩短临界区、避免持锁调用外部系统，并用线程转储找等待环。

**具体例子** ：两个账户转账如果一个按 A→B 加锁，另一个按 B→A 加锁，可能互等；统一按账户 id 排序后获取锁能打破这类循环等待。

**30 秒面试答法** ：wait 用于条件等待并释放监视器，sleep 不释放。死锁预防先统一资源获取顺序，诊断时看线程栈与持锁/等待关系。

**追问** ：notify 后被唤醒线程是否立即执行？还要重新拿锁；通知方没退出临界区前它通常不能继续。

**误区** ：用 if 包住 wait；在持锁状态下 sleep 轮询，导致真正能改变条件的线程进不来。

来源：[J-S01](../../sources/catalog.md#j-s01)、[J-S22](../../sources/catalog.md#j-s22)。

### J20 CountDownLatch Semaphore 和队列如何分工

优先级：P1。

**知识点详解** ：CountDownLatch 表达“等若干事件完成”，计数减至零后等待者继续，通常不可重置。Semaphore 表达“同时允许多少个执行者”，获取许可证后进入，finally 归还。BlockingQueue 既保存数据，也通过容量和阻塞协调生产消费。三者解决的问题不同，不能只按是否会阻塞分类。

**具体例子** ：初始化三个只读索引后开始服务可用 latch；限制模型最多 8 个并发调用可用 semaphore；收集待处理文档用有界 queue。调用获取超时时没有拿到许可证，不能在 finally 多还一次。

**30 秒面试答法** ：等完成用 latch，限并发用 semaphore，传任务并控制积压用有界队列。要分别处理超时、中断与资源释放。

**追问** ：并发 8 是否等于每秒 8 次？不是，并发限制与速率限制是不同约束。

**误区** ：把无界队列看成免费缓冲；只有生产速度长期不超过消费速度，积压才不会无界增长。

来源：[J-S07](../../sources/catalog.md#j-s07)、[J-S17](../../sources/catalog.md#j-s17)、[J-S23](../../sources/catalog.md#j-s23)、[J-S63](../../sources/catalog.md#j-s63)。

### J21 虚拟线程适合 AI 后端吗

优先级：P1。

**知识点详解** ：虚拟线程在 Java 21 正式交付，由运行时调度到载体线程。大量请求等待网络 IO 时，它能减少“一请求占一个平台线程”的资源压力，但不会让 CPU 运算或模型本身变快，也不会增加数据库连接数和模型配额。通常按任务创建虚拟线程，而不是建立固定大小的虚拟线程池复用它们；控制下游资源用信号量等手段。

**具体例子** ：同时等待许多模型/检索请求时可以评估虚拟线程。Java 21 中在 synchronized 内阻塞存在 pinning 风险；JDK 24 的改进移除了这种监视器相关限制，Java 25 官方文档仍提醒 native/foreign 调用的 pinning。不能把旧结论直接贴到新版本。

**30 秒面试答法** ：虚拟线程主要扩展 IO 等待型并发，不提升单任务计算速度。我会明确 JDK 版本、限制下游并发，观察 JFR 和尾延迟后决定是否采用。

**追问** ：百万虚拟线程能同时查询数据库吗？还受到连接池、内存和数据库容量限制。

**误区** ：认为虚拟线程天然没有竞态；在 Java 24+ 仍机械要求所有 synchronized 改为 ReentrantLock。

来源：[J-S24](../../sources/catalog.md#j-s24)、[J-S25](../../sources/catalog.md#j-s25)、[J-S26](../../sources/catalog.md#j-s26)、[J-S18](../../sources/catalog.md#j-s18)、[J-S68](../../sources/catalog.md#j-s68)。

### J22 中断和取消应该如何处理

优先级：P1。

**知识点详解** ：中断是协作式停止信号，不是强制杀死线程。阻塞操作可能抛 InterruptedException 并清除中断状态；业务若不能向上传递，应在适当清理后恢复中断标记，而不是吞掉继续运行。Future.cancel 是否中断任务、网络请求是否真正终止，要看具体实现。取消还要定义业务后果：请求已经提交到远端时，客户端停止等待不证明副作用没发生。

**具体例子** ：用户关闭回答页面后，后端停止输出、撤销模型订阅、释放许可证并记录取消状态；涉及写操作的工具仍需按幂等键查询结果，不能把未知状态当失败重做。

**30 秒面试答法** ：我会把取消信号传遍任务、客户端和资源释放路径；中断是协作机制，外部副作用需要独立确认和幂等设计。

**追问** ：为什么不用 Thread.stop？它可能在破坏不变量的时刻结束执行，安全清理无法保证。

**误区** ：catch InterruptedException 后只打印日志；把取消 Future 当成远程调用一定未执行。
