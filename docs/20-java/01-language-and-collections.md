### J01 为什么重写 equals 时通常也必须重写 hashCode

优先级：P0。

**知识点详解** ：equals 表示业务上的相等；Object 的默认实现主要比较对象身份。hashCode 用于先把键定位到哈希桶，equals 再判断桶里的哪个键相等。契约要求相等对象的哈希值相同，反向不成立，因为有限的整数空间必然可能碰撞。作为 Map 键使用期间，影响相等性和哈希值的字段应保持稳定，否则对象还在旧桶里，查询却按新哈希去另一个桶。

**具体例子** ：两个独立创建的 UserId(7) 应代表同一个业务标识。如果只重写 equals，HashSet 可能仍装入两份。Java 17+ 可用 record UserId(long value) 自动得到基于组成字段的相等性，但包含可变集合时仍要考虑防御性复制。

**30 秒面试答法** ：哈希容器先用 hashCode 缩小范围，再用 equals 判断相等，所以相等必须同哈希，同哈希不一定相等。重写两者要使用一致的业务字段，键最好不可变。

**追问** ：字符串哈希碰撞是否意味着字符串相等？不意味着。为什么改了键里的 id 后 get 失败？因为桶位置可能变了。

**误区** ：hashCode 不是内存地址的语言保证；不能认为两个对象哈希相同就可以互换。

### J02 ArrayList 和 LinkedList 怎么选

优先级：P0。

**知识点详解** ：ArrayList 用连续的引用数组保存元素，按下标访问 O(1)，尾部追加均摊 O(1)，中间插入删除通常要移动后续引用。LinkedList 用双向节点，按下标找元素需要遍历；只有已经定位节点或使用合适迭代器时，改链接才接近 O(1)。链表还需要节点对象和前后指针，内存局部性通常较差。二者都不自动提供并发修改安全。

**具体例子** ：检索得到 100 条文档后顺序处理或按下标展示，用 ArrayList 很自然。实现普通队列可优先考察 ArrayDeque，而不是因为“经常增删”就直接选 LinkedList。

**30 秒面试答法** ：先看访问模式。多数业务 List 用 ArrayList；LinkedList 的插删优势有已定位位置这一前提，下标定位仍是线性时间。我会结合规模和基准测试选择。

**追问** ：ArrayList 扩容为什么不是每次加一个？预留空间可摊薄复制成本；具体增长倍率属于实现细节。

**误区** ：不能脱离“查找位置”的成本说链表任意删除都是 O(1)。

来源：[J-S03](../../sources/catalog.md#j-s03)、[J-S04](../../sources/catalog.md#j-s04)、[J-S67](../../sources/catalog.md#j-s67)。

### J03 HashMap 的 put 和 get 到底做了什么

优先级：P0。

**知识点详解** ：可把 HashMap 理解为“桶数组＋冲突时的桶内结构”。先计算键的哈希并做扰动，再定位桶；空桶直接放入，否则比较已有键，存在就替换 value，不存在再插入。get 重复定位和比较过程。OpenJDK 常见实现用长度为 2 的幂的数组，用掩码定位；冲突多时可能树化。接口语义和实现策略要分开，HashMap 不承诺遍历顺序，也不保证并发写安全。

**具体例子** ：保存 documentId→文档时，同一个 id 再 put 是覆盖，不会变成两条；若 get 返回 null，可能是没有键，也可能 value 本身为 null，可用 containsKey 区分。

**30 秒面试答法** ：通过哈希定位桶，再用 equals 区分键；冲突时在桶内查找，必要时扩容或树化。平均查找很快，但性能依赖哈希分布，HashMap 本身不是线程安全容器。

**追问** ：为何不只比较 hash？不同键会碰撞。为何不能依赖遍历顺序？扩容和实现调整都可能改变它。

**误区** ：平均 O(1) 不等于任何输入、任何阶段都严格 O(1)。

来源：[J-S02](../../sources/catalog.md#j-s02)、[J-S05](../../sources/catalog.md#j-s05)。

### J04 HashMap 扩容和树化阈值怎么正确回答

优先级：P0。

**知识点详解** ：扩容解决整体装载过高；树化解决单桶冲突过多，两者不是同一个动作。OpenJDK 25u 的默认负载因子是 0.75，常见扩容是容量翻倍，桶内节点按新增的一个哈希位分流到旧位置或旧位置加旧容量。源码中的 TREEIFY_THRESHOLD=8、MIN_TREEIFY_CAPACITY=64 是实现常量；桶数不足 64 时会优先扩容。不要把“第几个 put 必然树化”当独立口诀，调用路径和插入前后计数也需要看源码。

**具体例子** ：容量为 16、默认负载因子时，阈值通常为 12；再插入新键使 size 越过阈值会触发扩容。若预计存很多键，合理预分配能减少复制和重新分桶。

**30 秒面试答法** ：先解释为何扩容、为何树化，再补默认参数。阈值属于指定 JDK 的实现，不是 Map 接口契约；小表冲突多先扩容，大表冲突多才考虑树化。

**追问** ：负载因子更小有什么代价？冲突可能少一些，但占更多空间。为什么容量取 2 的幂？配合位运算及翻倍分桶。

**误区** ：把链表长度“等于 8”机械理解为所有插入 API 都已经转换成树；把扩容说成所有键都必须重新调用 hashCode。

来源：[J-S05](../../sources/catalog.md#j-s05)。

### J05 ConcurrentHashMap 安全意味着什么

优先级：P0。

**知识点详解** ：线程安全针对它规定的操作，不意味着多步业务流程自动原子。读取通常无需整表锁，更新会对竞争位置协调。Java 8 以后常见实现不再是 Java 7 那套固定 Segment 分段锁结构，不能用旧源码描述所有版本。它不允许 null 键和值，避免并发场景下把“缺失”和“存在但为 null”混在一起。

**具体例子** ：if (!map.containsKey(id)) map.put(id, task) 仍有竞态，应考虑 putIfAbsent。计数可用 merge(key, 1, Integer::sum)。computeIfAbsent 的计算函数应短小，别在里面做数十秒 LLM 网络调用，否则会放大更新等待。

**30 秒面试答法** ：ConcurrentHashMap 提供并发安全的单次操作和指定的原子复合方法。要用 putIfAbsent、compute 等表达原子意图，业务跨多个键或外部系统仍需额外一致性设计。

**追问** ：value 是 ArrayList 就也安全了吗？不是，容器安全不传递给可变 value。size 能当并发配额判定吗？不能把瞬时统计当原子准入条件。

**误区** ：认为换一个 Map 类型就消除了所有并发错误。

来源：[J-S06](../../sources/catalog.md#j-s06)。

### J06 fail fast 是什么 能拿它保证线程安全吗

优先级：P1。

**知识点详解** ：普通集合的迭代器可能记录结构修改计数，迭代中发现集合被意外修改，就抛 ConcurrentModificationException。这是尽力发现编程错误，不是锁，也不是必然发生的并发检测。即使只有一个线程，在增强 for 中直接删除集合元素，也可能触发。并发集合的迭代器则可能采用弱一致语义，不是同一套规则。

**具体例子** ：清理过期任务可使用迭代器自己的 remove，或满足业务条件的 removeIf；跨线程共享时还得选择同步、并发容器或快照策略。

**30 秒面试答法** ：fail fast 是发现结构修改错误的尽力机制，不是并发正确性的保障；不能靠捕获这个异常来实现线程安全。

**追问** ：未抛异常是否证明没竞态？不能。弱一致迭代是否等于创建时完整快照？也不能。

**误区** ：说“ConcurrentModificationException 只会在多线程产生”。

来源：[J-S03](../../sources/catalog.md#j-s03)、[J-S07](../../sources/catalog.md#j-s07)。

### J07 Java 泛型的类型擦除是什么意思

优先级：P0。

**知识点详解** ：泛型主要在编译期检查类型。编译器会把类型参数按上界擦除，必要时插入类型转换或桥接方法。List&lt;String&gt; 与 List&lt;Integer&gt; 通常不是两份分别生成的运行时类。擦除不等于 class 文件里完全没有泛型信息，字段、方法等签名仍可携带反射可读的泛型元数据。

**具体例子** ：List&lt;String&gt; 中正常不能 add(1)，但混用 raw List 可绕开编译期检查，之后取出 String 才出现 ClassCastException。new T() 因运行时不知道具体构造类型而不能直接写，可传工厂 Supplier&lt;T&gt;。

**30 秒面试答法** ：泛型让类型问题尽量在编译期暴露；实现主要依靠擦除、必要的强转和桥接方法。不要用 raw type，也不要把擦除误解成所有泛型元信息都消失。

**追问** ：为什么不能同时重载 m(List&lt;String&gt;) 和 m(List&lt;Integer&gt;)？擦除后的方法签名冲突。

**误区** ：以为每个 T 都生成一份专门机器代码；以为泛型能彻底阻止反射或 raw type 带来的类型问题。

来源：[J-S08](../../sources/catalog.md#j-s08)。

### J08 extends 和 super 通配符怎么理解

优先级：P1。

**知识点详解** ：List&lt;Dog&gt; 不是 List&lt;Animal&gt; 的子类型，否则把 Cat 放进来会破坏类型安全。若参数只提供数据，可用 ? extends Animal，读取可当 Animal，但不能安全加入任意 Animal；若参数接收 Dog，可用 ? super Dog，能够加入 Dog，但读取一般只能当 Object。这就是生产者 extends、消费者 super，必须从这个 API 对集合的使用方向理解。

**具体例子** ：复制接口可设计为 copy(List&lt;? extends T&gt; src, List&lt;? super T&gt; dst)，从 src 读 T，向 dst 写 T。目标可能是 List&lt;Object&gt;，也能容纳这些 T。

**30 秒面试答法** ：泛型默认不协变。只读取的来源用 extends，只写入的目的地用 super；同一个参数既要按 T 读又要按 T 写时，通常直接用明确的 T。

**追问** ：extends 集合完全不能改变吗？能做某些不依赖具体类型的操作，如 clear，故“只读”只是简化说法。

**误区** ：把通配符当成运行时权限控制或真正的不可变性。

来源：[J-S09](../../sources/catalog.md#j-s09)。
