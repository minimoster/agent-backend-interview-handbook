### J23 JVM 运行时内存区域怎么讲

优先级：P0。

**知识点详解** ：每个线程有自己的程序计数器和 JVM 栈，栈帧保存局部变量、操作数栈等执行信息；堆用于对象和数组的分配，是各线程共享的逻辑区域；方法区保存类级结构和运行时常量池。规范说的是抽象区域，不规定某种固定物理布局。HotSpot 的元空间是类元数据的一种实现，使用本地内存，不能直接把“方法区”和“元空间”视为所有 JVM 中完全同义的名词。

**具体例子** ：深度无界递归可能耗尽线程栈；持续把文档内容加到静态 List 可能耗尽堆；不断生成且无法卸载动态类可能压迫元空间。这三种问题不能统一用扩大堆解决。

**30 秒面试答法** ：先分线程私有的执行区域和共享的数据区域，再区分规范与 HotSpot 实现，最后用不同内存耗尽场景说明实际意义。

**追问** ：对象引用是对象本身吗？不是，局部引用在栈帧中不代表被引用对象也在那一栈帧里。

**误区** ：认为所有 new 都必须在物理堆上形成独立分配，忽略逃逸分析等优化；把 native 内存排除在进程内存预算外。

来源：[J-S11](../../sources/catalog.md#j-s11)、[J-S27](../../sources/catalog.md#j-s27)。

### J24 GC 如何判断对象可以回收

优先级：P0。

**知识点详解** ：现代 Java GC 通常从根引用出发追踪可达对象，而不是简单统计每个对象被引用几次。根可能包括活跃线程栈中的引用、由运行时持有的类相关引用等。两个对象互相引用，但从根都无法到达，仍可以回收。强、软、弱、虚引用的可达性及处理规则不同，软引用并不是严格可预测的缓存淘汰策略。

**具体例子** ：请求结束后，局部变量消失本应让大文档可回收；如果它又被全局 Map 保存，仍有根到它的路径，GC 不会因为“业务用完了”而理解你的意图。

**30 秒面试答法** ：GC 看可达性，不看业务是否想用。循环引用本身不是 Java 无法回收的原因，真正泄漏常是无用对象仍被长生命周期对象引用。

**追问** ：WeakReference 适合作为关键数据唯一保存位置吗？不适合，需要能接受目标随回收消失。

**误区** ：把引用计数的循环引用问题套给所有 Java 收集器；把 finalize 当可靠资源清理方式。

来源：[J-S28](../../sources/catalog.md#j-s28)、[J-S29](../../sources/catalog.md#j-s29)。

### J25 标记清除 复制 标记整理有什么取舍

优先级：P1。

**知识点详解** ：标记阶段识别存活对象。清除回收死亡对象占的区域，可能留下碎片；复制把存活对象搬到另一片区域，分配和回收可更规整，但要预留搬迁空间；整理把存活对象聚拢，减少碎片，也需要移动和更新引用。实际收集器会混合多种技术，不能给每个年代硬套一个永恒不变的算法。

**具体例子** ：如果一批短命请求对象中只有少量存活，搬迁少量活对象可能合算；如果大部分仍活着，复制成本就可能显著。这个存活率差异是理解分代思想的重要入口。

**30 秒面试答法** ：三类方法主要在碎片、移动成本和预留空间之间取舍，现代收集器按对象分布和延迟目标组合使用。

**追问** ：并行与并发 GC 一样吗？并行是多个 GC 线程协作，并发强调部分 GC 工作与应用同时进行。

**误区** ：把并发收集器说成没有任何停顿；把算法名称当具体收集器名称。

来源：[J-S29](../../sources/catalog.md#j-s29)、[J-S30](../../sources/catalog.md#j-s30)。

### J26 G1 和 ZGC 怎么选

优先级：P1。

**知识点详解** ：G1 把堆分成 Region，结合分代与选择性回收来平衡吞吐和停顿目标；停顿目标是调优目标，不是任何负载下都能兑现的承诺。ZGC 更强调低停顿，把昂贵工作尽可能并发执行，也需要 CPU 和足够分配余量。选择应从业务 SLO、堆大小、分配速率和实际 GC 日志出发。

**具体例子** ：普通实习项目先保留可解释的默认或团队配置，测 p95/p99、GC 停顿和 CPU。如果证据显示 GC 是尾延迟瓶颈，再用相同负载对比收集器。Java 25 的 ZGC 已是分代收集器，不能继续背“ZGC 不分代”。

**30 秒面试答法** ：G1 通常用于平衡目标，ZGC 偏低延迟；我不会仅凭堆大就切换，而会做相同负载的指标比较，并核对 JDK 参数版本。

**追问** ：为什么并发 GC 仍需堆余量？回收进行时应用还在分配。ZGenerational 还需设置吗？Java 24 起该选项已移除。

**误区** ：认为换 GC 能修复无限缓存或数据库慢查询。

来源：[J-S31](../../sources/catalog.md#j-s31)、[J-S32](../../sources/catalog.md#j-s32)、[J-S30](../../sources/catalog.md#j-s30)。

### J27 内存泄漏和 OOM 是一回事吗 怎么排查

优先级：P0。

**知识点详解** ：泄漏是不用的对象或资源仍被保留；OOM 是某项内存分配无法满足，原因也可能是配置太小、一次性巨量输入或本地内存不足。先读取具体错误及容器限制，再看 GC 后存活量趋势。堆泄漏可从对象直方图、堆转储中的支配关系和 GC Root 引用链查起；本地内存问题则不能只盯 Java 堆。

**具体例子** ：Agent 把每轮全文上下文无限追加到会话缓存，活跃会话一多，GC 后占用仍上涨。修复包括对话截断、过期与容量上限，然后用持续负载验证占用是否回稳，而不是只把 Xmx 翻倍。

**30 秒面试答法** ：先区分耗尽区域和是否真实泄漏，再找持续增长的保留对象及引用链。修复后验证稳定负载下的存活量和错误率。

**追问** ：生产抓 heap dump 有何风险？可能暂停或带来 IO 压力，文件还可能含用户数据和密钥，应走受控诊断流程。

**误区** ：看到 OOM 就认定有泄漏；把不断增加最大堆当根治。

来源：[J-S27](../../sources/catalog.md#j-s27)。

### J28 类加载的加载 连接 初始化分别做什么

优先级：P0。

**知识点详解** ：加载找到并建立类的运行时表示；连接包括校验、准备和解析等过程。准备涉及为静态字段分配存储并建立初始状态；初始化执行类初始化逻辑，如静态初始化块和相应赋值。解析把符号引用转成可使用的运行时关联，其执行时机可以按实现延迟，不要把图示顺序说成每一步只能一次性紧邻完成。

**具体例子** ：static int n = loadConfig() 中方法调用属于初始化逻辑。读取编译期常量可能在调用方已内联，未必触发定义类初始化；所以不能把任何 static 字段访问都当同一种情况。

**30 秒面试答法** ：加载得到类，连接使结构合法并建立运行条件，初始化执行类级初始化代码；主动使用和常量访问的差异要分开。

**追问** ：同一个类初始化会被多个线程同时无序执行吗？运行时有初始化同步规则；循环初始化仍可能产生复杂问题。

**误区** ：把“准备阶段赋默认值”和“初始化执行程序赋值”混为一谈。

来源：[J-S33](../../sources/catalog.md#j-s33)、[J-S34](../../sources/catalog.md#j-s34)。

### J29 双亲委派是什么 现代类加载器如何回答

优先级：P1。

**知识点详解** ：常见 ClassLoader.loadClass 实现先查是否已加载，再把请求交给父加载器，父加载失败后才尝试自己的查找。这样有利于共享基础类型并减少重复定义。运行时类型身份与定义它的加载器有关：同名 class 被不同加载器定义，可能是不同类型。Java 9+ 应知道平台类加载器，而不能只背 Java 8 的扩展类加载器。

**具体例子** ：插件系统可能需要隔离同名依赖，采取特定加载策略；这解释了双亲委派不是所有场景都绝不能改变的法律。但隔离后跨边界传对象，容易产生“名字一样却不能强转”的问题。

**30 秒面试答法** ：双亲委派是常见加载策略，不是 Java 对所有自定义加载器的绝对限制。要结合启动、平台、应用加载器及类身份解释。

**追问** ：两个相同全限定名是否必然代表同一类型？还要看定义加载器。

**误区** ：把委派关系讲成 Java 类继承关系；把双亲委派说成完整安全沙箱。

来源：[J-S35](../../sources/catalog.md#j-s35)、[J-S33](../../sources/catalog.md#j-s33)。
