### J30 IoC 和依赖注入为什么有用

优先级：P0。

**知识点详解** ：IoC 把对象创建、组装和生命周期管理交给容器；依赖注入是实现这种控制反转的方式。业务对象声明自己需要什么，不必内部到处 new 具体实现。构造器注入能让必需依赖清晰、字段可 final，并方便单元测试替换。容器仍然是真正创建 Java 对象，不是注解神奇地改变了语言规则。

**具体例子** ：AnswerService 依赖 SearchClient 接口，生产注入网络客户端，测试注入固定结果实现。这样不用真实付费调用也能验证“无检索结果时如何回答”。

**30 秒面试答法** ：IoC 把组装责任放进容器，DI 让对象声明依赖；收益是降低耦合、可替换、可测试。对必需依赖我优先考虑构造器注入。

**追问** ：两个实现都匹配怎么办？明确 qualifier/primary 或在配置里指定。循环依赖能都自动解决吗？不能，构造器循环就是明显问题，应优先重构依赖方向。

**误区** ：把 IoC 简化为“用了 @Autowired”；为了让容器启动而掩盖设计不合理的循环依赖。

来源：[J-S36](../../sources/catalog.md#j-s36)、[J-S37](../../sources/catalog.md#j-s37)。

### J31 Bean 生命周期要掌握到什么程度

优先级：P1。

**知识点详解** ：先建立 Bean 定义，再实例化和注入依赖，随后经历初始化相关回调与后处理，最终成为可用 Bean；某些后处理器会返回代理对象。容器关闭时对受管理对象执行相应销毁回调。真正的扩展点顺序比口诀复杂，首份实习应先理解“何时依赖可用、何时代理生效、谁负责清理”。

**具体例子** ：连接客户端可在受控初始化后准备，在销毁时关闭；不要在构造器里假设字段注入已经完成，也不要在 @PostConstruct 里依赖自己的代理事务已经拦截内部调用。

**30 秒面试答法** ：Bean 从定义、实例化、注入、初始化到后处理及销毁形成生命周期。代理也是这个过程中的产物，所以初始化期与正常外部调用的行为可能不同。

**追问** ：prototype 的销毁完全由容器自动管理吗？不应这样假定，取出后的资源释放往往由使用方负责。

**误区** ：只背很多接口名但无法解释何时关闭线程池；认为所有 new 出来的对象都享受 Spring 生命周期。

来源：[J-S38](../../sources/catalog.md#j-s38)、[J-S39](../../sources/catalog.md#j-s39)。

### J32 Spring 单例 Bean 线程安全吗

优先级：P0。

**知识点详解** ：默认 singleton 指一个容器内该 Bean 定义通常只有一个实例，并不附赠线程安全。多个 HTTP 请求可同时调用同一 Service；若请求状态保存在实例字段，容易互相覆盖。无状态服务将请求数据留在方法局部变量，较易正确；真正共享的状态需不可变结构、同步或外部存储的一致性保证。

**具体例子** ：不要在单例 ChatService 中用 String currentUser 或 StringBuilder answer 保存当前请求；改为方法参数和请求级状态对象。即使 StringBuilder 本身换成同步类型，也不代表用户之间该共享一份答案。

**30 秒面试答法** ：单例只是作用域。线程安全取决于是否共享可变状态及其访问方式，业务 Service 通常应保持无状态。

**追问** ：给字段加 volatile 能防串用户吗？不能解决错误的共享模型。把 scope 改成 prototype 是否解决所有问题？也不是完整方案。

**误区** ：把“Spring 管理”当成“自动加锁”。

来源：[J-S39](../../sources/catalog.md#j-s39)、[J-S10](../../sources/catalog.md#j-s10)。

### J33 Spring AOP 和两种代理如何工作

优先级：P0。

**知识点详解** ：AOP 把日志、权限、事务等横切逻辑放在方法调用边界。常见 Spring AOP 使用代理：调用者拿到代理，代理执行增强后委托目标。JDK 动态代理围绕接口，类代理通常用 CGLIB 子类方式；类代理不能通过重写拦截 private/final 方法，final 类也不能被继承。Spring Boot 的默认选择还会受配置影响，不可把核心框架默认值当所有项目默认值。

**具体例子** ：调用方→代理.beginTransaction→目标.save→代理.commit/rollback。目标里的 this.otherMethod() 直接调用自身，通常绕过代理；这个边界正是事务失效题的核心。

**30 秒面试答法** ：AOP 的关键是调用有没有经过代理。JDK 代理基于接口，类代理基于子类；方法可见性、final 和自调用都影响能否增强。

**追问** ：AspectJ 字节码织入也有完全相同自调用边界吗？不一定，它与代理模式机制不同。

**误区** ：看到 @Transactional、@Async、权限注解就认为任何路径都生效。

来源：[J-S40](../../sources/catalog.md#j-s40)。

### J34 为什么同类调用会让事务失效

优先级：P0。

**知识点详解** ：默认代理模式下，事务拦截器在代理上。外部通过代理进入带事务方法，拦截器才决定创建/加入事务；目标对象内部的 this 调用并不会重新经过这个代理。若外层本来有事务，内层数据库操作仍可能参加现有事务，但内层声明的新传播行为不会因自调用自动生效。因此“没生效”要区分“完全无事务”和“注解属性未按预期执行”。

**具体例子** ：下面的入口没有事务，调用 persist 时没有经过 Spring 代理，所以其注解不能开启事务。

```java
@Service
class TaskService {
    public void submit() { persist(); }
    @Transactional
    public void persist() { /* 两次数据库写入 */ }
}
```

推荐将 persist 提取到独立受管 Bean，由注入的协作者调用；或在合适边界使用 TransactionTemplate。测试时故意让第二次写入失败，再查第一次是否回滚。

**30 秒面试答法** ：不是注解消失了，而是调用绕过代理。我的修复首选清晰拆分事务服务或程序式事务，并通过失败测试验证真实回滚。

**追问** ：外层 REQUIRED、内层 REQUIRES_NEW 自调用会开新事务吗？不会仅凭该内部注解开新事务。

**误区** ：说“内部调用一定没有任何事务”；只改方法为 public 就认为修复完成。

来源：[J-S41](../../sources/catalog.md#j-s41)、[J-S42](../../sources/catalog.md#j-s42)。

### J35 除了自调用 事务还会在哪些地方不符合预期

优先级：P0。

**知识点详解** ：排查四层：对象是否由容器及事务设施管理；调用是否经过支持该方法的代理；异常是否按回滚规则传播；数据库及事务管理器是否覆盖实际操作。未修改默认策略时，对 RuntimeException/Error 回滚，普通 checked exception 不自动回滚，可明确 rollbackFor；Spring 6.2+ 还支持配置全局默认回滚策略，因此必须看实际配置。catch 后正常返回可能让拦截器看不到失败。命令式事务通常绑定执行线程，新开的线程不会自动继承。

**具体例子** ：写入成功后抛 IOException，若期望回滚应明确规则。若异常被吞掉，即使配置 rollbackFor 也不能保证拦截器知道业务失败。还应检查实际使用的事务管理器是否对应那个数据源。

**30 秒面试答法** ：我按 Bean、代理调用、异常规则、资源边界排查。还会确认方法可见性与具体 Spring 版本，而不是背“非 public 全失效”。

**追问** ：Spring 6+ 类代理能否支持 protected/package 可见事务方法？默认可以；接口代理的方法仍需 public 且在接口上。private 仍不能靠类代理重写。

**误区** ：把数据库不支持事务、异常被捕获和代理绕过全叫同一种原因；期待数据库回滚同时撤销已发送邮件。

来源：[J-S41](../../sources/catalog.md#j-s41)、[J-S43](../../sources/catalog.md#j-s43)、[J-S44](../../sources/catalog.md#j-s44)。

### J36 REQUIRED REQUIRES_NEW NESTED 怎么区别

优先级：P1。

**知识点详解** ：REQUIRED 有事务就加入，没有则新建；多个逻辑范围可能共享同一物理事务。REQUIRES_NEW 启动独立物理事务并挂起外部事务，其提交可独立生效，也可能需要额外数据库连接。NESTED 通常借同一个物理事务的保存点做局部回滚，能否支持取决于事务管理器和资源。外层最终整体回滚时，保存点不是独立提交。

**具体例子** ：主业务失败后仍想记录审计，有时会考虑独立事务，但必须评估连接池：每个线程都持外层连接、再等内层连接，可能耗尽池。若只是允许子步骤局部撤销，保存点语义可能更匹配。

**30 秒面试答法** ：关键比较物理事务是否共享、失败影响范围和资源代价。传播行为只在有效拦截的调用上生效，不能忽视自调用。

**追问** ：内层 REQUIRED 标记 rollback-only，外层捕获异常后提交会怎样？仍可能因共享事务已被标记而失败，出现 UnexpectedRollbackException。

**误区** ：把 NESTED 当作 REQUIRES_NEW 的别名；大量嵌套独立事务却不算连接池容量。

来源：[J-S45](../../sources/catalog.md#j-s45)。

### J37 一次 Spring MVC 请求怎么到 Controller

优先级：P0。

**知识点详解** ：请求经过 Servlet Filter 链，进入 DispatcherServlet；由 HandlerMapping 找到处理器，再由 HandlerAdapter 执行适配。参数解析、类型转换和验证发生在调用周围。返回值可能经视图解析生成页面，也可能经 HttpMessageConverter 序列化为 JSON。异常可交给异常解析机制。安全过滤通常应在更前的安全链处理，不能只靠业务 Controller 临时补判断。

**具体例子** ：POST /tasks 的 JSON 被解析为 CreateTaskRequest，校验后调用服务，返回结果序列化为 JSON；如果字段类型错误，甚至可能还没进入 Controller 主体就已产生错误响应。

**30 秒面试答法** ：DispatcherServlet 是入口协调者，映射找目标、适配器执行、参数解析和返回值处理完成协议转换。Controller 不等于整个请求链。

**追问** ：Filter 与 Interceptor 的主要边界？前者属于 Servlet 过滤链，后者围绕 Spring MVC 处理器执行；选择要看需要覆盖哪些请求阶段。

**误区** ：认为 @ResponseBody 是手动调用 JSON.toString；认为所有错误都会进入自己方法里的 try/catch。

来源：[J-S46](../../sources/catalog.md#j-s46)、[J-S47](../../sources/catalog.md#j-s47)。

### J38 参数校验和统一异常处理为什么都需要

优先级：P0。

**知识点详解** ：参数校验尽早检查输入形状和基本约束，例如非空、长度和范围；业务层还要验证语义和权限，例如“这个文档是否属于该用户”。二者不是互相替代。异常处理把内部失败转换成稳定的状态码和错误体，同时给日志留下 requestId，而不是把堆栈、SQL 和密钥回传。Spring MVC 不同验证入口可能产生不同异常，应按版本覆盖测试。

**具体例子** ：prompt 限长可避免超大请求占用内存；documentId 是正数仍不代表当前用户有权读取它。公开响应给错误码和可理解信息，内部按 traceId 查诊断日志。

**30 秒面试答法** ：校验保证输入满足约束，业务授权保证能做这个操作，统一异常层保证失败可预期、可定位且不泄密。

**追问** ：HTTP 200 加 success=false 可不可以？需遵守团队协议，但不能因此忽略传输层状态、监控和客户端错误处理语义。

**误区** ：以为前端验证足够；把模型生成的 JSON 当成已经可信的业务参数。

来源：[J-S47](../../sources/catalog.md#j-s47)、[J-S48](../../sources/catalog.md#j-s48)。

### J39 Spring Boot 自动配置怎么排查

优先级：P0。

**知识点详解** ：Boot 根据类路径、配置属性、已有 Bean 等条件选择自动配置，减少手工组装。Starter 主要提供依赖组合，自动配置提供条件化 Bean，两者并不相同。自己定义某个 Bean 后，相关自动配置可能退让。出现“为什么没创建客户端”时，应该看条件匹配报告，而不是盲目加很多注解。

**具体例子** ：引入数据库依赖后仍连不上，依次查依赖版本、数据源属性、自动配置条件、已有 Bean 冲突和环境覆盖。可用 --debug 查看条件报告；Actuator 暴露面必须受控。

**30 秒面试答法** ：自动配置不是无条件魔法，是条件匹配的配置机制。排查从依赖、属性和条件报告入手，明确哪些配置生效及为什么退让。

**追问** ：配置在本地正常线上不正常先看什么？生效 profile、环境变量、配置优先级与实际依赖版本。

**误区** ：把引入 starter 等同于业务逻辑已经完成；为方便调试公开暴露所有管理端点。

来源：[J-S49](../../sources/catalog.md#j-s49)、[J-S50](../../sources/catalog.md#j-s50)。

### J40 认证 授权 CSRF CORS 分别是什么

优先级：P0。

**知识点详解** ：认证确定是谁，授权决定能操作什么。Spring Security 在过滤链中处理认证及相关防护，服务层也可以做方法级授权。CSRF 关注浏览器自动带凭证导致的跨站请求伪造；CORS 控制浏览器对跨源响应的访问，并不是业务授权。是否需要 CSRF 防护取决于凭证如何随请求发送，不能因为返回 JSON 就关闭它。

**具体例子** ：已登录用户 A 访问 /documents/B 的数据仍必须做对象级权限判断。若采用 Cookie 会话，浏览器会自动带 Cookie，应认真配置 CSRF；如果用 bearer token，也要核查它存放和发送方式，防止一概而论。

**30 秒面试答法** ：认证不等于授权，CORS 不等于防 CSRF。我会按身份、角色/对象权限和浏览器凭证机制分层防护。

**追问** ：JWT 解码成功等于可信登录吗？还需验证签名、有效期及预期 issuer/audience 等规则。

**误区** ：只隐藏前端按钮；只在 URL 层验证登录却不校验资源归属。

来源：[J-S51](../../sources/catalog.md#j-s51)、[J-S52](../../sources/catalog.md#j-s52)、[J-S53](../../sources/catalog.md#j-s53)、[J-S69](../../sources/catalog.md#j-s69)。
