### FB25 进程、线程和状态转换如何共同解释并发

**优先级：P0**

**知识点详解**：进程提供地址空间及资源隔离；进程内线程共享地址空间和许多进程资源，各有执行栈、寄存器状态与线程局部信息。线程方便共享数据，也必须同步。抽象状态包含新建、就绪、运行、阻塞和终止：运行线程等 I/O 可阻塞；事件完成后通常先回就绪，而不是立即运行。Linux 可观测状态码与教学五状态并非严格一一对应，例如 D 表示不可中断等待。

**具体例子**：服务开 500 个线程并不意味着 500 个线程同时占用 CPU。很多可能等待连接池或网络；把等待误认为 CPU 不够，继续加线程反而增加内存和切换。

**面试答法**：我用资源边界解释进程/线程，用状态转换解释为什么有线程不代表有并行，再结合实际工具定位等待原因。

**追问**：线程切换总比进程切换快多少？没有固定倍率，地址空间、缓存、调度及硬件都会影响，必须测量。

**常见误区**：线程共享所有东西；阻塞线程持锁时其他线程可以自动拿走锁；把 Java WAITING 与 Linux 状态码直接等号连接。

### FB26 死锁四条件与预防、避免、检测怎样区分

**优先级：P0**

**知识点详解**：在经典资源分配模型中，互斥、占有等待、不可剥夺和循环等待是死锁的必要条件；多实例资源图出现环不单独足以证明死锁。预防通过规则破坏某条件，如全局锁序破坏循环等待；避免在分配前判断能否保持安全状态，银行家算法需知道最大需求；检测允许问题发生后检查等待关系并恢复。CPU 可抢占不表示任意业务锁或资源能安全强行夺走。

**具体例子**：转账同时锁账户 2 和 7，所有线程按账户 ID 从小到大加锁可消除相反锁序。超时退出必须释放已经取得的锁，并决定整笔业务重试，不能只重试最后一步。

**面试答法**：我先画资源等待图，再指出采用哪类策略及代价。数据库死锁回滚和业务幂等重试要一起设计。

**追问**：无死锁是否一定无活锁和饥饿？不是，反复退让可能无进展，固定优先级也可能让低优先级任务长期等候。

**常见误区**：四条件具备就断言一定已经死锁；杀任意持锁线程不会破坏业务；加超时就无需定义回滚。

### FB27 虚拟内存为什么不等于把磁盘当内存

**优先级：P0**

**知识点详解**：虚拟地址经页表翻译到物理页或其他后备状态，允许隔离、共享、按需分配与灵活布局。TLB 缓存地址翻译，缺页异常不一定是错误，可能触发加载或分配。分页使用固定大小页，通常避免按可变连续段分配的外部碎片，但末页仍可内部浪费；分段按逻辑区域管理，也可与分页组合。虚拟内存不等于 swap，进程有很大虚拟空间也未必有足够物理内存完成计算。

**具体例子**：映射 20 GB 文件后 RSS 未必立刻增加 20 GB；逐页触碰才产生相应驻留与缺页成本。相反，容器内实际驻留与其他内存超过限制仍可被 OOM 机制处理。

**面试答法**：我区分虚拟大小、驻留页、页缓存和交换，再说明页表、TLB 和缺页如何协作。

**追问**：分页能共享和保护吗？可以，页表权限控制访问，多个地址空间可映射共享物理页，并非分段独有。

**常见误区**：虚拟内存一定有 swap；malloc 成功证明未来不会 OOM；分页完全没有碎片。

### FB28 内存对齐与大小端是同一个问题吗

**优先级：P1**

**知识点详解**：对齐关心地址是否满足架构与 ABI 要求，大小端关心多字节数值在内存中各字节顺序。某些架构可处理非对齐但有额外成本，另一些可能异常；类型对齐不必恒等于类型大小。结构体可能插入填充，不能直接把内存布局当可移植网络格式。网络序常按大端表达多字节字段，序列化应显式选择字节序与宽度。

**具体例子**：32 位数 0x01020304 在小端内存低地址处是 04，在大端处是 01。若协议读取 4 字节却直接转换未对齐指针，可能同时犯字节序和对齐两个错误。

**面试答法**：我分别讲地址约束和字节排列，跨平台协议用显式编码避免依赖结构体内存布局。

**追问**：用 packed 消除填充是否总是优化？可能引入非对齐访问、更多指令甚至架构异常，要看目标 ABI。

**常见误区**：小端机器不能发送网络包；结构体 sizeof 就是协议长度；所有 8 字节类型都要求相同对齐。

### FB29 哈希表加双向链表怎样实现 LRU 并验证边界

**优先级：P0**

**知识点详解**：哈希表负责按 key 定位节点，双向链表表达最近使用顺序。读命中或更新已有 key 后把节点移到头部；插入新 key 超容量则移除尾部真实节点并从哈希表删除。哨兵节点简化空表与单元素边界。平均每次操作 O(1)，不是对任意哈希攻击都保证最坏 O(1)。get 也修改链表，所以并发使用需要锁或专用并发设计。

**具体例子**：容量 2，依次 put(A)、put(B)、get(A)、put(C)，B 应被淘汰；容量 0 时不能保留数据，更新 A 的值不应多占一个节点。下面原创实现使用 Python 基本 dict，不使用有序容器，便于逐步检查指针。

**面试答法**：我先给出“哈希表节点与链表节点一一对应”的不变量，再写删除和插头两个原语，最后组合 get/put。

**追问**：为什么不能只用普通队列？访问中间元素后要 O(1) 移动，需要可直接定位节点及前后指针。

**常见误区**：get 是只读可无锁；淘汰后忘记删哈希映射；重复 key 多插节点。

**原创 Python 3 教学实现**（不提供并发保证；测试范围见文末）：
```python
class Node:
    def __init__(self, key=None, value=None):
        self.key, self.value = key, value
        self.prev = self.next = None

class LRU:
    def __init__(self, capacity):
        if capacity < 0:
            raise ValueError("capacity must be nonnegative")
        self.capacity, self.nodes = capacity, {}
        self.head, self.tail = Node(), Node()
        self.head.next, self.tail.prev = self.tail, self.head

    def _detach(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _front(self, node):
        node.prev, node.next = self.head, self.head.next
        self.head.next.prev = node
        self.head.next = node

    def get(self, key, default=None):
        node = self.nodes.get(key)
        if node is None:
            return default
        self._detach(node)
        self._front(node)
        return node.value

    def put(self, key, value):
        if self.capacity == 0:
            return
        node = self.nodes.get(key)
        if node is not None:
            node.value = value
            self._detach(node)
            self._front(node)
            return
        node = Node(key, value)
        self.nodes[key] = node
        self._front(node)
        if len(self.nodes) > self.capacity:
            victim = self.tail.prev
            self._detach(victim)
            del self.nodes[victim.key]
```
返回缺失默认值可能与已存 None 混淆；生产 API 可选择异常、(found, value) 或独立 sentinel。严格 LRU 与高并发缓存的近似访问记录、准入策略是不同设计，不拿这段替代 Caffeine。

**实际验证**（2026-10-09）：从本页抽取的原样 Python 代码，通过容量 0–5、每种容量 10 个随机种子、合计 30000 次 get/put，与 OrderedDict 参考模型逐步对拍；每步检查前后指针、链表顺序、哈希键集合与容量，另测负容量异常。OrderedDict 仅用于独立测试基准，不在实现中使用；未做并发测试或性能基准。

可复验源码与运行命令见 [examples/backend](../../examples/backend/README.md)。

### FB30 用户态进入内核意味着什么，何时发生切换

**优先级：P1**

**知识点详解**：用户态应用受权限限制，内核通过受控入口管理设备、地址空间与调度。系统调用是主动请求服务，同步异常源于当前指令，例如缺页；硬件中断来自外部事件。进入内核不必马上换进程，内核处理完成后可返回同一线程，所以模式切换与任务上下文切换不同。内核访问也受页表、架构保护与虚拟化边界约束，不能描述成任何地址永远都能读写。

**具体例子**：应用 read 缓存中的文件数据可能短暂进入内核后立即返回；若等磁盘则可能阻塞并切到其他任务。两条路径都调用 read，性能却不同。

**面试答法**：我区分特权级转换和调度转换，并用系统调用、异常、中断三个入口解释。

**追问**：缺页一定访问非法地址吗？合法按需映射也可缺页；需要看异常是否能由内核满足。

**常见误区**：每次系统调用都切换到另一进程；用户态不能利用页缓存；内核态就不受任何内存保护。

### FB31 删除文件名后空间为什么还在，软链接怎样解析

**优先级：P0**

**知识点详解**：硬链接是同一文件对象的多个目录项，通常共享 inode 且不能跨文件系统；符号链接是保存目标路径的独立对象，可跨文件系统并可悬空。删除一个名字只减少链接计数，最后一个硬链接删除后若仍有打开引用，文件数据通常等到引用关闭才释放。相对符号链接目标相对于链接所在目录解析，而非执行命令时的当前目录。

**具体例子**：日志文件已 rm，进程仍打开旧文件，df 显示空间没下降。应确认持有者并按服务支持方式轮转/重开文件，不能凭猜测强杀生产进程。

**面试答法**：我先区分名字、inode 与打开文件描述符三个层次，再解释删除和引用生命周期。

**追问**：复制符号链接到另一目录后为什么失效？相对目标的解析基准改变，需核对是否应保留链接还是复制实际内容。

**常见误区**：删除文件名立即擦除数据；硬链接是保存路径的快捷方式；软链接跟随目标重命名自动修改。

### FB32 调度算法如何在吞吐、响应、公平之间取舍

**优先级：P1**

**知识点详解**：FCFS 简单却可能让短任务排在长任务后；SJF 在已知运行长度等假设下优化平均等待，却需要估计且可能饿死长任务；优先级支持业务差异但要防饥饿；轮转以时间片换响应，片太小增加切换成本；多级反馈队列根据行为调整优先级。以上是理解用的抽象算法，不应直接当作当前 Linux 每个调度类的完整实现。

**具体例子**：交互请求希望短时间获得一次运行机会，批处理更在意总吞吐；如果把长 CPU 任务与短网络回调塞到同一执行资源，公平调度也无法消除所有尾延迟。

**面试答法**：我先给评价指标，再描述调度规则、依赖的先验信息及饥饿风险，最后说明系统实现可能组合多种机制。

**追问**：等待越久优先级越高能解决什么？老化可降低饥饿风险，但需与实时任务约束共同设计。

**常见误区**：短作业优先知道未来长度；线程越多越公平；某经典算法名就是现代内核的全部调度逻辑。
