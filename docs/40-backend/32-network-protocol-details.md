### FB15 从分层模型讲到 URL 请求与页面渲染

**优先级：P0**

**知识点详解**：OSI 七层用于分离物理、链路、网络、传输、会话、表示与应用职责；互联网常按链路、IP、传输和应用四层讨论，不能机械一层一协议。输入 URL 后，浏览器先处理 URL、缓存与安全策略，再可能做 DNS、建连与 TLS、发 HTTP；随后解析 HTML、发现 CSS/脚本等资源，建立 DOM 与样式、布局、绘制和合成。连接、DNS 或资源缓存命中时步骤会省略，HTTP/3 以 QUIC 替代 TCP 传输。

**具体例子**：首屏慢可能是 DNS/握手慢，也可能 HTML 已到但大脚本执行阻塞主线程。应先区分 TTFB 与页面渲染指标，再决定查网络还是前端。

**面试答法**：我按职责画出一条路径，同时标明缓存、连接复用和协议版本的分支，最后用瀑布图把时间归到相应阶段。

**追问**：看到页面是否表示全部请求完成？异步脚本、图片、长连接可以继续工作，需给出完成指标的定义。

**常见误区**：每次访问必须新建 TCP；TLS 统一叫 SSL；DNS 一定发生在建连之前且绝无缓存。

**来源**：[FB-S019 RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293)、[FB-S021 RFC 9114 HTTP/3](https://www.rfc-editor.org/rfc/rfc9114)、[FB-S022 RFC 8446 TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446)、[FB-S027 RFC 1034 DNS](https://www.rfc-editor.org/rfc/rfc1034)、[FB-S058 RFC 9110 HTTP 语义](https://datatracker.ietf.org/doc/html/rfc9110)。业务组合、反例与答题组织为原创教学推导。

### FB16 TCP 与 UDP 的服务模型如何影响应用设计

**优先级：P0**

**知识点详解**：TCP 提供有连接、有序可靠字节流，没有应用消息边界；UDP 提供数据报边界，不承诺可靠、顺序或去重。可靠不等于网络永远可用，断线后的业务结果还需应用确认。UDP 上可以建立可靠协议，例如 QUIC 在 UDP 上实现可靠流与拥塞控制，所以“UDP 应用都能容忍丢包”错误。TCP 也不天然保障机密性，通常另配 TLS。

**具体例子**：视频通话可能允许丢弃已过时帧，支付业务则需要稳定操作 ID 与结果查询。即便支付走 TCP，请求发出后断线也不能认定对方没扣款。

**面试答法**：我从连接、消息边界、顺序、可靠性和应用自定义需求比较，而不把 UDP 简化成快、TCP 简化成慢。

**追问**：DNS 只用 UDP 吗？不是，传统 DNS 也可用 TCP，另有加密传输；选择取决于协议与配置。

**常见误区**：一次 write 对应一次 read；用 TCP 就不必做幂等；UDP 就不能做可靠下载。

**来源**：[FB-S019 RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293)、[FB-S020 RFC 9000 QUIC](https://www.rfc-editor.org/rfc/rfc9000)、[FB-S027 RFC 1034 DNS](https://www.rfc-editor.org/rfc/rfc1034)。业务组合、反例与答题组织为原创教学推导。

### FB17 握手、半关闭和 TIME_WAIT 应怎样连起来

**优先级：P0**

**知识点详解**：建连时双方各自提供初始序列号并确认对方序列，第三次报文完成对服务端序列的确认，也帮助区分旧连接报文。关闭时两个发送方向独立终止：收到 FIN 表示对方不再发送，不代表本端不能继续发。ACK 与本端 FIN 可能合并，因此逻辑双向关闭不必恰好四个报文。主动完成关闭的一方通常进入 TIME_WAIT，保留处理末次确认重传及旧报文的时间。

**具体例子**：客户端发送完上传后 shutdown 写方向，仍可读取服务端计算结果，这就是半关闭用途。另一场景中服务器主动关闭空闲连接，则 TIME_WAIT 可能在服务器侧。

**面试答法**：我画两条独立字节流的序列空间，标出 SYN/FIN 占用序列号及 ACK 含义，再解释等待状态的目的。

**追问**：TIME_WAIT 多就该立刻调参数吗？先确认主动关闭方、连接复用、短连接速率和端口压力，不能仅凭数量判断故障。

**常见误区**：三次握手只为证明收发能力；客户端永远 TIME_WAIT；关连接只能四次报文。

**来源**：[FB-S019 RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293)。业务组合、反例与答题组织为原创教学推导。

### FB18 ARP 查询的是最终服务器还是下一跳

**优先级：P1**

**知识点详解**：IPv4 路由选择先决定下一跳，再在相应本地链路上解析下一跳的链路层地址。目标在同一子网时可查目标；跨网段通常查网关。缓存命中不必广播，否则广播请求并接收响应。IPv6 使用基于 ICMPv6 的邻居发现，不能把 ARP 原样套过去。地址解析仅解决本地下一跳发送，不负责端到端路由。

**具体例子**：笔记本访问远端机房的 Web 服务，以太网帧目标通常是本地网关 MAC，IP 包目标仍是远端服务器 IP；经过路由器时链路层封装逐跳变化。

**面试答法**：我先看路由表，再看邻居缓存，用“下一跳”避免把 MAC 解释为跨互联网固定地址。

**追问**：ARP 缓存被恶意伪造会怎样？可能错误转发，需结合交换网络防护；HTTPS 认证仍需严格验证，不能绕过证书错误。

**常见误区**：每个远端网站都在本地广播查其 MAC；IPv6 没有地址解析问题。

**来源**：[FB-S025 RFC 826 ARP](https://www.rfc-editor.org/rfc/rfc826)、[FB-S026 RFC 4861 IPv6 邻居发现](https://www.rfc-editor.org/rfc/rfc4861)。业务组合、反例与答题组织为原创教学推导。

### FB19 可靠传输、流量控制与拥塞控制分别保护什么

**优先级：P0**

**知识点详解**：序列号与确认帮助识别字节位置和缺失，校验检测传输错误，重传恢复丢失，接收端重排并去重后向应用提供有序流。rwnd 反映接收能力，cwnd 反映网络拥塞控制的允许在途量，发送还受拥塞算法、已在途数据与本地缓冲限制。滑动窗口提高流水线效率，但它本身不是全部可靠性机制。收到 TCP ACK 只说明对端协议栈接收相应字节，未证明订单事务提交。

**具体例子**：接收方磁盘慢使应用不再读取，接收窗口可能缩小；网络路径拥塞则可能触发丢包与 cwnd 调整。两者都“发不动”，诊断证据与解决方式不同。

**面试答法**：我分别回答丢了怎么办、对端装不下怎么办、网络装不下怎么办，再区分传输确认和业务确认。

**追问**：零窗口一定断连接吗？不一定，协议有相应探测机制，应用仍应设置业务超时。

**常见误区**：窗口越大越快；有 TCP ACK 即业务成功；校验和等同加密完整性保护。

**来源**：[FB-S019 RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293)、[FB-S023 RFC 5681 TCP 拥塞控制](https://www.rfc-editor.org/rfc/rfc5681)。业务组合、反例与答题组织为原创教学推导。

### FB20 如何解释慢启动，而不把 Reno 当作所有 TCP

**优先级：P1**

**知识点详解**：经典慢启动按 ACK 驱动增长，近似呈按 RTT 快速增长；达到门槛或检测拥塞后调整策略。Reno 的拥塞避免常用加性增、乘性减解释；CUBIC 用不同增长函数，不能统一叫线性增长。初始窗口固定 1 MSS 是过时概括，RFC 6928 讨论更大的初始窗口。BBR 等算法又有不同模型；面试先声明讲哪个算法，不宣称服务器一定使用它。

**具体例子**：高带宽长 RTT 链路上，初始发送额度和增长过程影响小文件/大文件表现；在有损无线网络上，把每次丢失都解释成队列拥塞也会导致不同效果。

**面试答法**：我用 Reno 说明基础，再补“增长规律依算法与实现”；需要优化时读取实际内核配置并压测，而非从题库猜。

**追问**：为何叫慢启动却增长很快？相对于立即用满链路，它从有限窗口探测，名称不表示线性缓慢增长。

**常见误区**：所有 Linux 都用相同算法；1 MSS 是通用初始值；拥塞窗口就是接收窗口。

**来源**：[FB-S023 RFC 5681 TCP 拥塞控制](https://www.rfc-editor.org/rfc/rfc5681)、[FB-S024 RFC 6928 初始拥塞窗口](https://www.rfc-editor.org/rfc/rfc6928)、[FB-S057 RFC 9438 CUBIC](https://datatracker.ietf.org/doc/html/rfc9438)。业务组合、反例与答题组织为原创教学推导。

### FB21 如何设计不会被拆包、粘连和超长输入破坏的分帧

**优先级：P0**

**知识点详解**：TCP read 返回的是当前可读字节，可能包含半条、多条或任意片段。应用协议可用固定长度、长度前缀或带转义分隔符。长度前缀解码应先累积完整头，再验证非负长度、最大帧长和溢出，再等足正文；分隔符协议要处理分隔符出现在内容中。流式解析还需限制未完成帧占用与等待时间，防止慢速大帧耗尽内存。

**具体例子**：发送两帧长度分别 3 和 5，接收端可能先收到 2 字节头再收到剩余所有字节。测试把同一编码数据在每个字节边界切开，结果仍应解出完全相同的两条消息。

**面试答法**：我把接收缓冲区当状态机，保存“等头/等体”和剩余长度，不把网络读取次数当消息次数。

**追问**：UTF-8 字符被切半怎么办？先按字节分帧或使用增量解码，不能随意把每块字节单独当完整字符串。

**常见误区**：关闭 Nagle 就不粘包；读到多少就是一条；信任客户端提供任意长度直接分配。

**来源**：[FB-S019 RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293)、[FB-S029 RFC 9112 HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112)。业务组合、反例与答题组织为原创教学推导。

### FB22 HTTP/1.1、HTTP/2、HTTP/3 的阻塞分别在哪里

**优先级：P0**

**知识点详解**：HTTP/1.1 默认持久连接，可复用 TCP；HTTP/1.0 也存在非默认 keep-alive 扩展，不能说绝对不支持。HTTP/2 通过二进制帧和流复用减轻 HTTP 层串行限制，但 TCP 丢失字节仍可能阻塞该连接上其他流的数据交付。HTTP/3 使用 QUIC 的独立流，减少这种跨流的传输层队头影响；同流有序约束、连接级拥塞和资源竞争仍存在。协议特性与浏览器产品支持必须分开。

**具体例子**：同一页面大图片流丢包，HTTP/2 连接中的其他流可能等待 TCP 缺口；HTTP/3 不要求所有流都等同一个字节缺口，但带宽拥塞仍影响所有请求。

**面试答法**：我从复用单位、底层传输和阻塞范围比较，不承诺升级协议必然让任何接口更快。

**追问**：HTTP/2 服务端推送可以直接当生产建议吗？必须核查客户端支持及收益；本讲义只讲协议能力，不承诺浏览器当前启用状态。

**常见误区**：HTTP/2 完全没有队头阻塞；HTTP/3 不可靠；把所有 HTTP 都称短连接文本协议。

**来源**：[FB-S028 RFC 9113 HTTP/2](https://www.rfc-editor.org/rfc/rfc9113)、[FB-S029 RFC 9112 HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112)、[FB-S021 RFC 9114 HTTP/3](https://www.rfc-editor.org/rfc/rfc9114)。业务组合、反例与答题组织为原创教学推导。

### FB23 TLS 1.3 如何完成认证与密钥建立

**优先级：P0**

**知识点详解**：HTTPS 是在安全传输上使用 HTTP，TLS 保护机密性、完整性与端点认证。常见 TLS 1.3 证书模式中，证书与签名验证对方身份，密钥交换产生共享秘密，再派生对称流量密钥保护数据；不能拿历史 RSA 密钥交换中“用公钥包住随机对称密钥”的图覆盖所有版本。客户端要验证域名、证书链与有效性；组织信任的私有 CA 也可用于 HTTPS，443 是默认端口不是强制端口。

**具体例子**：访问域名 A 却收到只对 B 有效的证书，即使连接能加密，也未正确认证 A，客户端应拒绝。重新绕过验证会把“加密到攻击者”误认为安全。

**面试答法**：我把身份认证、密钥协商、对称加密三件事分开，并先声明 TLS 版本与认证模式。

**追问**：TLS 1.3 的 0-RTT 能随便提交订单吗？早期数据存在重放风险，需限制可重复操作并遵守服务器策略。

**常见误区**：公钥私钥只是用来互相加密；HTTPS 能证明网站内容可信；证书检查失败只影响体验。

**来源**：[FB-S022 RFC 8446 TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446)。业务组合、反例与答题组织为原创教学推导。

### FB24 DNS 递归、迭代和缓存如何影响排障

**优先级：P1**

**知识点详解**：客户端通常把请求交给递归解析器，解析器可以从缓存应答，也可以根据委派逐级询问根、顶级域与权威服务器。递归是替请求方拿最终答案的职责，迭代是根据响应继续问下一方的查询过程。CNAME 会引入别名解析，负缓存会保留不存在等结果，因此真实访问不是每次经过所有层级。TTL 到期和各层缓存使记录修改并非瞬间处处生效。

**具体例子**：刚把服务迁到新 IP，部分用户仍访问旧地址：先比较权威结果与用户递归解析器的缓存，再看应用是否自己长期缓存，而不是立即归咎于负载均衡器。

**面试答法**：我分客户端缓存、递归解析器缓存和权威记录三个层次，用查询结果与 TTL 定位变化卡在哪里。

**追问**：DNS 切换能解决数据库主从切换吗？只能改变名称解析；应用连接、复制一致性、故障隔离和写入权限仍需处理。

**常见误区**：DNS 每次从根开始；改记录等于现有 TCP 连接自动换地址；DNS 只能使用 UDP。

**来源**：[FB-S027 RFC 1034 DNS](https://www.rfc-editor.org/rfc/rfc1034)。业务组合、反例与答题组织为原创教学推导。
