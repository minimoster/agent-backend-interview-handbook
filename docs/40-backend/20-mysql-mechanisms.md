### FJ26 MySQL 慢 SQL 怎样定位，EXPLAIN 应看哪些字段

**优先级：P0。**

**知识点详解**：慢接口未必慢在 SQL 执行：连接池等待、数据库锁、结果网络传输、应用反序列化都可能耗时。先关联请求追踪与具体 SQL/参数、数据量和调用次数，用慢查询日志、Performance Schema/sys 等证据定位。SHOW PROFILE/PROFILES 在 MySQL 8.4 已弃用，不能作为新项目首选。获取诊断记录也要控制 SQL 参数中的敏感信息。

普通 EXPLAIN 是优化器计划与估算；EXPLAIN ANALYZE 提供实际执行后的计时、行数、循环次数。传统格式重点字段：
- table / id / select_type：先辨认表、子查询与执行块，不把行号当完整物理顺序。
- type：访问方式，如 const、eq_ref、ref、range、index、ALL。它不是越过某条等级线就“合格”；小表全扫可能最划算。
- possible_keys 是候选，key 是选用者；key_len 表示使用键部分的长度，受类型、字符集、NULL 等影响，绝不是越短越快的评分。
- rows 是估计扫描数量，filtered 是估计过滤比例；连接内外层乘积及实际 loops 可能放大总工作量。
- Extra 的 Using index、Using index condition、Using temporary、Using filesort 分别涉及覆盖、索引条件下推、临时结果、额外排序，不能互为同义词；filesort 也不必然在磁盘完成。

**具体例子**（未运行）：查某租户最近20条订单，估算只扫100条，实际扫80万条。先确认该租户是否是异常大客户、统计是否过时、排序是否被联合索引满足，再比较改写或索引效果。衡量总耗时、扫描/返回比、锁时间和写入开销，不能只看 key 从 NULL 变成非 NULL。

**面试答法**：从端到端时间拆分开始，定位 SQL 后比较估算与实际、连接倍增和排序；索引是否出现只是线索，优化必须有相同条件下的前后证据。

**追问**：怎么证明不是锁等待？结合等待事件、事务和阻塞者信息。为什么参数一样计划仍变？数据分布、统计、配置与缓存状态均可能影响。

**误区**：type 至少 range 才合格；key_len 越短越好；EXPLAIN ANALYZE 是完全不执行的安全预览。

### FJ27 索引有哪些分类，“索引失效”为什么常常说得太粗

**优先级：P0。**

**知识点详解**：索引分类有多个维度：普通/唯一/主键强调约束；单列/联合强调键组成；全列/前缀强调存多少字段内容；聚簇/二级强调行组织；B-tree、全文、空间强调访问结构和查询语义。覆盖索引则描述某个查询所需信息恰好已在索引中，不是建表时另一种独立物理类型。

“没走索引”至少拆为两种：条件无法有效构造定位范围，或存在候选路径但优化器估算成本更高。例如对列包函数、隐式类型转换、前导 `%` 可能削弱普通 B-tree 的范围定位；但函数索引/生成列匹配、字符集与比较规则、返回列是否覆盖，都可能改变结果。OR 不是无条件失效，优化器还可能使用 index merge。缺少最左列，也可能全索引扫描或在满足限制时采用 skip scan；这并不意味着一定高效。

全文检索与空间查询各有适合的索引，不能因为倒排/空间能力不同就称其普遍低效。独立搜索引擎提供另一组功能和运维取舍，引入后还需处理数据同步、延迟、权限和结果一致性。

**具体例子**（未运行）：时间过滤可将 `DATE(created_at) = '2026-10-01'` 改写为同一天的半开时间区间，前提是业务时区和列类型一致。若真的需要函数表达式索引，则验证目标版本和表达式匹配，而非机械消灭所有函数。

**面试答法**：先分约束、物理组织和访问模式，再分析条件能否形成范围及成本是否划算；用计划证明，少说“永远失效”。

**追问**：前缀索引能保证任意查询都覆盖完整字符串吗？不能，只存前缀会缺失完整值。联合索引永远比 index merge 好吗？需看查询模式和成本。

**误区**：每一列建索引都改善性能；全文或空间索引普遍没用；没用来定位就等于索引完全没参与执行。

### FJ28 B+ 树、聚簇索引与覆盖查询怎样影响真正的页访问

**优先级：P0。**

**知识点详解**：InnoDB 的常规索引按页组织，内部节点引导查找，叶子按键序保存记录。高扇出帮助控制树高，有序叶子适合范围访问；比起二叉树，需要的层次通常少，比起纯哈希则保留范围与排序能力。默认页大小常见为 16KiB，但可配置，不能说任何 InnoDB 都固定 16KiB。缓冲池命中、键宽、行大小和树高决定实际 I/O，三层树不等于每次三次磁盘读。

有主键时用其作为聚簇索引；没有主键时选择合适的首个所有列非 NULL 的 UNIQUE 索引；再没有则生成隐藏聚簇键。因此“没主键就无聚簇索引”不成立。二级索引携带聚簇键，查询缺少列时再到聚簇记录取整行，称回表；宽主键会放大各二级索引。

覆盖能减少取完整行的机会，但不能绝对保证不访问聚簇记录。InnoDB 二级记录不带聚簇记录全部版本元数据；当二级记录有删除标记或页由较新事务修改时，MVCC 可见性检查可能需要查聚簇记录并用 undo 找合适版本。ICP 可先在索引中排除不符合条件的项，减少不必要回表，和覆盖不是同一机制。

**具体例子**：orders(id PK, user_id, total) 的 user_id 二级索引通常也带 id，查 id/user_id 有覆盖机会；加 total 通常需要回表。反过来，将一大段 JSON 加入联合索引只为覆盖，会显著增加写入和缓存成本，应先验证收益。

**面试答法**：页式有序树支持等值和范围；聚簇记录承载行，二级记录携带聚簇键。覆盖减少访问，但版本可见性会带来例外，不能只按返回列画绝对 I/O 数。

**追问**：为什么推荐稳定较短主键？降低二级索引和变更成本，仍需兼顾业务 ID 策略。回表一定比聚簇直接查慢吗？选择性、覆盖和缓存都影响整体代价。

**误区**：B+ 树永远三层；无主键表没有聚簇组织；Extra 显示 Using index 就能证明任何快照下零聚簇访问。

### FJ29 索引 (A,B,C) 跳过 B、出现多个范围时，到底用了哪些列

**优先级：P0。**

**知识点详解**：联合索引按字典序排列：先 A，同一 A 内再 B，同一 A/B 内再 C。固定 A 后，B 仍然有序；问题是不同 B 组之间 C 不保证全局单调。因此 `A=7 AND C>20` 通常可先以 A 缩小范围，再利用 C 过滤；不能解释成“固定 A 后 B 变无序”。适合时 ICP 在二级索引层过滤 C，若查询覆盖全部所需列还可能避免部分回表。

讨论“用了后面的列”必须指出用途：形成扫描区间、在索引记录中过滤、覆盖输出、满足排序，四种并不相同。MySQL 8.4 手册对普通多列 range 构造的说明是：等值条件可继续用后续键部分；遇到不等式、BETWEEN、LIKE 等范围操作后，该普通规则不再继续扩展后续键部分。这不意味着后列完全无用，也不能仅凭 key_len 值证明所有条件都用于精确定位，NULL 检查等转换也会影响键长度。

对离散整数范围，`B BETWEEN 10 AND 12` 在数学上可写为 B IN(10,11,12)，但优化器是否自动等价改写不能假定。显式 IN 可形成多个等值范围，使每个范围继续使用后列；值非常多时又会增加优化与扫描成本。特殊路径、版本优化和代价选择应以 EXPLAIN、optimizer trace 和实测确认；本章没有运行 MySQL，不宣称已测得某个 BETWEEN 反例。

**具体例子**（索引顺序示意）：
```text
(7,1,10) (7,1,40) (7,2,5) (7,2,30)
```
B 从1到2有序，C 却是10、40、5、30。A=7/C>20 的结果是第2、4项，不能用 C 的一次全局二分就直接得到两条。若 A/B 都等值，C 范围则在该组内连续。WHERE 中把 C 写在 A 前不会改变索引列顺序。

**面试答法**：先画键元组排序，再分别讲区间、ICP、覆盖和排序；普通范围规则有边界，但“后列全失效”是错误表达，实际路径必须看计划。

**追问**：没 A 条件能否使用 (A,B,C)？可能索引扫描或满足条件的 skip scan，但不能保证收益。两个范围条件是否能把二维矩形精确表示成一段字典序区间？通常不能，仍需过滤或多段范围。

**误区**：固定 A 后 B 无序；BETWEEN 一律保证使用所有后列；看到 key_len 较长就认定访问行一定更少。

键顺序示意为原创推导。

### FJ30 隔离级别如何影响读异常，InnoDB RR 到底怎么处理幻读

**优先级：P0。**

**知识点详解**：脏读是读到其他事务尚未提交的数据；不可重复读是同一记录在重复读取间发生变化；幻读是满足谓词的结果集合发生变化，不必表现为行数增加，例如删一条再插一条也能保持数量却改变集合。隔离的强弱不是“有无任何互相影响”，更不能把 ACID 一致性等同于副本强一致。

InnoDB 默认 REPEATABLE READ。普通非锁定一致性 SELECT 在 RR 通常复用第一次此类读取建立的 Read View，在 RC 每次此类语句建立新视图；BEGIN 本身一般不等于已经创建一致性读快照。自身写入可见，锁定读与 UPDATE/DELETE 还按各自规则访问当前状态，因此混用读法时不能只套“本事务永远看旧版本”。

RR 下范围锁定读常借 next-key 锁限制相关间隙插入，以协调幻行；唯一索引精确命中等情况锁范围又不同。RC 一般减少间隙锁使用，但外键/重复键检查等仍有例外。SERIALIZABLE 追求可等价于串行顺序的结果，不等于操作系统必须一次只跑一个事务；等待、死锁与重试仍需处理。

**具体例子**（时序练习，未运行）：A 在 RR 普通查库存看到10；B 更新为8并提交；A 普通重查仍可能看到10。若 A 改为 FOR UPDATE，不能保证继续读同一历史值，且要处理锁等待。想扣库存优先采用条件 UPDATE 并检查受影响行数，见 [B18](02-databases-and-sql.md#b18)。

**面试答法**：先说数据库/隔离级别，再说读法。RR 的一致性读靠版本视图，范围锁定读用锁协调；隔离名称不代表所有读写都完全互不影响。

**追问**：RR 是否解决所有业务并发不变量？不是，跨行条件还需约束、锁或更强事务方案。用 COUNT 不变能证明无幻读吗？不能证明集合完全相同。

**误区**：BEGIN 立即固定所有查询快照；幻读只是行数变多；串行化必定物理单线程执行。

### FJ31 undo、redo、binlog 与 Read View 怎样共同支撑事务

**优先级：P0。**

**知识点详解**：ACID 不对应四个互不相关的开关。原子性需要撤销未完成事务；隔离需要锁与版本可见性；持久性需要崩溃恢复协议、刷盘和可靠存储；一致性还依赖约束与业务正确写法。只有日志而没有业务不变量，仍可能原子地提交一笔错误转账。

- undo 保存撤销所需信息，也让一致性读重构旧版本；不是为每个事务复制整库。长事务所需旧版本会限制 purge 进展。
- redo 记录足够的修改信息，用于故障后重建未落稳的数据页变化。它可能包含未提交事务的修改，恢复不是“只重放已提交 redo”；未完成事务还需回滚。
- binlog 在服务器层记录用于复制和时间点恢复的事件，不能替代 InnoDB redo；恢复历史还需要一致的基线备份及连续日志。不同格式也不能简单概括为永远原始 SQL。
- Read View 保存可见性判断所需边界、自身事务标识与生成时活跃事务集合。对某版本的修改事务 ID，先处理自身可见，再根据高低边界与活跃集合决定；不可见时沿 undo 寻找较早版本。不能只比较“提交时间早晚”。

以 MySQL 8.4 源码命名为例：比 m_up_limit_id 小的旧事务可见，自己可见；大于等于 m_low_limit_id 的新事务不可见；中间区间再检查 m_ids 中是否为创建视图时活跃事务。名称容易反直觉，面试先讲语义，不硬背 min/max 别名。RR 通常首次一致性读建视图，RC 逐次一致性读建立，详见 FJ30。

提交是否能抗主机掉电还要看 innodb_flush_log_at_trx_commit、sync_binlog、操作系统和存储是否正确兑现同步写语义；配置降低持久性换吞吐时必须说明故障损失窗口。复制与备份又是另一层恢复能力，不能直接说“事务提交后任何故障都零丢失”。

**具体例子**：更新库存从10到9，内存页可先变脏，相关日志与事务协议使引擎无需每次提交立即把所有变更数据页随机刷盘。崩溃恢复先重建必要页状态，再处理未提交事务；读事务若需要先前的10，可通过版本链得到。

**面试答法**：undo 管撤销与旧版本，redo 管崩溃后的页修改恢复，binlog 管复制/历史重放，Read View 决定读哪个版本；持久性承诺必须附刷盘和故障模型。

**追问**：有 binlog 无备份能方便恢复到任意时点吗？还要有完整可用历史和基线，不能默认。删完大表后旧版本立即清空吗？要看仍在用的视图和清理进程。

**误区**：redo 只有提交后才写；undo 仅服务 rollback；BEGIN 就复制整库；一个日志独自保证全部 ACID。

### FJ32 什么时候分库分表，单表“最大多少行”怎样回答

**优先级：P1。**

**知识点详解**：垂直拆库按业务域拆分表和职责，垂直拆表把宽字段、冷字段拆到关联表；水平拆分保留近似相同结构，把不同行按租户、时间或哈希等路由到不同分片。前者处理耦合、资源隔离与宽行，后者分散数据/负载。把数据切成同实例里的许多表不一定突破该机器 CPU、I/O 和连接限制；数据库分区也不自动等于跨服务器分片。

不能用“一千万/两千万行必拆”作通用阈值。先测工作集、索引大小、读写 QPS、热点分布、备份恢复时间、DDL 窗口及 p99。归档、正确索引、减少扫描、升级资源或读扩展可能更简单。引入水平分片后，必须设计分片键、全局唯一 ID、跨分片关联/聚合、事务、一致性、扩容搬迁和故障回退。按 user_id 路由能让单用户查询集中，却使全站时间线需要多分片归并；时间分片便于归档，但最近分片可能热。

MySQL 8.4 InnoDB 表空间理论上限依页大小变化，16KiB 页在手册中对应64TB量级（按二进制页容量约64TiB）；其他页大小不同，文件系统和配置还会进一步限制。不能把文件系统某配置下的单文件上限当统一数据库上限。行数乘平均业务字段长度只算粗下界，还要加聚簇记录元数据、二级索引、页空闲、碎片、溢出页、日志/备份/迁移空间。

**具体例子**（假设估算，未测量）：2亿行、每行有效内容500字节约100GB十进制原始内容，但索引、页利用率和复制副本使实际容量显著更大。应从代表性样本导入测量每行“数据＋全部索引”占用，再乘规模并给扩容/备份留余量，而非据100GB直接采购。

**面试答法**：先证明单点瓶颈和运维窗口，再选垂直或水平拆分；行数没有通用阈值，理论容量不等于可接受性能或恢复时间。

**追问**：取模分片扩容为什么麻烦？改变模数会改变大量路由，必须迁移和切流，而非只加一台机器。哈希平均分布能消灭单租户热点吗？不能拆开单个热点业务键。

**误区**：分表后每条查询自然只访问一片；忽略跨片唯一性与事务；把64TB描述为任何配置都固定可用容量。

拆分决策和容量示例为原创工程分析。

<a id="fj33"></a>
### FJ33 MySQL 复制如何工作，读写分离为什么会读不到刚写的数据

**优先级：P1。**

**知识点详解**：经典基于 binlog 的复制中，源端发送日志事件，副本接收后写 relay log，再由应用线程执行。现代 MySQL 支持协调器和多个并行 worker，不能永远画成唯一 SQL 线程串行重放。接收完成、落盘完成、事务应用完成和客户端可见是不同状态。

普通异步复制允许源已提交并响应时副本仍未应用，因而读写分离会出现陈旧读。半同步等机制等待的确认也不应自动解释为所有副本已执行且能读到。具体故障转移的数据安全还依赖选主、持久化和复制配置。

路由要按读语义：刚创建订单后的确认可读主；依赖前次写入的查询可携带已提交 GTID，在选定副本等待其执行到目标并设超时/回退；允许陈旧的统计可读副本。事务中的锁定读、读后写和一致性快照不应被简单按 SQL 是否以 SELECT 开头拆到不同节点。固定睡100ms只能降低某种延迟下的概率，不证明复制已追上。

**具体例子**（时序示例，未运行）：写入 order=42 的提交已返回；页面立即查副本得到不存在，用户误以为失败再次提交。解决不仅是读主，还需要请求幂等，避免切换与网络重试生成两笔订单。监控复制延迟时同时看接收、应用和错误状态。

**面试答法**：复制是日志传送加副本应用，异步会产生读后写缺口；路由按一致性需求，关键确认读主或等指定提交点，超时有明确策略。

**追问**：多个副本中等到了一个，能随便换另一个读吗？不行，等待保证绑定其执行状态。并行应用越多一定越快吗？受依赖、锁竞争和 I/O 限制。

**误区**：全部 SELECT 一律副本；半同步等于所有副本已应用；收到写成功就表示任何选出的新主都保有该写。

路由示例为基于这些机制的原创设计。

### FJ34 MySQL 与 Redis 应怎样分工，为什么不能只比较“毫秒与微秒”

**优先级：P0。**

**知识点详解**：MySQL/InnoDB 提供关系模型、索引查询、约束、事务和成熟的持久化恢复能力；Redis 提供内存数据结构及低开销访问，可承担缓存、计数、排行榜和部分实时状态。两者都有内存、网络、CPU、持久化配置与故障边界；数据库命中缓冲池不等于每次磁盘随机读，Redis 操作巨大值也不等于永远微秒级。

选型先问权威数据在哪里、允许丢多少、允许旧多久、查询需要关联/约束还是简单键操作、恢复怎样做。常见组合让关系库保存交易权威状态，Redis 缓存可重建视图；但不是说 Redis 只能做缓存，也不是说所有 MySQL 都任何故障零丢失。把 Redis 当权威数据时要明确持久化、备份、故障切换和业务补偿，而非仅开启 AOF 即结束设计。

**具体例子**：商品详情读多，可在提交数据库变更后失效 Redis 缓存；最终库存扣减由数据库条件更新/约束保证。积分展示可以允许短暂旧值，而支付金额核对应走权威一致路径。基准测试固定硬件、网络、payload、并发、持久化和目标命令后才比较吞吐/延迟。

**面试答法**：我按数据语义与故障承诺分工，再谈延迟；缓存减少常见读取成本，但不会自动接管事务不变量或实现双系统原子提交。

**追问**：缓存宕机可以全部请求直接打数据库吗？需回源限流、优先级和容量预案。Redis 有事务是否等同 InnoDB 事务？模型与回滚语义不同，需独立比较。

**误区**：MySQL 每次都读磁盘；Redis 持久化就绝不丢；用两个没有条件的延迟数字证明架构优劣。

### FJ35 UNION 与 UNION ALL 去重什么，结果有默认顺序吗

**优先级：P0。**

**知识点详解**：UNION 合并兼容列结构的查询结果，并默认按完整结果行消除重复；UNION ALL 保留所有行。它们不是 JOIN：JOIN 横向组合关联行的列，UNION 纵向追加结果行。去重有额外工作，但算法及是否物化由优化器决定，不能说必然通过排序实现。

默认去重并不承诺输出按某列排序，要明确最外层 ORDER BY。选择 UNION ALL 的前提是业务确实需要重复，或可证明各来源互斥；不能为了快就改变统计语义。两边列数必须匹配，结果类型/字符集和比较规则影响转换与判重。若投影了来源标签，本来同一业务 id 的两行也可能变成不同完整结果行。

**具体例子**（未运行）：`SELECT 7 AS id UNION SELECT 7` 返回一个7；换 UNION ALL 返回两个7。若每边再各带不同的 source 列，UNION 不会只按 id 去重。合并两个租户订单源时，要先明确订单号是否全局唯一，以及去重按什么业务键。

**面试答法**：UNION 对整行去重，ALL 保留重复，二者都需显式最终排序；先保证语义，再比较去重成本。

**追问**：每个分支都 ORDER BY 就能保证总结果顺序吗？不能代替最外层排序。每组第二名用哪一个窗口函数？取决于第二行、竞赛名次、第二个不同分数，完整例子见 [S01](../70-practice/sql-nine-worked-problems.md#s01)。

**误区**：UNION 自带按第一列升序；UNION 只按主键判重；UNION ALL 在任何业务场景都可替换 UNION。
