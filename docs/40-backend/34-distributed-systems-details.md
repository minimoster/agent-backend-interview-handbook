### FB53 CAP 的 C 和 A 应怎样按故障模型理解

**优先级：P1**

**知识点详解**：CAP 讨论存在网络分区时，不可能同时对所有相关请求满足线性一致性与所定义的可用性。线性一致要求操作看似在调用与返回之间某一时刻原子发生，并尊重真实时间先后，不要求所有副本在每个物理瞬间字节相同。可用性指非故障节点接到请求最终应答，不等于普通月度 SLA。分区是需要面对的网络故障，不是正常部署随手选择丢掉的一个功能。

**具体例子**：两机房失联，都允许对同一最后一张券成功扣减会破坏统一的单件库存事实；若只有能获得权威多数的一侧继续写，另一侧必须拒绝或等待。展示缓存则可以采用不同一致性承诺。

**面试答法**：我先声明分区期间讨论的具体操作，再说明是拒绝/等待还是接受可能冲突的结果；不会把产品永久贴成简单 CP/AP 标签。

**追问**：正常网络时是否没有权衡？仍有延迟、同步与成本取舍，但那不是把 CAP 三选二口诀机械套用。

**常见误区**：C 是所有副本瞬时完全一致；A 是 99.99%；一次系统只能为所有数据选择一种一致性。

### FB54 分布式锁怎样实现所有权、重入和过期写保护

**优先级：P0**

**知识点详解**：Redis 最小租约可用 SET key unique_token NX PX lease，一条命令原子设置身份和有效期；解锁用原子比较当前 token 后删除，避免删除新持有者的锁。token 必须跨客户端唯一，单线程 ID 不够。重入需要共享存储中核对持有者并维护计数，ThreadLocal 只能记录本地信息。ZooKeeper 临时顺序节点可以排队协调，数据库也可用唯一约束/锁；三者都要分析失联、会话过期和旧执行者恢复。资源端 fencing token 或条件版本保护实际写入。

**具体例子**：A 拿到版本 41 后暂停，B 拿到 42 并写入，资源端拒绝后来的 41；随机 UUID 只能区分所有者，不能直接提供单调比较。正常结束显式 unlock，崩溃依赖租期/会话，不假设线程结束就跨网络立即释放。

**面试答法**：我把获取原子性、解锁身份和资源写保护分三层；若只为了数据库行互斥，优先考虑数据库本身的事务约束。

**追问**：业务已提交但 unlock 超时是否订单失败？业务成功事实不随清理失败改变；记录告警并按安全身份重试释放，不能触发无条件业务回滚。

**常见误区**：SETNX 再 EXPIRE 没有风险；GET 后 DEL 两步是原子；有锁就不需要幂等；锁越粗吞吐越好。

### FB55 Redlock 的多数租约需要哪些假设

**优先级：P1**

**知识点详解**：Redlock 在多个独立 Redis 实例上尝试获取同一随机 token 的租约，以多数成功和剩余有效时间判断是否获得锁。获取耗时必须扣除，还需考虑时钟漂移安全余量；失败后释放已获取锁并退避重试。它不是把同一主从集群的若干副本当独立节点，也不会给业务数据库自动加上 fencing。若业务正确性依赖严格互斥，必须明示暂停、时钟和网络假设，并由资源端提供过期执行者保护。

**具体例子**：五节点方案只取得三把锁但用时已超过有效租期，不能判成功；即便成功，客户端暂停到租约过期后也不得假装仍有业务写权限。

**面试答法**：我先描述多数和租期扣减，再主动说明时钟与暂停假设。对强正确性资源，不把“获得多数锁”当作足够的完整证明。

**追问**：复制多几个锁副本就等于共识日志吗？不是，租约协议与协调所有业务状态的共识系统有不同边界。

**常见误区**：拿到任意三把锁就永久安全；Redlock 修复 Redis 主从丢库存；没有 fencing 也可绝对阻止旧客户端。

### FB56 2PC、TCC、Saga、Outbox 怎样围绕不变量选择

**优先级：P1**

**知识点详解**：2PC 协调参与者准备与提交，增加协调和阻塞/恢复成本，资源需支持相应协议。TCC 将业务拆成 Try 预留、Confirm 确认、Cancel 释放，需处理幂等、空回滚和悬挂；Saga 用本地事务序列与业务补偿协调，补偿是新动作而非时间倒流。Outbox 在同库事务写业务和待发事件，异步可靠发布并要求消费幂等。选择取决于能否预留、能否补偿、用户能否接受中间态。

**具体例子**：酒店已确认但机票失败，Saga 可以尝试取消酒店，但取消可能有费用或失败，所以原计划不能承诺等价数据库 rollback。库存预留则可用带有效期的 TCC，但迟到 Confirm 不应复活已取消预留。

**面试答法**：我先定义哪些状态绝不能出现、哪些中间态可展示，再选事务模式，最后讲恢复记录、重试和人工处置。

**追问**：为什么不能在一个长数据库事务里调用所有远端？远端故障使锁长期占用，本地 rollback 也撤销不了已完成外部副作用。

**常见误区**：Saga 自动强一致；Outbox 从不重复；TCC 三个接口无需持久状态。

### FB57 唯一标识怎样在顺序、可用性和恢复之间取舍

**优先级：P0**

**知识点详解**：自增/号段依赖持久分配协调，适合可接受中心服务或批量取号的场景；UUID v4 偏随机，v7 带时间顺序信息，不能说所有 UUID 无序。经典 Snowflake 把时间差、节点与毫秒内序列组合，位宽是实现约定；常见 41/10/12 只作为实例，毫秒内最多 4096 个序列值。唯一性要求节点 ID 不重复、同时间序列不复用，并处理时钟回退和重启。Redis INCR 若异步复制丢进度也可能重号。

**具体例子**：时钟回退时可以在小回退范围等待，超阈值拒绝取号；也可采用持久逻辑时间等不同策略，但需说明跨重启恢复。分配不同机器 ID 不能解决同节点回退后重复使用旧毫秒序列。

**面试答法**：我先问 ID 是否暴露时间、是否要求趋势有序、是否能容忍暂停，再选择方案；业务唯一索引仍是最后检测防线。

**追问**：UUID 能当主键吗？可以评估版本、二进制存储、索引局部性和写负载，不做一刀切结论。

**常见误区**：全局唯一等于全局连续；Snowflake 固定位宽适用于全部实现；趋势递增等于严格真实时间全序。

### FB58 RPC 和 HTTP 为什么不是同一层次的替代品

**优先级：P0**

**知识点详解**：RPC 是远端过程调用的交互抽象，HTTP 是传输应用语义的协议；RPC 可以运行在 HTTP 上。gRPC 通常用 protobuf 定义消息/服务，并使用 HTTP/2 支持单次、服务端流、客户端流与双向流。远端调用不是本地调用：会超时、部分失败、重复、版本不兼容，并需要 deadline、取消、重试策略、负载均衡与鉴权。HTTP 也可持久连接和二进制内容，不能被概括成短连接文本。

**具体例子**：会员服务调用权益服务，客户端超时后服务端可能已扣权益。换成 gRPC 不会自动消除不确定结果，仍须业务幂等键和查询接口。

**面试答法**：我先分层，再比较接口契约、序列化、流式能力和运维生态；性能用实际负载与协议设置验证。

**追问**：RPC 减少延迟主要看什么？连接复用、序列化、批量、服务端处理、跨区 RTT 与排队常比框架名字重要。

**常见误区**：RPC 一定不用 HTTP；接口生成能解决所有版本兼容；超时可无限重试。

### FB59 Dubbo 注册中心和调用路径怎样分工

**优先级：P1**

**知识点详解**：提供方发布服务与可发现元数据，消费方经注册中心发现并更新可用地址，再按路由和负载均衡直接调用提供方；注册中心通常不转发每次业务请求。客户端缓存地址可让短暂注册中心故障与存量调用分离，但新实例发现和健康变化会受影响。Dubbo 版本存在接口级与应用级服务发现差异，应说明所用模型，而不是把单张历史架构图当全部版本。

**具体例子**：注册中心短暂失联时，旧连接与缓存地址可能继续工作；若同时扩容新提供者，消费者未必发现它。服务恢复后应检查地址刷新、陈旧节点清理与调用失败率。

**面试答法**：我画注册/订阅控制链路和业务直连数据链路两条线，再说明注册中心故障对两条链路的不同影响。

**追问**：负载均衡均匀分请求就足够吗？实例容量、长连接、热点方法、熔断和尾延迟也影响选择。

**常见误区**：每个调用必须经注册中心代理；注册中心挂了所有存量调用必立刻失败。

### FB60 消息积压怎样扩容才会真正追上

**优先级：P0**

**知识点详解**：先观察生产速率 λ、有效消费速率 μ、最老事件年龄、分区倾斜、失败重试与下游瓶颈。若 μ≤λ，积压不会清空；若 μ>λ，理想清空时间约为积压量/(μ-λ)，实际还受故障与峰值影响。增加消费者受分区可并行度、键串行要求和数据库容量限制。临时转发新 topic 必须保存原 ID、可靠交接与进度边界，不能无保护搬消息。

**具体例子**：教学假设积压 30 万条，持续生产 1000/s，恢复后消费 2000/s，理想约 300 秒清空。若扩容把数据库拖垮，使失败重试加倍，账面消费者数虽更多，有效 μ 反而下降。

**面试答法**：我先找有效吞吐损失，再扩最窄环节；所有重放保持幂等，并监控追赶期间业务延迟和下游余量。

**追问**：何时放弃顺序？只有业务明确允许交换或按版本处理，不能为追赶默认改变一致性契约。

**常见误区**：加消费者必然加速；积压条数下降就表示用户全部处理成功；重试吞吐算成功吞吐。

### FB61 一致性哈希和虚拟节点解决了什么，没解决什么

**优先级：P1**

**知识点详解**：一致性哈希把节点和键放到哈希空间，通常按环上后继归属；节点增减只改变部分区间，而简单取模常使更多键改归属。虚拟节点让一个物理节点分散承接多个区间，改善均衡并可表达权重，哈希空间不限定为 32 位。数据迁移、故障检测、副本一致性不由哈希函数自动完成；单个超热键依然只落某个逻辑归属，不能靠虚拟节点拆散。

**具体例子**：缓存池新增节点后，一部分键需要重新回源，仍要对冷启动限流。若某明星商户占一半读流量，可用只读多副本/本地缓存等单独策略，而不是仅把虚拟节点从 100 增到 1000。

**面试答法**：我讲清减少路由变化的目标，再补负载分布与热键例外，不把名字里的“一致性”解释为数据强一致。

**追问**：缩容立即删除节点会怎样？尚未迁移/重建的数据可能暂不可得，应先排空并控制回源冲击。

**常见误区**：一致性哈希保证副本一致；虚拟节点解决任何热点；加节点完全没有缓存穿透成本。

### FB62 复制、Sentinel、Cluster 的职责怎样区别

**优先级：P0**

**知识点详解**：复制把主数据传播到副本，提供读取副本及恢复基础；Sentinel 监测非分片主从组并协调切换；Cluster 用槽分片路由数据，并结合副本与故障转移扩展容量。它们不是三种互斥的存储结构，Cluster 也依赖复制。异步复制意味着读副本可能陈旧、切换可能丢近期写；WAIT 能提高已传播副本证据，但不能把部署自动变成强一致数据库。客户端还需支持拓扑变化与 MOVED/ASK 等重定向。

**具体例子**：读多写少商户详情可接受短时从库陈旧，库存提交却不能直接依赖同一陈旧读。多键 Lua 在 Cluster 需要同槽设计，否则单实例脚本搬过去会失败。

**面试答法**：我用扩读、自动切换、分片扩容三种需求解释组件，再明确延迟复制与多键原子范围。

**追问**：为何三个主节点没有副本不是完整容灾？每个主节点的槽一旦不可服务，数据没有可晋升副本来接管。

**常见误区**：Cluster 不使用主从复制；Sentinel 自动扩展存储容量；WAIT 等价跨所有故障的强一致提交。

### FB63 Quartz、XXL-JOB、ElasticJob 如何按任务语义选择

**优先级：P1**

**知识点详解**：Quartz 关注触发器和作业持久化，可用 JDBC JobStore 集群协调触发；XXL-JOB 提供中心调度与执行器管理的工程控制面；ElasticJob 强调分布式弹性分片作业。比较时应检查定时精度、错过触发策略、分片、重试、故障恢复、权限与操作界面，而不是笼统排名性能或普及度。任何调度都可能在崩溃边界重复执行，业务要以 job_key+计划时刻/业务周期标识一次逻辑运行。

**具体例子**：每日结算任务用 settlement_date 作为业务唯一键，重复触发只继续已有批次。某分片完成后节点崩溃，重调度时检查持久分片进度而不是从内存推测。

**面试答法**：我先定义任务是否可重复、是否有分片和补跑需求，再比较框架；调度成功不等于业务成功。

**追问**：长任务错过下次触发怎么办？明确允许重叠、跳过、排队还是合并，不能由线程池拥塞偶然决定。

**常见误区**：调度器保证所有副作用恰好一次；框架自带重试就无需状态表；直接用 popularity 当选型证据。
