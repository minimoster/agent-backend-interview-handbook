### B01 HTTP 的安全性、幂等性与状态码分别解决什么问题

**优先级：P0**

**知识点详解**： “安全方法”指请求语义不要求修改资源；“幂等”指相同请求执行一次和多次的预期资源效果相同，响应内容不一定相同。GET 属于安全且幂等的方法；PUT、DELETE 是幂等方法；POST 不天然幂等。401 表示缺少有效认证，403 表示服务器理解请求但拒绝执行，409 表示与资源当前状态冲突。

**具体例子**： 重复删除同一条草稿，第一次成功，第二次可能返回不存在；草稿最终都不存在，因此不因状态码不同而失去幂等性。创建订单的 POST 应由业务请求号防重。

**面试答法**： 我先区分协议语义与业务实现，再决定能否自动重试；方法名不会自动帮数据库实现幂等。

**追问**： 请求超时能否判断订单没创建？不能，响应可能丢失，应查询业务请求号对应结果。

**常见误区**： 把幂等理解为“返回值永远相同”，或者说 GET 在实现上绝不产生日志等副作用。

### B02 HTTP 缓存里的 no-cache、no-store 和协商缓存有什么区别

**优先级：P1**

**知识点详解**： 新鲜度决定缓存响应能否直接复用；验证器用于询问内容是否变化。no-cache 允许存储，但复用前需要成功验证；no-store 要求不存储。缓存过期后，可以携带 ETag 对应的条件请求，未变化时用 304 复用原内容。

**具体例子**： 商品图片可以长时间缓存；个人订单结果应谨慎设置缓存范围和策略，不能只因为接口用 GET 就让公共代理缓存。

**面试答法**： 我区分“可否存储”“多久可直接复用”“过期后如何验证”，并考虑用户身份、Vary 和共享缓存。

**追问**： 304 为什么不能直接当成一份完整业务响应？它需要和缓存中的表示结合。

**常见误区**： 把 no-cache 翻译成“完全不缓存”，把缓存当成所有用户都能共享的一份数据。

### B03 TCP 为什么可靠，又为什么会出现所谓粘包

**优先级：P0**

**知识点详解**： TCP 提供有序字节流，通过序号、确认、重传等机制处理丢失和乱序。流量控制关注接收端是否处理得过来；拥塞控制关注网络承载能力。字节流不保留应用每次 write 的消息边界。

**具体例子**： 发送方先写“hello”，再写“world”，接收方可能一次读到十个字节，也可能分多次读。应用可以设计“长度字段＋消息体”，读够指定长度再解析。

**面试答法**： TCP 保证字节流层面的可靠、有序交付；业务消息分帧和超时后的业务结果确认仍由应用负责。

**追问**： 一条消息超过一次 read 的缓冲区怎么办？循环累积，直到帧完整，并设置最大帧长。

**常见误区**： 把一次 read 当成一条完整 JSON；把 TCP 确认等同于远端订单已提交。

### B04 三次握手、连接关闭与 TIME_WAIT 如何联系起来

**优先级：P0**

**知识点详解**： 握手同步双方序号并确认双向通信状态。TCP 两个方向可分别关闭，所以关闭连接不是一个不可分的动作。TIME_WAIT 让旧连接中的延迟报文有时间消失，并使最终确认丢失后的关闭过程有机会完成；常见主动关闭方会进入该状态，但同时关闭等情况不能用一句“只有客户端进入”概括。

**具体例子**： 服务每次请求都新建连接、立即主动关闭，会积累短连接及 TIME_WAIT。应先观察连接复用、流量和端口占用，再决定调整策略。

**面试答法**： 我会画状态变化解释用途，不把握手和挥手只背成数字。

**追问**： 关闭为什么不一定恰好四个报文？确认与 FIN 在具体场景中可以组合。

**常见误区**： 看到 TIME_WAIT 就认为泄漏，直接降低系统参数而不检查请求模式。

### B05 HTTP 1.1、2、3 的主要差别是什么

**优先级：P0**

**知识点详解**： HTTP/2 用二进制帧承载多条流，让多个请求共享连接，并压缩首部；它运行在 TCP 上，TCP 丢包仍可能阻塞该连接后续字节交付。HTTP/3 基于 QUIC，独立流减少跨流的传输层队头阻塞，但不是“完全没有等待”，同一流内仍有有序性要求。

**具体例子**： 页面同时请求多个资源时，HTTP/2 可以在一条连接上交错发送不同流的帧。网络丢包时要区分“应用流多路复用”与“底层字节交付”。

**面试答法**： 我从连接复用、流、多路复用和队头阻塞分层比较，不仅说版本越高越快。

**追问**： HTTP/3 是否等于 UDP 不可靠？不是，QUIC 在 UDP 上提供所需的可靠传输与安全能力。

**常见误区**： 说 HTTP/2 已经彻底消除队头阻塞，或把 HTTP/3 说成 HTTP/2 简单换一个协议头。

### B06 HTTPS 中 TLS 到底保护了什么

**优先级：P0**

**知识点详解**： TLS 建立加密与完整性保护通道，并通过证书等机制认证对端。证书不是直接拿来加密所有业务数据；握手协商后，应用数据由派生出的会话密钥保护。TLS 1.3 的 0-RTT 数据有重放风险，不能随意用于有副作用操作。

**具体例子**： 客户端校验证书链和目标主机身份后再发送登录请求；关闭证书校验虽然可能“连通”，却丢掉重要身份保证。

**面试答法**： HTTPS 保护传输过程中的机密性、完整性和服务器身份；不能代替应用权限检查，也不保证服务器本身可信无漏洞。

**追问**： 有 HTTPS 为什么还需要登录和鉴权？传输安全不回答“这个用户能否访问这个订单”。

**常见误区**： 把证书、非对称密码和对称会话密钥混成一个东西；认为加密能阻止所有重放或越权。

### B07 AI 输出流为什么常用 SSE，断线如何恢复

**优先级：P0**

**知识点详解**： SSE 是服务器向客户端持续发送文本事件的方式，使用 text/event-stream。原生 EventSource 支持重连和 Last-Event-ID，但“记住最后事件编号”不等于服务器自动保存和重放全部结果。服务端仍需定义事件编号、保存期限和恢复语义。

**具体例子**： 一次生成的事件编号为 run-8/1、run-8/2……客户端收到 12 后断线。重新连接时，若后端保留了事件，可从 13 补发；若未保存，应清楚报告不可恢复，而不是重新生成一份并假装接着原文本。

**面试答法**： 单向输出适合 SSE。我还会处理代理缓冲、及时 flush、心跳、断线取消、慢客户端及终止事件。

**追问**： 原生 EventSource 能否任意设置 Authorization 首部和 POST 请求体？其接口不提供这种通用请求配置；可选择适当鉴权设计或基于 fetch 读取流。

**常见误区**： 只把响应分块就称为完整 SSE；认为网络重连等于恢复模型状态。

恢复方案与事件编号为原创设计示例。

### B08 WebSocket 与 SSE 怎么选择

**优先级：P1**

**知识点详解**： WebSocket 提供双向消息通信，并定义数据帧、关闭和 Ping/Pong 等机制。持续双向交互适合它；仅服务端推送文本时 SSE 通常更直接。协议能传消息，不代表自动拥有业务确认、历史存储或重连后补发。

**具体例子**： 实时协作编辑需要客户端持续发送操作并接收他人更新，可选择 WebSocket；一次问答的文本流可以用 SSE。两者都需要限制连接数和单条消息大小。

**面试答法**： 我根据通信方向和应用需求选协议，再单独设计心跳、鉴权、消息编号与重连补偿。

**追问**： Ping/Pong 成功是否证明业务消费者已经写入数据库？不能，它只说明相应协议交互完成。

**常见误区**： 把 WebSocket 当成自带可靠业务消息队列，或认为连接不断开就没有任何资源上限。
