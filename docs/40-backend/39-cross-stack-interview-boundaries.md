# 跨栈面试追问：原子写、迁移与共享凭据状态

[返回后端目录](README.md) · [公开样本](../60-interviews/README.md)

本章用合成情境讲解原子写、在线迁移与共享凭据状态。核查日期2026-10-10；第三方数据库和云服务实验尚未运行。

<a id="mongodb-atomicity"></a>

## MongoDB单文档原子性与业务不变量

单文档更新可原子修改多个字段，不意味着“先查再写”两个请求是一个原子操作。教学库存10：把过滤条件写成ID与 `stock >= 1`，更新用 `$inc` 扣1并检查是否匹配，避免所有请求先读10再各自写9。多个文档需要保持共同不变量时，评估数据建模或事务；`updateMany`并非把所有文档作为一项原子修改。

乐观更正可带预期version：读取v4后更新时要求version仍是4，并递增到5；另一个提交者再以4提交应匹配失败，重新读取或报告冲突。只过滤不变ID再set同一字段，会有最后写覆盖。单文档原子性、唯一索引、读取一致性和故障耐久性是不同问题，仍需固定部署与write concern。[MongoDB官方原子性说明](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)

<a id="event-loop-and-go-init"></a>

## Python事件循环与Go初始化不是同一层机制

asyncio事件循环调度任务与回调、处理异步IO和子进程。协程在等待点让出执行；把阻塞文件读或CPU重循环直接塞进协程，仍可能拖住同一循环上的其他请求。需要线程/进程执行器或合适异步库时，显式限制并发、结果队列和取消语义，不能以“用了async”证明并行或响应及时。以实际Python版本选择API，应用代码一般优先高层入口。[Python事件循环文档](https://docs.python.org/3/library/asyncio-eventloop.html)

Go包初始化则在程序启动阶段：依赖包先初始化，包级变量按依赖规则初始化，再运行init函数。不能让init隐藏网络请求、不可恢复副作用或无限等待，导致入口尚未开始就失败。导出标识符由名称首字母是否大写判断，与init顺序无关。slice/map拷贝需要确认是否共享底层对象，不等于语言自带任意深拷贝。[Go语言规范](https://go.dev/ref/spec#Package_initialization)

<a id="migration-dual-write"></a>

## 在线表迁移：主记录、增量和切换需要同一时间线

先列不变量与回退边界：哪些数据为真、写入是否能暂停、允许多久陈旧、切换后能否回旧表。原创迁移方案可分为：新schema兼容发布；历史backfill带水位与幂等键；持续增量投影；按业务键/版本对账；灰度切读；确认所有消费者与定时任务切换；观察后再退旧链。

直接双写失败时，一个库成功不代表另一个成功。同库若业务允许可用同一事务；跨库可用事务outbox加幂等投影，传播版本和删除tombstone，防较老backfill覆盖新修改。变更水位、快照边界与增量消费位置要能对上，否则看似“全量对账通过”后仍会丢窗口内写入。

Binlog/CDC、读回填和双写各有边界：CDC需要处理schema变化、迟到、重放与保留期；读回填碰不到长期不访问数据；双写增加失败窗口。按更新延迟、回放能力、schema 变化与维护成本选择同步方式。定时发奖这类副作用消费者应先核对读取口径和幂等记录，避免灰度期间双重处理。

同库 `RENAME TABLE` 可在满足官方锁与表约束的情况下完成名字切换，不自动完成schema语义转换、历史数据校验、应用缓存和跨库原子写。[MySQL 8.4官方说明](https://dev.mysql.com/doc/refman/8.4/en/rename-table.html)。切换前测试写入进行中、删除/重建同ID、投影重试、定时任务竞争和回滚；未执行这批故障测试不能把迁移讲成零停机保证。

<a id="shared-token-refresh"></a>

## 多实例Token刷新：锁只解决一部分竞争

合成场景：多个实例共享第三方access token，新token签发后旧token立即失效。服务端将token密文、过期时间和单调版本放在受控共享存储；临近过期先协调一个刷新者，其余等待短时间或继续按服务契约使用当前值。获得锁后再检查是否已有新版本，避免排队者依次刷新。提交新token时比较刷新租约/版本，拒绝旧执行者迟到覆盖。

仅加分布式锁仍有“签发成功、存储失败”的结果未知窗口。若第三方可查询当前状态或支持幂等刷新，先对账；否则需明确失败升级和重新登录流程，不能盲目连刷。业务请求遇到认证失败，可读取当前版本，仅在版本确实更新且该业务请求允许安全重试时重试一次；转账等副作用不能因为401或网络错误就随意重放。

不要日志记录token正文，不把Redis复制延迟和客户端缓存当作瞬时全局可见；需要实测延迟、失效码与服务方刷新规则。Token具体创建、配置或泄漏处理须走对应授权与安全流程，本章不提供真实凭据操作。[分布式锁边界](34-distributed-systems-details.md#fb54) · [鉴权与Secret](36-interview-followup-topics.md#fb85)

<a id="password-migration"></a>

## 旧密码哈希迁移：沉睡账户使“无感全量按期完成”不成立

教学题指定旧系统无盐MD5并要求迁到bcrypt。不能由旧哈希还原原密码再批量直接计算新密码哈希。用户下一次成功登录时可以用刚验证的输入按新算法生成盐与哈希，原子替换算法版本；并发更改密码须比较旧版本，避免迟到迁移覆盖新密码。全过程不把明文写日志或长期保存。

一直不登录的账户无法靠此完成指定期限内的全量迁移，需要按安全政策重置/失效等措施；因此“不打扰任何用户”与“所有账户一年内直接迁完”可能冲突，应该指出约束而非承诺。bcrypt有输入字节限制和工作因子等实施条件；新系统选型还应考虑当前推荐的内存困难算法。具体参数按组织规范、库版本与性能测试决定。[OWASP密码存储与旧哈希升级](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

<a id="sandbox-runtime-boundary"></a>

## 容器runtime、gVisor与业务权限分开检查

Docker客户端把请求交给daemon，runtime参与创建容器进程。常见容器共享宿主机内核；gVisor通过用户态内核Sentry实现不同系统调用边界，`runsc`是其OCI runtime。这个Sentry不是日志产品sentry.io，换runtime也不等于应用获得了用户授权。

实际威胁模型还需检查宿主机挂载、Docker socket、网络、运行用户、CPU/内存/PID限制、文件路径与产物校验。镜像默认用户要读其配置，不能说所有容器默认非root或全部root；非root本身也不是充分隔离。不同模型产品的专有沙箱细节没有在本次核验，不能由Docker/gVisor机制推断其具体实现。[gVisor官方架构](https://gvisor.dev/docs/architecture_guide/intro/) · 部分章节暂未发布
