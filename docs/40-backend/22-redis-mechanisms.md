### FJ37 Redis 逻辑类型与内部编码有什么区别，如何映射业务

**优先级：P0。**

**知识点详解**：逻辑类型定义可做的操作；内部编码是服务端为同样语义选择的存储方式。String 是字节序列，可存序列化值或整数计数；Hash 适合按字段更新；List 保存有顺序的元素；Set 提供去重/成员判断；Sorted Set 为唯一成员维护分数排序；Stream 是带 ID 的追加日志，可结合消费组追踪处理。Bitmap 基于字符串位操作；HyperLogLog 做基数近似估算，不能列出原成员；Geo 支持距离/范围位置查询。这些不应只背类型名，还要说明是否允许误差、如何分页、如何更新。

常见编码演进：String 有 int、embstr、raw 等；小 Hash/Sorted Set 在 Redis 7.0+ 使用 listpack，老版本常见 ziplist；较大 Hash 使用哈希表，较大有序集合通常结合跳表与字典；Set 可以用 intset、哈希表，7.2+ 小集合还可用 listpack。List 可使用紧凑结构与 quicklist，quicklist 是串接紧凑节点的结构，不是“ziplist一大就变成普通单元素链表”。Streams 常使用 radix tree 配合 listpack。阈值、编码转换和对象布局都应按版本与实际 `OBJECT ENCODING` 核查。

**具体例子**（未运行）：验证码用带 TTL 的 String；每天登录标记可按日期建 bitmap，但用户 ID 特别稀疏时需重评空间；积分榜用 ZSET，同时定义同分排序；只需近似独立访客数才考虑 HLL；轻量任务用 Stream 时还要处理 pending、确认、重复、裁剪及持久化。Redis 5 引入 Streams，后续命令能力持续增加，不能把当前文档中所有命令都宣称5.0已有。

**面试答法**：先按访问和正确性需求选逻辑类型，再解释服务端编码随规模/版本调整；编码转换不改变业务类型，却影响性能与内存。

**追问**：把 JSON String 改 Hash 一定省内存吗？依字段数、大小、编码及键开销而定，需测量。List 当可靠队列还缺什么？确认、重试、幂等和故障恢复语义。

**误区**：Redis只有五种能力；所有小结构都永远ziplist；HLL可精确返回所有去重成员。

### FJ38 Redis 为什么快，单线程与 I/O 多路复用怎样准确表述

**优先级：P0。**

**知识点详解**：常见低延迟来自内存工作集、紧凑结构、较短命令路径及事件驱动网络处理。I/O 多路复用让一个事件循环监听很多连接的就绪事件，随后在非阻塞 socket 上读写；没有数据的连接无需各占一个专门等待线程。就绪并不代表应用请求完整，协议解析及部分写仍需状态管理。

Redis 6/7 常规命令执行主要在主线程串行处理，避免普通命令之间的细粒度数据锁竞争；但整个进程还有后台释放、持久化协作等线程，快照/重写还可能有子进程。Redis 6 引入可配置 I/O 线程；7.2 配置区分网络写出与可选的读取/协议解析线程化，命令本体并不会因此普遍多线程并行。Redis 8 等后续实现继续演进，回答时应锁定版本，不能把6.0流程图当永恒架构。

单命令原子执行也不等于多个客户端命令组合原子。大集合遍历、排序、复杂 Lua、巨量响应和 CPU 密集操作仍会让其他请求等待；增加 I/O 线程无法直接解决主执行路径上的昂贵运算。网络 RTT、客户端排队和持久化 fork 也可能主导尾延迟。

**具体例子**：一次读取百万成员的集合可能让小 GET 同时变慢。排查慢日志、延迟事件、单键大小、CPU 与网络后，将业务读取分页/限量；只把 io-threads 从1改为8未必有收益，还可能增加协调成本。配置变更需在真实负载下测量，本章未进行该实验。

**面试答法**：Redis常规命令串行与整体只有一个线程不同；多路复用减少连接等待成本，I/O线程提升网络路径能力，复杂命令仍需控制工作量。

**追问**：pipeline 能减少什么？主要减少往返和批次开销，不能自动提供多命令事务原子性。多路复用是完成通知吗？通常是就绪通知。

**误区**：在内存所以所有命令O(1)；Redis整个进程永远单线程；开I/O线程就能并行执行任意Lua脚本。

### FJ39 RDB、AOF、复制与备份分别怎样帮助故障恢复

**优先级：P0。**

**知识点详解**：RDB 将某一时点的数据按持久化格式编码为快照，适合备份和重启加载；它不是把进程内存指针布局原封不动保存，再一次复制回内存。快照间隔越长，最近变更损失窗口可能越大。后台生成常用 fork，fork暂停与后续写时复制可能增加延迟和内存，不能只预算平时 used_memory。

AOF 追加可重放的写操作，always/everysec/no 等刷盘选择在延迟与故障风险间取舍；everysec 不是任何系统故障下严格最多丢一秒的数学承诺。重写根据当前数据生成较紧凑恢复表示，不是简单截断旧文件。现代 AOF 可使用 RDB 前导的混合格式，Redis 7.0+ 采用多部分 AOF 管理，含基础文件、增量文件及清单；备份恢复必须按目标版本的一致文件集合处理。

复制让另一节点持有数据，自动故障转移恢复服务；持久化让节点重启后重建状态；备份提供可回到的历史副本。错误删除会同步到副本，也可能写进持久化文件，所以“有主从＋AOF”不能代替独立备份与恢复演练。RDB/AOF谁恢复快取决于数据量、日志压缩程度、硬件及格式，不应给无条件倍率。

**具体例子**（故障演练设计，未运行）：记录可接受RPO/RTO，在隔离环境从备份恢复，核对关键键数与业务校验，再验证恢复耗时。恢复缓存后逐步放量，避免冷启动让所有请求同时回源。若缓存可重建，可选与权威业务状态不同的持久化策略。

**面试答法**：快照、追加日志、副本、备份各有职责；按允许丢失和恢复时间设计，并测试恢复，不能无条件承诺零丢失。

**追问**：同时配置RDB/AOF就没有文件管理风险吗？仍需看实际恢复优先规则和一致备份流程。fork后实际内存会翻倍吗？取决于写入与页面共享，不是固定值。

**误区**：RDB是内存镜像直接拷回；AOF永远只有一个纯命令文本文件；复制可以找回任何误删。

### FJ40 键到期一定马上释放内存吗，淘汰策略有哪些

**优先级：P0。**

**知识点详解**：TTL说明键逻辑上什么时候过期。Redis结合访问时检查的被动过期和后台采样的主动过期，清理无人再次访问的到期键；不是每键分配独立定时器，也不应把“每100ms扫描所有键”当完整机制。已经逻辑过期与内存何时实际回收不完全相同。

淘汰由内存压力触发，与过期独立。在经典Redis6/7的maxmemory策略中：
- allkeys-lru / allkeys-lfu / allkeys-random：从全部键中按近期、频率或随机策略选。
- volatile-lru / volatile-lfu / volatile-random：只从设置了过期的候选键选；volatile-ttl偏向更早到期键。
- noeviction：不主动淘汰，需要额外内存的写入可能失败，读取等仍按命令规则处理。

LRU/LFU含采样与近似机制，不能当精确全局访问历史排序。volatile策略没有适合候选时同样可能拒绝写；没有TTL的键也可能被allkeys策略淘汰。因此“永不过期缓存”仍可能消失，而且若无更新机制会无限陈旧。maxmemory也不等于进程RSS的绝对上限，碎片、复制/AOF缓冲等需另留预算。

**具体例子**：每个缓存键都设一天TTL，但工作集十分钟就超过内存预算；需要选择合适淘汰策略与回源限流。若同实例混放不可丢会话/配额与可丢缓存，策略无法理解业务重要性，应考虑隔离和持久化边界。

**面试答法**：TTL管新鲜度，淘汰管内存压力；主动与被动过期协作，LRU/LFU近似，候选范围及拒写结果必须讲清。

**追问**：TTL越长命中率一定越好且无代价吗？工作集与陈旧风险会上升。LFU统计是从系统诞生累计永不衰减吗？实现有计数近似和衰减。

**误区**：有TTL就不会OOM；volatile没有候选会自动变allkeys；无过期时间就是永不丢失。

### FJ41 看门狗续租能保证分布式锁永远安全吗

**优先级：P0。**

**知识点详解**：单实例租约锁的最小逻辑见 [B29](03-redis-and-caching.md#b29)：原子SET NX加过期，唯一所有者标记，释放时原子比较再删除。续租也必须在同一个原子操作中确认“仍是我的标记”再延长，不能先GET后EXPIRE，否则过期换主后可能替别人改租约。

Redisson的watchdog会在适用获取方式下维持租约，默认超时可由lockWatchdogTimeout调整；显式leaseTime表示按给定时长自动释放，不能假定任何重载都会无限自动续期。具体调度间隔、批处理和获取API要查所用Redisson版本，不能只背“固定30秒锁、固定10秒续期”。

续租只能缓解任务比预计更长，无法阻止进程长暂停、网络分区或客户端失效导致租约到期。A过期后B获锁，A恢复仍可能执行旧写；随机解锁标记避免误删，却不能阻止资源接收旧写。关键资源可以要求单调递增fencing token，并在资源端原子拒绝旧序号；若资源端不验证，token只是日志字段。业务幂等、数据库约束和锁的故障模型仍须独立设计。

**具体例子**（伪代码，未运行）：续期脚本只在 `GET(lockKey)==token` 时执行 `PEXPIRE(lockKey,ttl)`；若不匹配或请求结果未知，任务应停止依赖锁的后续写，并按业务协议恢复。不要“续租失败只记日志，照常写库存”。

**面试答法**：看门狗延长有效租期，不提供永久独占证明；要原子校验续期、处理失锁，并通过资源端条件更新/fencing保护关键写入。

**追问**：资源不可改造时怎么办？重新评估该锁是否足以承担正确性，优先利用已有数据库事务/约束。异步主从故障切换会怎样？锁写可能未复制，见B30。

**误区**：续期线程活着就一定续成功；SETNX单独构成可靠锁；随机UUID就是单调fencing token。

### FJ42 两级缓存如何失效，删缓存失败和旧读回填为什么是两类问题

**优先级：P0。**

**知识点详解**：本地缓存→Redis→数据库能减少网络访问，但每个应用实例多了一份独立状态。写库后只删Redis，其他实例的本地值仍可能旧。应定义新鲜度目标、版本、失效传播、断连恢复和TTL；要求强读后写的关键操作可直接读权威库，不应把最终一致误称强一致。

有两条不同故障时序：
1. 数据库提交成功，DEL失败，旧Redis值持续存在。需要可靠记录失效意图，幂等重试并监控积压。
2. A读到旧库值后暂停；B提交新值并DEL成功；A恢复把旧值回填。此时DEL本身没有失败，单纯“失败再试”不能证明消除此竞态，参见 [B26](03-redis-and-caching.md#b26)。

数据库提交与发送消息分两步同样有崩溃缺口。可把业务写与outbox事件放同库事务，或用可靠CDC读取提交变更；投递/消费仍要处理重复、乱序、检查点、重试退避与告警。版本化缓存/失效标记应防止旧读覆盖新状态，但必须把比较和写入原子化，并说明版本来源及墓碑保留，否则只是换一种竞态。

广播也有语义差异：Redis Pub/Sub不持久化，断连会丢消息；使用它作快速失效提示时，需要断连清空本地缓存、短TTL或版本验证兜底。Kafka同一消费组把分区分给成员，并不会让每个实例都收到每条失效；广播到所有本地缓存需要明确独立订阅模型或统一失效服务，并考虑动态实例生命周期。Redis客户端缓存tracking也是另一种方案，客户端必须正确处理失效和连接中断。

延迟双删尝试在第二次删除时清理旧回填，但固定延迟无法覆盖无界暂停和复制延迟，故是特定假设下的减小窗口措施。无限重试也不是可靠方案：要有持久队列、幂等、指数退避、失败可见性和人工修复入口。

**具体例子**（设计示例，未运行）：商品更新提交时记录outbox(id,key,version)；投递者可重复发事件，消费者按版本幂等失效。应用订阅断开后立即使本地缓存不再可信，重连完成同步/清空后再启用。业务能否容忍旧值需写进接口约定，不能只写“最终会同步”。

**面试答法**：先分DEL失败与旧读回填，再设计数据库提交到事件投递的可靠链路；两级缓存还需每节点失效和断连恢复，双删/消息都不自动构成强一致。

**追问**：TTL能保证写入后30秒必定全新吗？还受旧值回填时间、读副本延迟及刷新方式影响。消息重复会怎样？幂等DEL容易，但带值更新需要版本比较。

**误区**：Pub/Sub一定可靠送达；Kafka同消费组自动广播每实例；数据库提交后发送MQ就无原子性缺口；DEL返回成功证明没有旧值再出现。

时序与组合方案为原创分析。

### FJ43 大键与热键怎样识别，为什么“超过10KB”不是统一标准

**优先级：P0。**

**知识点详解**：大键强调单个值/集合的体积、元素数量及处理成本；热键强调访问过度集中。它们可以独立存在：一个很小的计数键也能承受极高QPS，一个几乎不读的大集合仍可能在删除/迁移时造成延迟。10KB只能是某业务阈值，不能当Redis官方统一界线。

诊断结合 MEMORY USAGE、字符串长度/集合基数、慢日志、延迟监控、网络流量与热点采样。全量诊断本身会占资源，SCAN/HSCAN等要分批限速，COUNT是提示，迭代可能重复且不是一致快照。大键删除可以评估UNLINK把实际回收异步化，但摘除键、后台回收、复制传播与业务影响仍有成本；不能在未核对作用域时直接删生产键。

大键治理先改访问模式：不一次取全量、给集合规模上限、分页、过期与归档，必要时按业务维度拆键。热读可考虑本地缓存/请求合并，热写考虑聚合/分片计数，但读结果要归并，精确性和延迟也会变化。String改Hash不保证节省内存；对一个原子库存键任意随机拆分会改变业务正确性。

**具体例子**（未运行）：排行榜只展示前100，避免每次拉全量百万成员；若榜单本身过大，按赛季/区域拆分，并明确跨区域总榜的归并方式。热商品详情本地短TTL缓存可以降低Redis压力，但新增两级一致性问题需按FJ42处理。

**面试答法**：大与热是体积和访问集中度两个维度，用指标确定阈值；治理要同时控制单次工作量、数据生命周期和热点语义。

**追问**：UNLINK后内存立即下降吗？实际释放异步，观察周期和分配器/RSS行为不同。SCAN返回空批次就结束吗？游标回到0才是该次遍历结束。

**误区**：10KB以上一律错误；Hash天然比String省；拆键不影响原子性；慢日志能完整解释网络和客户端等待。

### FJ44 Redis 全量复制、部分重同步与复制积压缓冲怎样配合

**优先级：P1。**

**知识点详解**：全量复制先传某个状态的快照，再追上快照期间及之后的变更流；部分重同步则从副本已处理的偏移继续发送遗漏片段，避免每次短暂断线都传整库。现代PSYNC协议使用复制ID和偏移来标识同一数据历史的位置，不能用普通进程runid概括全部语义。

主节点的复制backlog保存一定历史流，副本重连携带复制ID与偏移；若历史匹配且所需字节仍在backlog中，才有部分重同步机会。缓冲容量不足或历史不匹配会要求全量。提升副本后保留部分旧历史识别信息，可帮助其他副本继续同步，具体协议仍按版本说明。

有盘全量同步可由后台快照文件传输；无盘复制允许子进程直接把RDB流发给副本，不意味着没有快照编码或内存成本。复制异步，副本读可能旧，故障切换可能丢最近写；WAIT等待复制确认能降低部分风险，却不能把部署直接变成强一致、自动持久化无丢失系统。

**具体例子**（容量估算，未测量）：若复制流平均每秒5MB、希望常见30秒断连仍可增量恢复，150MB只是基于均值的backlog起点，还要留突发、重连与调度余量。应从实际复制字节速率估算，不能用客户端请求数量直接换算。

**面试答法**：全量是快照加后续流，部分同步靠复制历史ID、偏移和保留窗口；backlog提高短断连恢复效率，不改变异步复制的一致性边界。

**追问**：复制正常能代替备份吗？错误写会复制。无盘复制一定更快吗？取决于磁盘、网络、数据和副本数量。

**误区**：副本每次重连必全量；只比较offset不比较历史ID；WAIT成功就保证任何故障不丢写。

<a id="fj45"></a>
### FJ45 Sentinel、Cluster 和持久化如何组合，怎样说明高可用边界

**优先级：P0。**

**知识点详解**：Sentinel负责监控主从、故障确认、协调提升副本和让客户端发现新主，不负责把单个数据集自动分片。某个哨兵主观判断不可达只是SDOWN；达到配置quorum等条件才可确认ODOWN；真正故障转移还需获得多数哨兵授权，若quorum高于多数则还需满足更高数量。仅两个哨兵或同一故障域部署容易失去授权能力；客户端也必须支持重新发现和重连。

Redis Cluster把16384个槽分配到主节点，用键哈希映射到槽；hash tag可让相关键落同槽，支持需要同槽的多键操作，但也可能聚集热点。MOVED表示路由应转向新的槽归属，客户端可更新缓存；迁移期ASK只要求当前请求临时到目标并先发ASKING，不应立即把全部后续路由永久切过去。

Cluster的副本承担故障提升，但“每主一个副本”不是充分可用性保证：选举需要可达的主节点多数、合适副本资格/数据新鲜度，以及槽覆盖与相关配置；网络分区、多个同组节点同时故障都会改变结果。默认要求完整槽覆盖的配置下，未覆盖槽可影响集群服务；允许部分覆盖也不等于丢失槽的数据可读。不能只画六个节点就声称可容忍任意三台故障。

高可用、持久化和备份应组合：复制提供替代节点，Sentinel/Cluster自动切换，RDB/AOF帮助重启恢复，独立备份应对误操作。故障检测、选举、客户端重试都需要时间，异步复制还可能丢写，所以高可用不是零停顿、零损失。

**具体例子**（时序示例，未运行）：三个主各一副本，若所有副本与各自主放同一台物理机，丢那台机就同时失去该槽数据的主副本。若多数主节点彼此隔离，剩余副本即使有数据也未必能获得提升授权。部署应按故障域分散，并测试客户端在MOVED/ASK和切换中的行为。

**面试答法**：Sentinel做单数据集故障转移，Cluster再做槽分片；可用性取决于多数、槽覆盖、副本和客户端，持久化另管恢复，不能把副本数量当万能保证。

**追问**：hash tag越多越好？只用于确需同槽的键，过度使用会集中负载。切换后重试写操作安全吗？仍需业务幂等及未知结果处理。

**误区**：quorum就等于选举多数；有一个副本就任何故障都可用；迁移只有MOVED；高可用绝不丢写。
