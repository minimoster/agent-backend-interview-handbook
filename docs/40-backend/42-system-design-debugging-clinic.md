# 系统设计与排障诊所：从现象到可证伪假设

[后端目录](README.md) · [主学习路线](../00-guide/expanded-map-and-study-plan.md#topic-map) · [原有系统设计](05-system-design-and-reliability.md)

本章把网络、数据库、缓存、队列与 Linux 基础组织成完整演练，要求每一步说明证据、风险和回退。负载与指标为教学设定；数据库迁移、压测、容器发布及真实事故操作尚未执行。

<a id="design-latency-queue"></a>
## 1. QPS没涨，P99从200ms变成2s，先查什么

**先澄清：** 哪个接口、哪个租户/实例、哪个时间窗？P99来自客户端还是网关？失败请求是否计入？最近是否发布、变更连接池或扩大返回体？把一张全局图拆成这些维度，可能就发现只是一条热点路由。

**证据分层：** 接入等待→应用排队→借连接→SQL/缓存→外部调用→序列化→写出。每段看请求数、等待时长、在途数与错误。trace定位个别慢请求的依赖，指标判断总体变化；采样trace没抓到，不等于没有慢请求。

**原创反例：** CPU不高，DB连接全占满，线程大多在借连接。先扩大线程池只会增加等待者；数据库如果已经到容量边界，扩大连接池可能让锁竞争更糟。先问连接何时获取、是否在事务中等远端、是否及时归还，结合[Java诊所](../20-java/16-executor-failure-followups.md#java-queue-admission)。

**容量直觉：** 对满足相应稳定观察条件的平均量，可用L≈λW理解在途量；λ是相同边界的吞吐率，W是平均逗留时间。它不是“QPS乘P99就得到线程池最优数”的公式。并发、吞吐与延迟不能脱离分母和边界比较。尾部恶化时更要分成功/失败和排队/执行。

**继续追问：各实例P99平均可以当整体P99吗？** 不可以直接这样聚合。采用可聚合的原始分布或合适直方图桶，再计算整体分位值；直方图自身有桶误差。

**收束方案：** 先保护已有请求和稀缺资源，限制接纳与排队，按错误语义降级；建立小范围对照验证并保留回滚。不能因一次重启后恢复就认定根因是GC。

<a id="design-sql-evidence"></a>
## 2. 索引没失效，SQL为什么还慢

**起手问：** EXPLAIN显示用到了索引，但查询仍要几秒，怎么办？

用索引只是执行路径的一部分。核查实际扫描/返回数量、数据分布、回表、排序和临时结果、锁等待、磁盘/缓存以及参数。返回百万行且网络慢，换一个索引不能使响应体凭空消失。对深分页，稳定排序和keyset可减少跳过成本，但API语义随之改变；要给排序键附唯一tie-breaker，不能只按时间戳分页。

**追问：读少但慢，是不是锁？** 看等待事务和阻塞事务，找它们实际SQL、持锁时间和业务路径；不要把所有WAITING都当死锁。MySQL8.4的`performance_schema.data_lock_waits`用于关联请求/阻塞锁，权限与采样视角要核对。真正死锁、普通锁等待、连接获取等待应分别处理。

**教学只读查询，未执行：**

```sql
SELECT REQUESTING_ENGINE_TRANSACTION_ID,
       BLOCKING_ENGINE_TRANSACTION_ID
FROM performance_schema.data_lock_waits;
```

查询得到阻塞关系后，还要关联事务和语句上下文。不要据一张瞬时表直接KILL最大事务，也不要把EXPLAIN ANALYZE当完全无影响的静态展示：它会实际执行相应查询，需在授权环境按风险使用。

**验收：** 明确假设“等待锁占主导”与“扫描过多占主导”各需要什么证据，提出只改变一个因素的复验设计，保留原SQL语义与边界样本。

<a id="design-migration-watermark"></a>
## 3. 在线迁移十亿行，为什么全量加增量仍会覆盖新数据

**先定合同：** 要迁移哪些表/字段，允许多大陈旧窗口？写入是否仍由旧库权威接纳？排序或版本由谁产生？失败恢复是继续还是重建？“零停机”必须进一步解释每阶段允许的读写和错误。

**原创竞态：** 全量扫描读到v5；增量流已把目标更新到v6；全量批次迟到又写v5。仅有两个同步通道不足以保证顺序。给每条数据建立权威版本/位置，目标使用条件写，或采用经过论证的快照与日志水位协议；删除必须有墓碑/事件，不只同步现存行。

**一条可讨论的步骤链：**
1. 盘点schema、主键、字符集、时区、约束、权限与敏感列，设计向后兼容目标
2. 建立变更捕获与可恢复水位；解释快照边界如何与增量对应
3. 分批回填，限制资源占用并保存进度，迟到写不能压过新版
4. 校验按范围/租户的数量、摘要和关键业务不变量，而非只看总行数
5. 小比例影子读取和对比；对差异保留可追踪版本
6. 灰度切读，观察错误、尾延迟、权限与结果差异
7. 切换写权威前定义旧写的拒绝或转发，不让两库任意写冲突
8. 保留回退窗口；删旧列/旧库是最后一步，回退前说明新写如何保全

这些是设计问题，不能当成已完成生产迁移的步骤保证。删除、schema变更、重复事件、日志保留不足、snapshot中断、切换期间旧请求迟到都应分别演练。

**继续追问：主从延迟越来越大怎么办？** 区分接收日志与应用日志的进度，按worker看错误、长事务与处理瓶颈，结合业务读陈旧影响；Seconds_Behind_Source之类单值不代表每个关键实体的最新程度。

**回答边界：** 双写不能自动原子化；全量+CDC不能自动解决版本覆盖；“回滚应用代码”不能自动把新schema/新数据恢复为旧状态。[本地提交与重放](41-storage-recovery-followups.md)

<a id="design-job-api"></a>
## 4. 设计一个文档导出/Agent任务接口，怎样定义成功

以原创文档任务为例，先分接纳、执行、产物验证和下载授权四阶段。接纳返回task_id与查询入口，不等于任务已完成。状态可以是queued/running/succeeded/failed/cancel_requested/canceled等应用自己的合同；不能把它们假称为某个协议的通用标准。

**最小数据模型：** tenant_id、task_id、operation_key、参数摘要、状态/版本、owner_epoch、deadline、产物摘要/大小、错误分类。按(tenant_id,operation_key)处理重复命令；参数冲突拒绝；下载再核权限。临时文件名包含任务身份，校验后原子发布可见产物；失败清理不得删除另一个任务的文件。

**追问：worker租约超时，被新worker接管，旧worker回来？** 租约只协调接纳权，提交产物还要核对当前owner_epoch或版本；产物状态与摘要绑定，旧worker不能覆盖新产物。外部对象存储的写入、数据库状态和下载可见性属于多个边界，需恢复记录和垃圾回收策略。

**追问：取消按钮点完，为何结果仍出现？** 定义“请求取消”与“取消成功”。如果提交已先成立，就按合同报告已完成；若取消已经被权威确认，旧worker提交必须被相应原子条件拒绝。不能靠本地UI隐藏结果假装撤回副作用。[A2A协议边界](../10-agent/32-a2a-task-lifecycle-lab.md)讲另一套具体协议，注意不要混用状态名称。

**监控按阶段：** 排队年龄、最老在途、取消完成延迟、未知结果数量、重放冲突、未发布临时产物、下载拒绝。吞吐和成功率按固定时间窗与明确分母记录。

<a id="design-incident-runbook"></a>
## 5. 未遇过的线上告警，怎么有条理地处理

先保护用户和证据，再定位根因：
- 判断影响范围、错误种类、是否持续扩大，关联最近变更
- 在授权范围用低风险只读观察确认队列、线程、连接、锁、日志水位与资源压力
- 将现象写成可证伪假设，说明下一条证据会支持或否定什么
- 优先可回退的小范围缓解，避免同时改池、SQL、GC和重试
- 复核业务不变量与用户路径，保留恢复/对账任务

**工具选择表：**
| 现象 | 下一类证据 | 不能直接下的结论 |
|---|---|---|
| Java请求等待 | 重复线程栈、池队列、连接获取耗时 | WAITING一定是死锁 |
| Go CPU高 | CPU profile、分配、业务输入差异 | 一张火焰图已经证明根因 |
| 内存高 | 存活堆、累计分配、RSS、容器限制 | heap下降RSS不降必然泄漏 |
| MQ积压 | 到达/完成速率、分区热点、错误和最老年龄 | 加消费者总能提高吞吐 |
| 数据不新 | 实体版本、水位、应用延迟、缓存floor | 服务返回200就一定最新 |

诊断接口需要受控访问；日志和dump可能包含敏感数据，采样也会有开销。真实重启、KILL、改配置、迁移与数据修复都要按相应授权和变更流程执行。这里提供演练思路，没有执行任何生产操作。
