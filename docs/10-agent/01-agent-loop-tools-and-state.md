### A01 什么是 Agent？与聊天机器人、Workflow 有什么区别？

**优先级：P0** 

**知识点详解** 
- 模型负责产生预测；Agent 是围绕目标调用模型、执行工具、读取结果、更新状态的整个系统。能聊天不自动代表能采取行动。
- Workflow 的主路径由代码规定；Agent 允许模型动态决定部分步骤。实际系统通常混合使用，两者不是互斥标签。
- 自主程度越高，路径、成本和错误越难预测。稳定的格式转换未必需要多轮 Agent，开放式研究才更可能需要动态探索。

**具体例子** ：固定“提取 PDF → 总结”可以做成工作流；发现论文证据不足后自行追加检索，更接近 Agent 行为。

**30 秒答题主线** ：我把 Agent 定义为模型驱动的、有状态的工具执行闭环。它与普通问答的区别在于能根据观察决定行动；与固定工作流的区别在于部分路径在运行时决定。我会先用最简单可验证的流程，再增加自治。

**追问** ：你项目中哪个决定由模型做？哪个决定必须由代码做？

#### 参考答案

模型可以提出下一步行动、候选参数和解释；权限、参数校验、预算、状态转换和真实副作用由可信代码执行。面试举例应指向实际代码路径，不能把建议架构说成自己的已实现功能。

**验收点：** 指出一个候选动作和执行器拒绝它的代码条件；没有实现时只作为设计说明。

**常见错误** ：把所有调用 LLM 的程序都称为 Agent；认为 Agent 越多越先进。

**来源** ：[AG-T01](../../sources/catalog.md#ag-t01)。

### A02 ReAct 如何工作？为什么不能只让模型一直“想”？

**优先级：P0** 

**知识点详解** 
- ReAct 的核心是把推理与外部行动交替起来：模型选择行动，执行环境返回观察，再据此继续。外部信息可以修正模型先前的假设。
- 工程实现不必解析一大段自然语言思维过程；可使用结构化 tool call，保存动作、参数、结果和简短决策说明。
- 当缺的是事实或执行结果时，重复生成文字不等于获得新证据。终止还需要成功条件、步数上限和预算约束。

**具体例子** ：用户问某仓库为何测试失败，先读错误日志，再读对应函数，修改后运行测试；“猜测已经修复”不等于测试通过。

**30 秒答题主线** ：ReAct 是行动和观察反馈驱动的迭代模式。每轮根据当前状态决定工具，真实执行后把结果回传，再继续或结束。实现重点是可靠的工具协议和停止条件，不是展示冗长思维文本。

**追问** ：工具没返回怎么办？模型连续调用同一个工具怎么办？

#### 参考答案

工具超时要记录“结果未知”或明确失败，再按工具的幂等合同决定查询、重试或终止。连续同一工具且状态/证据没有变化属于无进展信号；限制轮数、重复签名与总预算，不能只靠提示词叫模型停止。

**验收点：** 模拟工具超时与三次相同观察，断言状态不被误标成功，且达到无进展或预算界限后终止。

**常见错误** ：把生成的“我已经执行”当成工具结果；把 ReAct 拼成 React 前端框架。

**来源** ：[AG-T02](../../sources/catalog.md#ag-t02)。

### A03 一次 Function Calling 到底是谁执行函数？如何设计工具？

**优先级：P0** 

**知识点详解** 
- 应用先把工具名称、用途和参数定义给模型。模型输出调用请求，应用校验并实际执行，再用对应调用 ID 返回结果；模型本身没有直接执行你本地函数。
- 工具宜围绕明确业务能力设计，参数可解释、返回值有界，错误区分参数错误、未授权、暂时失败和业务失败。
- 有依赖的调用必须排序；相互独立且只读的调用可以并发。副作用操作还要单独做权限和幂等控制。

**具体例子** ：search_docs(query, limit) 返回文档 ID、摘要和来源；不返回整个数据库，也不开放任意 SQL 给模型。

**30 秒答题主线** ：模型负责提出调用，runtime 负责验证、执行和回传。我会让工具职责单一，限制参数和输出体积，按 call ID 关联结果，并把可重试错误和不可重试错误分开处理。

**追问** ：工具名不存在如何处理？多个调用的结果怎样一一对应？

#### 参考答案

未知工具名不得猜测执行，返回可处理的结构化错误，并保留原调用 ID。每个工具结果关联对应调用 ID；并行结果的到达顺序不是调用身份。

**验收点：** 倒序返回两个调用结果，并加入未知工具名；结果仍绑定原ID，未知调用没有真实副作用。

**常见错误** ：把 Function Calling 说成模型直接连数据库；所有异常一律重试。

**来源** ：[AG-T03](../../sources/catalog.md#ag-t03)、[AG-T44](../../sources/catalog.md#ag-t44)。

### A04 JSON Schema 能解决什么？为什么解析成功还不安全？

**优先级：P0** 

**知识点详解** 
- JSON 解析只判断语法；Schema 再限制类型、字段、必填项、枚举和范围。例如 properties 列出字段，并不自动让字段必填，required 才承担这个职责。
- Schema 通过仍不等于业务有效：某个 user_id 可以是合法整数，却不属于当前登录者。授权和资源存在性必须在服务端检查。
- 处理链可分成：解析 → 结构校验 → 业务校验 → 授权 → 执行。错误反馈提供字段和原因，修复次数有上限。

**具体例子** ：limit 必须是 1–20 的整数；模型给出 100000 时，在查库之前拒绝，而不是执行完再裁剪。

**30 秒答题主线** ：我会用 Schema 缩小模型输出空间，再用服务端校验守住边界。结构正确、业务正确和有权限是三件不同的事，任何一层失败都不应进入有副作用的执行。

**追问** ：缺失与 null 有何区别？未知字段怎样处理？

#### 参考答案

缺失表示字段没有提供，null 表示提供了显式空值；required 只要求字段存在，是否允许 null 由类型规则决定。additionalProperties 默认允许额外字段；要拒绝未知字段必须显式约束，再独立校验权限与业务语义。[JSON Schema 对象参考](https://json-schema.org/understanding-json-schema/reference/object)

**验收点：** 分别输入缺字段、null、额外字段和合法类型但越权参数，检查四种验证层的结果。

**常见错误** ：认为“返回了 JSON”就可靠；把租户 ID 完全交给模型选择。

**来源** ：[AG-T04](../../sources/catalog.md#ag-t04)。

### A05 Agent 的 state 应保存什么？为什么不能只存聊天记录？

**优先级：P0** 

**知识点详解** 
- 聊天记录面向模型理解，运行状态面向程序控制。后者至少要能表达任务、当前节点、已完成结果、剩余预算、错误和取消状态。
- 节点读取状态并输出变化，边决定下一节点；并行节点写同一字段时，要明确覆盖、追加还是按 ID 合并，避免相互覆盖。
- 恢复所需数据应可序列化；数据库连接、客户端对象等运行时资源不能简单当作持久状态保存。

**具体例子** ：两个检索子任务分别返回证据列表，应按文档 ID 合并；若都直接覆盖 evidence，较早结果会丢失。

**30 秒答题主线** ：我把对话消息和执行状态分开。状态保存任务进度与可恢复信息，节点只更新自己负责的字段，并定义并发合并规则。这样才能做取消、重试、恢复和问题定位。

**追问** ：恢复时哪些字段可重建？追加 reducer 如何清空？

#### 参考答案

可从可信配置重建的显示字段和缓存不必成为恢复真相；任务身份、已执行副作用、必要输入版本与状态版本不能随意丢弃。追加 reducer 的“清空”不是自然追加空列表，应按所用框架采用显式删除/替换操作，并测试恢复后是否重复追加。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)

**验收点：** 保存、重启、恢复并重放一次结果；状态没有重复追加，已完成副作用不会因缓存缺失而重做。

**常见错误** ：把一个全局 map 当所有用户状态；认为有聊天历史就能安全恢复任务。

**来源** ：[AG-T05](../../sources/catalog.md#ag-t05)。

### A06 ReAct 与 Plan–Execute 如何取舍？怎么防止无限循环？

**优先级：P1** 

**知识点详解** 
- ReAct 逐步决策，适合下一步取决于新观察的任务；Plan–Execute 先分解再执行，更容易显式表达依赖和阶段进度，但计划也可能过时。
- 可把计划保存为有 ID 的任务节点，明确输入、输出和完成条件；新证据使原计划失效时再局部重规划。
- 停止条件由程序兜底：最大步骤、deadline、token/费用预算、连续无进展次数；不能只在提示词里写“不要死循环”。

**具体例子** ：比较三种数据库可先规划三条独立调研；其中一家资料不足时，仅重做那条分支，不从头再来。

**30 秒答题主线** ：我按任务的不确定性选模式。依赖明确时先计划，探索性强时逐步行动。无论选哪种，都要把停止条件、预算和失败状态写进 runtime，并允许根据证据调整计划。

**追问** ：什么算“无进展”？计划的环和不存在的依赖如何发现？

#### 参考答案

无进展可定义为相同工具参数、相同观察结果、没有新增证据或未完成节点数不下降。计划执行前检查 ID 唯一、依赖存在和拓扑可排序；存在环时拒绝计划或请求有界修复，而不是启动后等死。

**验收点：** 用重复ID、缺依赖和有向环三个计划，检查启动前拒绝，不留下无限等待节点。

**常见错误** ：认为先生成一份计划就一定更可靠；所有失败都重新规划全部任务。

**来源** ：[AG-T06](../../sources/catalog.md#ag-t06)；停止条件为工程设计建议。

### A07 多 Agent 真比单 Agent 好吗？怎么协作？

**优先级：P1** 

**知识点详解** 
- 多 Agent 的价值通常来自独立上下文、任务分工或并行探索，不是简单重复调用同一模型就得到多个独立专家。
- 任务交接要有目标、约束、输出格式、来源和完成标准；主控负责去重、处理冲突、汇总结果，不能只拼接子任务文本。
- 子任务强依赖、共享修改多时，协调开销可能超过收益。比较时应固定预算或至少同时报告成本，避免用更多 token 冒充架构收益。

**具体例子** ：分别研究性能、部署和许可可以并行；两名 Agent 同时修改同一函数容易冲突，应指定负责者。

**30 秒答题主线** ：我先判断任务能否独立拆分。多 Agent 可以隔离上下文和并行，但会增加调用、协调和重复工作成本。我会做单 Agent 基线，比较同等约束下的完成率、时间和费用。

**追问** ：子 Agent 结论矛盾谁裁决？一条分支超时，整个任务是否失败？

#### 参考答案

用证据和任务验收规则裁决矛盾，不能把多数票当事实证明。分支超时是否令全任务失败取决于它是否为必要依赖；可选分支可产生明确标注的部分结果，必要分支阻止依赖它的发布。

**验收点：** 让必要分支与可选分支分别失败；只有合同允许的部分结果可发布，冲突结论必须保留证据。

**常见错误** ：把多角色提示词等同于独立验证；直接套用厂商内部评测提升数作为自己的指标。

**来源** ：[AG-T07](../../sources/catalog.md#ag-t07)。

### A08 MCP、Function Calling、Tool 和 Skill 是一回事吗？

**优先级：P1** 

**知识点详解** 
- Tool 是可执行能力；Function Calling 是模型输出结构化调用意图的一种机制；MCP 规定应用如何连接服务、发现能力并交换请求结果。
- MCP 的 host 容纳客户端，客户端连接服务器；服务器暴露工具、资源等。使用 MCP 不自动获得安全授权或高质量参数。
- Skill 通常是特定产品里的任务说明、资料或脚本集合，并无跨所有系统统一的含义。先说明你项目中的定义，再比较它与工具的关系。

**具体例子** ：检索工具既可以是本地函数，也可以由 MCP 服务暴露；“如何完成文献调研”的说明可以组织这些工具的使用。

**30 秒答题主线** ：这几项处于不同层。工具提供能力，Function Calling 表达模型的调用请求，MCP解决应用和外部服务的标准化连接；Skill 更接近可复用任务方法，其执行仍依赖工具和 runtime。

**追问** ：MCP server 是否等于 Agent？工具发现后是否应默认允许调用？

#### 参考答案

MCP server 提供协议化能力，不必包含规划或自主循环，因此不等同 Agent。发现工具只是获得能力描述，不等于获得调用授权；运行时还应检查用户范围、租户、工具白名单和风险策略。[MCP 工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

**验收点：** 发现一个工具后，在没有该动作授权时请求执行；目录可见不会使调用获得权限。

**常见错误** ：说 MCP 是模型训练方法；把 Skill、Agent 的定义说成所有框架统一标准。

**来源** ：[AG-T08](../../sources/catalog.md#ag-t08)；Skill 对比为术语边界说明。
