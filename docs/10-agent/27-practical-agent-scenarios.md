# Agent场景题：目标、状态、证据与执行边界

[返回Agent目录](README.md) · [验证范围](../../coverage/AGENT_LABS_VALIDATION.md)

本章通过场景设计与测试任务练习目标、状态和执行边界。核查日期2026-10-10。实验尚未接入商家、用户账户、医学服务、相册或真实模型。

<a id="trace-latency"></a>
## 1. 怎样解释Trace、线上指标和端到端时延？

从入口到最终产物，分别记录理解、检索、模型、工具、状态合并和输出耗时。Trace/Span串起调用，任务身份串起多轮过程；避免混淆同一会话、同一任务和一次请求。查看第一处错误，再做固定工具结果或正确证据的干预验证，不能只凭最后一段文本归因。

监控请求量、错误/超时/解析失败、调用次数、step分布、分支失败、缓存命中、token/费用及P50/P95/P99。首个进度事件、首段有用文本和最终完成的时间分开。只读且独立分支可并行；下单必须等待最终预览及授权。技术流程见[Harness](18-harness-runtime-and-observability.md)，实验与抽样见[评测章节](25-agent-evaluation-and-routing.md)。

<a id="system-prompt"></a>
## 2. System Prompt与有界循环怎样设计？

固定部分描述职责、目标解释规则、外部数据边界、工具用法、输出契约和缺证据/停止策略。动态部分是本次目标、权威任务状态、必要历史和授权证据。不要把会变化的价格、身份或权限全写成固定Prompt。

每轮读取状态，模型提出候选行动，执行器检查结构、业务、权限和预算，获得真实结果，再更新状态并验证完成。成功、失败、待用户输入、取消、预算耗尽和结果未知都应有明确出口。不得把未经执行的工具建议记成已完成步骤。

**验收：** 连续相同观察没有新证据时停止；用户取消后未启动任务不再启动；迟到成功不能静默覆盖终态；模型只输出“完成”却没有产物时仍判未完成。

<a id="goal-conflict"></a>
## 3. 用户说“睡不着，想听恐怖故事”怎么办？

将明确诉求、推测的助眠目标和产品范围分开。恐怖故事本身不能无依据地称作非法请求，“睡不着”也不能自动推断脆弱状态或替用户决定内容。若产品专为助眠，可解释其范围，询问是否想改为轻松故事，并保留用户选择；一般故事助手可按请求提供符合内容规则的故事。

设计评测至少包含明确要恐怖内容、真正要求助眠、否定替代、产品范围外请求和需澄清的歧义。评估目标遵从、解释清楚和必要澄清，不奖励把所有请求一律改成系统猜测的目标。这里讨论意图治理，不提供医疗判断。

<a id="ordering-state-machine"></a>
## 4. 只有Function Calling的外卖流程，与完整Agent有何不同？

固定流程可用状态机：理解槽位→读取已获授权的默认资料→搜索商家/菜单→补齐规格→预览商品与总额→取得针对当前预览的明确批准→执行→查询真实订单终态。Function Calling只是模型表达结构化调用的方式，后端仍控制每个允许转换。

完整Agent可动态比较候选、处理缺货或解释方案，但不应获得更多付款权限。任务状态记录商家、商品、数量、规格、优惠/费用、地址、配送方式、价格与预览版本、批准范围、业务操作ID和终态。价格/商品/地址有实质变化时使旧批准失效。工具超时后先用操作ID核实，不能重新建一个订单。

**原创奶茶答案：** 解析门店/饮品/杯型/糖冰/数量等必要槽位，只在需要时追问；提供少量可修改候选。形成包含实际商品、最终金额和交付信息的预览；执行前核对批准和库存版本；保存订单身份，失败分成未执行、结果未知与已执行待确认。没有价格或批准时，停在预览/等待状态。

“随便”可授权系统推荐有限候选，不能解释为无限预算、任意地址或免确认支付。“不用了”要结合具体被问事项：取消规格追问不自动批准订单，取消下单则终止任务。退款/售后是新的动作契约，不能因为下单获批就任意取消、投诉或退款。

**验收：** 缺必要规格、候选价格变化、取消与完成竞态、重复请求、外部已成功但响应丢失。检查没有错误扣款、重复订单或虚假成功；本章没有实际交易测试。

配套[原创内存契约实验](../../examples/agent_scenario_contracts/README.md)已在Python 3.12.14运行12项测试，覆盖批准绑定、取消、已知结果复用、未知结果不盲重试、查询恢复及循环预算。它没有并发、持久化或真实支付，不能作为生产安全保证。

<a id="medical-qa"></a>
## 5. 医学问答Agent需要哪些组件？

先限定用途，例如受控医学资料检索与一般信息解释，而非自动诊断、处方或替代临床人员。知识摄取保留权威来源、版本和适用范围；记录解析保留单位与不确定性；检索与工具受身份和数据范围约束；上下文最小化；输出核对引用并说明证据不足；高风险用途需要专业审核、升级流程与独立验证。

把“检索→模型→验证”画出来不等于临床安全。评测需分离找错资料、单位/时序识别错误、误读证据和不适当行动；样本、数据处理、部署与责任边界由真实使用场景确定。[WHO健康AI治理指导](https://www.who.int/publications/i/item/9789240029200)强调伦理、人权与治理；本段是在此原则下的原创架构练习，不是医疗建议或监管合规认证。

<a id="photo-retrieval"></a>
## 6. 上万张照片怎样按自然语言检索？

建立去重、文件/拍摄时间等元数据与可回查原图身份；可结合OCR文本、用户标注与视觉表示。采用经过对齐的图文编码器，查询文字与图片在兼容空间比较。[CLIP论文](https://arxiv.org/abs/2103.00020)提供图文学习路线；任意ResNet输出与任意文本向量相乘，即使维度一致也没有共同语义保证。

检索先控制相册和用户权限，再用时间、地点等必要条件过滤，最后排序与去重。为具体人物或敏感信息建立索引需适用的授权和处理边界；位置缺失不能从图片内容编造。更新或删除照片时同步管理索引、缓存和派生文本。

标注正确图片集合，区分找全某次旅行与找到一张代表照片；测试语义改写、相似场景、时间限制、旋转/低清和无匹配查询。分别报告召回、排序、延迟与错误解释，不把图片搜索演示当Agent完成率。未执行模型索引或检索压测。

<a id="rich-stream"></a>
## 7. 文字流中怎样安全插入旅行卡片？

使用应用事件契约，例如text_delta、card、progress、error、done；每个事件有task_id、递增sequence、schema_version及payload。卡片输出受Schema和业务白名单约束，前端按固定组件渲染，不执行模型生成的脚本或任意HTML。价格、库存等数据使用可信查询结果和版本，不能只展示模型猜的值。

流式片段可能跨JSON边界，先完成事件解析再处理卡片；text_delta应按规定合并，card按稳定ID去重，done依据任务终态而非连接断开。断线用事件游标/快照恢复；过期游标、慢客户端、错误事件和取消都有策略。SSE的运输和业务确认基础见[A24–A26](04-streaming-and-reliable-execution.md#a24)。

**验收：** 重复事件、UTF-8分片、非法卡片字段、恶意URL、流中断、游标过期和旧任务事件。只有通过验证的payload进入组件，文案流也不能覆盖未验证的终态。

<a id="topic-continuity"></a>
## 8. 一个session里频繁换话题，怎样维持连贯？

维护活跃话题、实体及其关系、当前任务约束和跨话题稳定偏好。用户从一款游戏换到另一款时，近期原文帮助消解“它”，但未明确的实体仍需澄清；不要把前一款游戏的结论默认套到后一款。

按话题总结已验证事实、未知和未决任务，检索只取与本轮相关的历史，长期偏好按范围复用。当前明确更正优先用于当前任务，临时变更与全局更新分开。若用户单会话承担多个工作流，任务ID仍必须分开，不能只用session_id当唯一状态键。

历史轮数是实验变量，详见[原创窗口对照](25-agent-evaluation-and-routing.md#context-ablation)。评测包括跨实体指代、返回旧话题、否定条件、新旧偏好冲突、跨任务副作用和缺证据；测任务连续性而非仅测“回答像聊天”。
