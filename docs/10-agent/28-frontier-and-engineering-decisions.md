# 开放性问题：用条件、证据与实验作判断

[返回Agent目录](README.md)
本章练习依据条件、证据与实验作工程判断。模型能力、产品界面、价格和版本变化很快，选型时需记录精确身份与测量条件。文中尚未运行的实验标为待验证。

## 1. AI能写代码以后，工程师应把注意力放在哪里？

需求与验收、跨模块合同、数据/权限边界、架构取舍、并发/资源、审查和运行反馈仍需明确责任。AI也能辅助这些工作，不能把“写代码”与“管代码”说成互斥的职业替代。生成多不代表解决多，测试通过也不覆盖所有业务或安全要求。

编码场景通常有代码、类型、测试和可回滚变更，便于形成反馈闭环；业务动作可能缺可重置环境、授权或可靠判分。这个解释是条件比较，不是对所有领域成功率的统计结论。先用小步修改、差异审查、固定规格、静态检查和独立测试约束反馈，防止模型删测试或硬编码样例。

规格驱动开发写清目标、输入输出、边界、异常、非目标和验收，再让规格、实现与测试共同迭代。TDD侧重测试反馈，两者可以互补；错误规格不会因实现完全遵循而变正确。项目重建可按数据模型、访问层、服务与API小步实施，但每步保留跨层合同，不假定第一版必然需要全部重写。

**练习：** 同一注册功能让两种工作流实现，固定业务约束、修改范围和时间预算，对比隐藏用例、审查负担与成本；没有真实实验时不报告改善比例。

### 追问：同一个AI，为什么两个人做出的代码质量不同？

**口述答案：** “同一个模型只是相同的能力起点，不代表拿到了相同任务。需求是否完整、选了哪些仓库上下文、怎样拆修改、有没有独立验收、能否定位失败，都会影响产物。我会用一次具体变更讲清输入、决策、差异和验证，而不是把质量差异全归成提示词技巧。即便这些条件固定，生成仍可能有随机性，因此一次结果不能代表稳定水平。”

**原理与例子：** 假设需求是“让用户取消报告生成”。只说“加一个取消按钮”，可能得到前端隐藏进度但后台仍调用模型的实现。先写合同则要回答：取消哪个用户的哪个任务；取消状态何时生效；正在调用的工具是否接受取消；已上传文件能否撤销；晚到结果能否提交。代码审查再沿按钮→API→任务身份→取消信号→工具→状态提交逐层检查。生成、检查和责任不是三个互相替代的角色。

**追问一：测试全绿，还可能错在哪里？** 测试可能只检查按钮文字，漏了服务端权限、同时运行的第二个任务、取消和完成的竞争、未知外部结果。先核对测试是否来自独立验收条件，再看模型是否删除断言、放宽预期、硬编码样例或顺手扩大依赖与权限。增加“甲取消后乙仍继续”“旧结果不得覆盖终态”等反例，不用模型自述代替实际状态断言。

**追问二：是不是把一切都交给另一个AI审查就够了？** 另一个审查器能帮助发现问题，但可能共享盲点，也可能没有完整上下文。应组合差异审查、类型/静态检查、确定性契约测试和必要人工判断。真实故障还需查运行状态；不能把“建议已采纳”当“部署已验证”。

**误区：** 代码行数、AI生成比例和提交数量都不是质量指标；“用了同一个品牌”不等于模型版本、工具权限、上下文和预算一致。面试只讲自己实际做过的检查；没独立实现取消，就说这是设计分析。继续练[固定源码的取消与提交边界](../50-projects/source-code-interview-deep-dive.md#direction-03)，不要把示例改写成个人生产经历。

## 2. Token成本、长上下文与团队规范怎样治理？

以任务为边界选择相关文件、函数和受控证据，保存精确约束与阶段结论；不是把全仓库和全部历史都输入。稳定规则描述构建、测试、架构和禁止事项；专业流程按需加载。规则文件与导入内容会占上下文，不是免费卸载记忆。

成本从无效调用、输入输出、重复前缀、失败重试和任务路由测量。缓存减少某些重复计算，不改变注意力机制，也不必减少窗口中的token数。某个工具常用5–8文件或某种JSON格式更省token，只能作待测策略，不能推广成阈值。

规范结合类型/lint/格式检查、测试和CI；Python类型注解本身不强制运行时类型，脚本/钩子和规则文档也有不同执行语义。Claude Code的持久指令与auto memory是不同上下文机制，不是强制执行配置；不能用“团队、个人、会话三层”当其完整机制。具体路径、加载与功能版本在使用时再查官方文档。

Codex、Claude Code、Cursor或其他编辑器的体验比较，只能来自自己的同任务记录。参照[面试工具比较](../90-interview/01-evidence-based-interview-preparation.md#coding-tools-and-harness)记录精确版本、上下文选择、编辑差异、测试、恢复、费用和时延，不编造“我用过”的故事。

### 追问：一个月用了多少token、花了多少钱，怎样回答才可信？

**口述答案：** “我先说明统计范围：哪个项目、哪段时间、哪种模型与币种，统计所有真实请求，包含失败和重试。输入、缓存输入、输出按当次价表分别算，再与服务方账单对账。没有 usage 的超时请求保留未知和预算预留，不记零；订阅额度、API估算与实付账单分开。没有自己的记录就明确说未统计，不报一个听起来合理的数字。”

**原理与手算例子：** 多轮请求通常重新提交本轮需要的上下文。假设三次请求的总输入分别是 4000、8000、12000 token，累计输入是 24000，而非最后一轮的 12000；这也不等于三次新增用户文本之和。缓存是否命中以实际 usage 为准，不能看到相同前缀就当它免费。

为便于练习，使用完全虚构的价表：每百万 token 未缓存输入 USD 2、缓存输入 USD 0.2、输出 USD 8，绝不是当前供应商报价。假设三次合计输入 24000，其中缓存输入 6000，输出 2000；这里明确“输入包含缓存子集”。则估算为 (18000×2 + 6000×0.2 + 2000×8) / 1000000 = USD 0.0532。若错误地把全部 24000 都按未缓存价计算后再加缓存费，就会重复计费。同样的调用结构发生 1000 次，才可作 USD 53.2 的情景估算，不是用户月账单或任何项目实测成本。

**追问一：请求超时，没有拿到最终 usage，能算免费吗？** 不能。客户端没收到不代表服务方没处理。把该请求标为未知，保留原请求身份与保守预留，查服务方记录再对账。例如上述已知估算 USD 0.0532，加未知请求预留 USD 0.04，总占用为 USD 0.0932；后者不是已消费账单，也不能把这笔预留编成实际 token。查清后替换同一请求的未知记录，不能追加一条已知记录却忘记释放原预留。重试必须是另一个真实请求，仍可能产生费用。

**追问二：换模型或启用缓存，怎样证明省钱？** 同一冻结任务集比较完整成功率、全部尝试费用、每个成功任务的总成本、P95完成时延和关键失败。便宜请求若多次修复，端到端可能更贵；仅对成功请求平均会隐藏失败成本。明确输入是否包含缓存、推理 token 是否已包含在输出、工具调用及外部搜索是否另计、免费额度/批量价/税费/汇率是否适用，不把不同币种直接相加。

**误区与工程边界：** 本地 tokenizer 的文本长度估计不等于服务方计费用量；缓存节约计算或单价，不代表消失于上下文窗口。设置单请求输出上限也不等于限制多轮、子任务和重试的总预算。多实例预算准入需要对共享余额原子预留、结算和未知状态持久化，不能依赖各进程读余额后分别放行；下面的计算器不实现这些机制。

**动手验证：** [离线成本计算器](../../examples/agent_costs/cost_ledger.py)明确采用“输入含缓存子集”的归一化合同，用 Decimal 避免二进制小数误差；[测试](../../examples/agent_costs/test_cost_ledger.py)覆盖多轮累加、失败照计、缓存不重算、未知预留/对账、重复身份及非法数值。运行 python3 -B -m unittest discover -s examples/agent_costs -v。遍历 n 条请求为 O(n) 时间，去重集合为 O(n) 空间；同次汇总只接受一种价表快照和币种，先按供应商/模型/计费版本分组再汇总。它不联网、不读取密钥、不估算真实模型效果，也不是并发预算闸门或账单系统。

## 3. 怎样跟踪前沿，怎样读榜单？

按发现→官方核验→论文方法/限制→小实验→可复查总结组织学习。研究者动态、GitHub和通讯适合发现线索，不能代替原论文、代码、模型卡和官方文档。记录发布日期与事件日期、版本和适用条件；过时目录、已停维护产品及二手图表需另查。

|入口|主要用途|必须核对|
|---|---|---|
|Arena|偏好对战观察|题目/人群分布、统计方式、置信区间与风格影响|
|Artificial Analysis|能力、速度、费用等维度|精确endpoint、样本、token口径、负载和方法版本|
|Open LLM Leaderboard|公开模型评测记录|数据release、维护状态、模型commit、量化和运行协议|
|SWE-bench|代码修复任务|具体split、harness/环境、patch范围与测试规则|

比较榜单时必须核对任务、评分、样本、模型版本与更新时间，不能默认当前排名已经验证或榜单仍在持续维护。综合与Agent基准见[评测章节](25-agent-evaluation-and-routing.md#model-benchmarks)，能力、偏好、价格和执行成功不能合成一个无条件总排名。

## 4. OpenClaw与Skills怎样讨论产品价值和风险？

讨论的是能力包复用、触发、方法、工具时机、必要询问、错误出口、scope与guardrail。格式可以让经验更容易分发，实际输出仍取决于模型、输入、工具、环境和运行时，不能从“结构化Skill”推出确定性或可靠性。

OpenClaw的技能机制应按实际采用的版本确认；不要用旧截图或其他产品格式替代它的当前合同。本章不安装技能、不运行OpenClaw，也不宣称当前市场优势。学习原理可参照[Skills结构与治理](16-skills-routing-and-governance.md)。

产品取舍分成使用门槛、可发现能力、生态质量、权限边界、调试/回滚与长期维护。路由冲突、恶意/低质技能、依赖变动、作用域过大和供应链需要独立验证。社区规模或流行度只是现象，因果解释与商业壁垒须有数据；可复制的包格式不等于可复制的有效数据、反馈或运行系统。

## 5. 固定DAG能让Agent“完全可控”吗？

把操作拆为有Schema、结果和失败条件的能力，建立黄金用例、预算和回退，可缩小错误面。注册流程可以拆校验、重复检测、创建记录和发验证邮件；每步说明输入/输出和副作用，邮件失败与注册失败不是同一个状态。

固定DAG适合明确依赖，不是所有Harness或Agent的唯一结构。动态探索、有限循环、人审和待输入可能必要；无论结构怎样，权限、语义、幂等、恢复与真实终态都要验证。合法JSON不意味着允许发邮件，模型选中工具不意味着目标批准。

能力逐项加入，使用未见回归、异常与注入反例测净收益；未覆盖情境保持澄清/失败或人工出口。代码骨架可以预先约束接口，但不能保证“完全无幻觉”。执行治理基础见[生产设计](26-agent-production-design-lab.md)与[Harness](18-harness-runtime-and-observability.md)。

<a id="framework-and-market"></a>
## 6. RAG框架、To C/To B与行业应用怎样选？

按解析、摄取、索引、查询/重排、组件定制、产品工作流、部署与数据限制、团队栈和运维来比较RAGFlow、LangChain、LlamaIndex、Dify等候选。不能统一宣称只有某框架能解析、某框架一定最灵活；先检查当前版本并做最小任务基线，再决定是否需要框架。

To C可能重体验、个性化、多模态或端侧，To B可能重业务规则、权限、审计和系统集成，但这不是单Agent与多Agent的必然分界。可靠性目标由失败代价、合同和负载决定，不把99.9%套给所有业务。核心加插件、编排加能力包是候选设计，是否有价值取决于可测复用与运行质量。

软件开发、客服或销售等应用可按数据可得性、反馈、可验证动作和使用习惯分析；不要据此发布“未来几年必替代多少工作”或固定行业排名。职业准备侧重真实需求理解、工程判断、领域知识、测量与持续学习。实际用AI完成的补全、调试、重构和文档工作记录为自己的样本，不借用别人的使用比例。

## 7. 开放权重、闭源服务、长上下文与端侧怎样比较？

逐项比较任务能力、数据接收方、可部署范围、许可证、定制方式、审计、运行资源和维护成本。开放权重不等于训练数据/全部过程开放；闭源服务也可能有受控定制接口。不能用未核查训练成本、家族名字或“便宜十分之一”决定方案，也不能把敏感行业一概规定为某种模型。

Qwen等模型家族不能用一个窗口数字概括：确认精确模型、权重/服务身份、tokenizer、版本及输入/输出限制。长窗口仍需测任务质量、位置效应、费用和时延，不能仅凭容量参数推荐。

端侧可减少网络依赖并支持特定本地数据场景，代价包括模型能力、内存、功耗、热约束、存储与生态。量化与CPU/GPU运行时以实际模型、设备、序列、并发和量化配置测试；“3B等于某大模型”“几十毫秒”“零成本”都不是通用结论。端云协作明确哪些数据外传、何时升级和断网时做什么，本地运行不自动阻止日志、遥测或插件外传。

<a id="robotics-and-future"></a>
## 8. LLM与机器人、持续学习和AGI该怎样回答？

LLM可参与语义目标解释、高层任务分解与交互恢复；感知定位、运动控制、实时deadline与物理安全需要适合设备的控制系统。不能因为模型会计划就允许它直接发无约束执行指令。验证分为仿真、受控设备与实际场景，并声明sim-to-real差距；本章没有机器人运行证据或落地时间预测。

持续学习、低成本端侧和可解释性可作为研究方向，但软件自动化框架不是已完成持续训练的证明。AGI定义与评价并无本章采用的确定统一尺度，因果、世界建模、长期学习和分布外行为应以任务和证据讨论，不说模型“只是统计，因此绝不具备某能力”，也不预测5–10年必达成。

“涌现”先检查测量：阈值或离散评分可能把连续变化显示成跳跃；能力组合与任务结构还需受控实验。模型升级和架构改进可共同起作用，比较同预算、同任务与相同权限；架构ROI不必总高于模型。没有实验不能断言所有问题靠prompt可解，或所有失败只能等更大模型。

<a id="security-and-personalization"></a>
## 9. 可靠性、AI安全与个性化隐私怎样落地？

Agent可靠性受决策、状态、工具、长程依赖和验证共同影响。0.95的十步乘积约为0.60，只是适当独立/条件成功概率假设下的演算，实际存在相关故障、重试和纠错。向用户说明能力范围、未知结果与介入条件，用失败成本和真实任务回归评估投入产出。

威胁模型区分注入/越狱、投毒与供应链、数据/工具滥用、虚假信息与公平等社会影响以及更长期对齐研究。按系统可暴露的能力和失败代价排优先级，不预先断言某种开放程度一定更安全或更易投毒。独立执行权限、隔离、日志和验证不能被模型或技能的“安全声明”替代。

个性化只收集目的所需数据，偏好也可能是个人数据；来源、用途、作用域、有效期与用户可控更正/删除都要明确。联邦学习仍可能泄露信息，不自动提供隐私；差分隐私的保证依邻接关系、参数、组合与实现而定，不是“无法反推”的绝对承诺。本章未实现联邦或差分隐私系统。

删除范围包括主数据、索引、缓存、日志和备份策略；曾经用作训练数据后的模型影响是另外的问题，不能只删一条向量就宣称彻底删除。实践中以数据最小化、授权、作用域、版本和可核查记录为基础，再评估额外隐私技术。
