# Text-to-SQL Agent：从一句需求到可解释的查询结果

[Agent 目录](README.md) · [六表 SQL Skill](31-tool-mcp-and-skill-contracts.md#synthetic-sql-skill) · [批处理任务与恢复](../50-projects/data-engineering-agent-case.md#job-lifecycle)

本章讨论一个通用教学设计：只允许分析已授权数据，模型提出查询候选，应用决定能否执行和发布。配套代码只运行合成内存数据库中的固定查询；没有接入模型或生产数据库。

<a id="text-to-sql-answer"></a>

## 面试题：直接写 SQL 或人工取数也能完成，为什么还要 Agent？需求怎样变成 SQL？

**可以这样口述：**

“如果需求和指标固定，我优先用参数化报表或 BI：查询经过审核，成本、权限和结果都更可预测。Agent 的潜在价值，是把变化较多的自然语言需求转换成受控的数据分析过程，帮助用户澄清口径、找到相关 schema、组织查询和解释结果；是否更省时、更准确仍要做对照评测。

我会先确认指标、统计粒度、时间和权限，再从可信目录中检索当前用户可访问的相关表、字段、关联键与指标定义。模型据此生成 SQL 草稿和参数，应用做确定性校验、权限检查和预算控制，才调用受限查询接口。查询成功之后，还要检查结果是否满足约定，并附上口径、数据版本和查询身份才能交付。错误只按类别做有上限的修复；空结果可以是正确结果。能执行、在一个样本上答案相同、业务上答对，是三种不同结论。”

这里没有承诺 Agent 能发现所有正确表、自动推断业务规则，或替代数据负责人。把“生成 SQL”当作整个产品，会遗漏最容易答错的口径与执行责任。

<a id="sql-request-contract"></a>

## 先把问题变成可核对的口径

假设用户问：“给我上个月按买家的付费订单数。”在生成 SQL 前，应用至少要收敛以下合同；无法从已批准定义中确定的部分，再向用户澄清。

| 合同项 | 必须明确的条件 |
| --- | --- |
| 指标 | 订单支付成功、净支付还是结算成功？取消/退款如何归属？采用哪个指标定义版本？ |
| 粒度 | 一行代表买家、订单还是商品明细？数订单不能被一对多连接变成数明细。 |
| 时间 | 用下单、支付还是结算时间？“上月”按哪个业务时区，以哪次请求的时间解析？上下界是否包含？ |
| 空值与重复 | 未知买家排除、单列还是报数据质量问题？重复事件按哪个业务键和版本去重？ |
| 数据与时效 | 数据来自哪个获准仓库/视图，快照或水位到何时？目录版本与实际 schema 是否相符？ |
| 输出 | 列、单位、允许的结果规模与可见范围；是否要求排序，以及并列值如何稳定排序？ |

**数据来自已登记的数据系统，不来自模型的记忆。** 数据负责人维护可追溯的表/列、主外键、指标公式、更新时刻、适用范围和废弃版本。schema linking 是把需求中的“买家”“付费”对应到候选列和业务定义，不是只做表名相似度检索。目录也可能过期；发现字段不一致要核对版本和新鲜度，不能让模型凭空补列。

检索前就带入认证上下文，只取该身份可访问的相关 schema、注释与必要统计信息。不要把全库表名和样例行先交给模型，再指望它自觉不使用敏感表。若确需样例，仍要单独检查行/列权限和脱敏；只过滤 schema 的名字不能代替数据库授权。相关关系没检索全时，应继续在已授权范围查找或停下来澄清，不能假定“Top-K 已满所以信息完整”。

<a id="sql-controlled-flow"></a>

## 模型提出候选，应用控制流程

可以将流程分成三个交付边界：**SQL 草稿、已授权执行、结果发布**。用户只要 SQL 时，到草稿就结束；授权读取数据也不自动授权导出到别处。

| 步骤 | 模型可做什么 | 应用必须掌握什么 |
| --- | --- | --- |
| 收敛请求 | 提议要补问的口径 | 身份、允许的数据域、已确认的合同与版本 |
| 找 schema | 从授权候选中提出关联与字段 | 可信目录检索、权限过滤、版本/时效检查 |
| 生成草稿 | 提出 SQL、绑定参数、预期列与假设 | 固定方言和输出结构；缺信息不得伪装成确定结论 |
| 校验与授权 | 可用 checker 发现语法/逻辑疑点 | SQL 解析及语句、表/列/函数/外部访问策略；执行身份和实际数据库权限；每个候选重新检查 |
| 执行与修复 | 根据结构化错误提出候选修改 | 查询时限、扫描/输出/并发预算、剩余尝试数、取消与停止条件 |
| 验收与交付 | 根据已获得结果解释发现 | 列/单位/口径检查、可见范围、数据与查询身份、最终发布状态 |

解析器和策略检查也不是权限系统的替身：数据库应使用最小权限身份，按实际引擎落实可访问对象与运行限制。对视图、可调用函数和外部连接等间接能力也要核查。不能只因语句以 `SELECT` 开头、附有 `LIMIT`，或 `EXPLAIN` 成功就放行。`LIMIT` 限制返回行数，不保证扫描量小；计划可生成也不证明指标或连接正确。LLM 自我批评/另一个 query checker 是质量辅助，不是安全边界。

校验通过的草稿应绑定 SQL 摘要、参数、合同版本和授权作用域，再执行对应候选；修改后不能沿用旧候选的批准。结果发布至少说明采用的指标/时间范围、数据快照或水位、目录/指标版本、查询运行标识和是否截断，供获准用户追溯。敏感参数与原始行不能未经处理直接写进展示或审计日志。

本章不实现这些生产门禁；固定六表查询的执行约束见[SQL Skill](31-tool-mcp-and-skill-contracts.md#synthetic-sql-skill)，长任务提交、状态对账和取消竞态见[数据工程案例](../50-projects/data-engineering-agent-case.md#job-reconciliation)。

<a id="sql-semantic-witness"></a>

## 会执行为什么还可能答错？用反例数据库分开三层结论

约定一个极小指标：统计 UTC 窗口 `[2026-10-01 00:00:00, 2026-10-02 00:00:00)` 内、状态为 `paid` 且买家已知的订单数，每个买家一行。订单主键唯一。这里的状态和时间是合成快照的约定，没有模拟退款历史或业务时区转换。

正确候选在订单粒度上聚合：

```sql
SELECT buyer_id, COUNT(*) AS paid_orders
FROM orders
WHERE status = :status AND buyer_id IS NOT NULL
  AND paid_at >= :start AND paid_at < :end
GROUP BY buyer_id;
```

错误候选多连接了一张明细表，却仍然 `COUNT(*)`：

```sql
SELECT o.buyer_id, COUNT(*) AS paid_orders
FROM orders AS o JOIN order_items AS i ON i.order_id = o.order_id
WHERE o.status = :status AND o.buyer_id IS NOT NULL
  AND o.paid_at >= :start AND o.paid_at < :end
GROUP BY o.buyer_id;
```

两条 SQL 都能执行。在空数据库上都返回 `[]`；在每个订单恰好有一条明细的数据库上，也可能返回同样的订单数。**一个买家的一张订单有两条明细**时，第一条返回 `(7, 1)`，第二条返回 `(7, 2)`。这是区分候选的 witness fixture：有意构造能暴露语义差异的数据。若合同本来要数商品明细，第二条可能符合另一种需求；错误取决于当前约定，不取决于 SQL 长得复杂。

还需要不同的边界反例：

| 合成 fixture | 要区分的候选 | 可观察差异 |
| --- | --- | --- |
| `empty` | 正确与多个错误候选 | 都为空，不能据此区分 |
| `ordinary` | 订单聚合与明细聚合；`< end` 与 `<= end` | 一单一明细且没有上界行，差异仍被掩盖 |
| `fanout` | 订单聚合与明细聚合 | 两条相同明细使订单数从1变成2 |
| `boundary` | 半开窗口与包含上界 | 起点计入、终点排除；错误上界把下一窗口订单算进来 |
| `nulls` | 已知买家指标、遗漏空值规则、`!= NULL` | 未知买家应排除；与 NULL 用普通不等号比较不能代替 `IS NOT NULL` |

因此要分别说清：

1. **可执行性**：当前方言接受并运行 SQL，可能仍然问错问题。
2. **给定 fixture 的执行结果一致**：只说明这些输入上未观察到差异；空库和过于整齐的数据可能没有区分能力。
3. **业务语义正确**：还依赖经确认的指标、数据与授权边界，不能靠一次执行成功或有限测试自动推出。

测试套件通过仍是有限证据。新增 fixture 应针对可能的错误变体，并覆盖已约定的连接、NULL 和时间条件；不要把测试样本反复调成让某个候选过关。这里未复现通用基准评测器，也没有测任何真实模型的准确率。

<a id="sql-result-comparison"></a>

## 比较结果时，既不能只比 SQL 字符串，也不能随意去重

大小写、空白、别名和部分写法不同，不一定改变语义。例如在本查询里，`COUNT(1)` 与 `COUNT(*)` 都数选中的行；重排独立的 AND 条件也可得到不同文本的同一结果。实验保留一个这样的候选，在全部已登记 fixture 上与正确候选比较。不能仅因字符串不同就判错，也不能从这几次相同推广为任意改写等价。

没有显式排序要求时，比较无序的 **bag（多重集合）**：不仅比较有哪些行，也比较每行出现几次。`[(7,), (7,), (None,)]` 与 `[(7,), (None,)]` 转成 set 后相同，却不应视为相同结果。用 `Counter(tuple_rows)` 保留重复数，也避免把带 NULL 的行混合排序而触发 Python 类型比较错误。

若合同要求顺序，就比较序列；查询需要相应 `ORDER BY`，分页或 Top-N 还要约定并列值规则。没有 `ORDER BY` 时，SQLite 的返回顺序不构成合同。

配套比较器只对本实验的整型/NULL、按位置对齐的行做精确比较，不检查列名、单位，也不实现通用 SQL 类型、排序规则或浮点误差等价。bag 比较在常见哈希假设下需 `O(n)` 时间、`O(u)` 额外空间，`u` 为不同结果行数；大结果不应无限载入内存，这里数据刻意很小。

原始实现：[semantics_lab.py](../../examples/text_to_sql/semantics_lab.py)；测试：[test_semantics.py](../../examples/text_to_sql/test_semantics.py)。只接受固定 fixture/查询名称，内部创建并关闭内存 SQLite，不接收用户 SQL。这是演示入口范围，不是任意 SQL 的安全证明。

```bash
python -B examples/text_to_sql/semantics_lab.py
python -B -m unittest discover -s examples/text_to_sql -p 'test_*.py' -v
```

测试覆盖空库假一致、普通库假一致、连接倍增、NULL、半开时间边界、不同文本候选、bag重复数和显式顺序。没有模型调用、真实业务库、权限系统、取消、并发或性能实验。

<a id="sql-repair-and-followups"></a>

## 追问：空结果、报错和取消分别怎么处理？

**查出零行，是否让模型换一条？** 不自动换。先保留成功执行、合同和数据版本；零行可以是正确答案。必要时在获准范围核对水位、过滤条件与数据质量，并向用户说明不确定性。为了得到非空结果擅自扩大时间、删除条件或换指标，会改变问题。

**字段不存在，是否一直把错误喂回模型？** 先归类。schema 过期时，在原授权范围核对目录版本；语法/方言问题可以给结构化诊断，让模型提出新草稿，再完整校验。可为一次请求设定例如“最多两次候选修复且共享总 deadline”的教学策略，实际阈值应按任务预算决定。权限拒绝应停止或走正式授权流程，不能换表、扩大身份或移除权限谓词；超时/扫描预算耗尽先检查执行状态，不能无界重跑。修复改变业务口径时重新确认合同。

**停了 token 流，SQL 就取消了吗？** 没有。取消要传到应用运行、排队任务和数据库连接/查询标识，由驱动调用对应取消能力并确认状态，停止后继执行与发布。Python SQLite 提供 `Connection.interrupt()`，但这个小实验没有测试跨线程取消；不同数据库需按自己的驱动和后端核验。取消与查询完成竞态时，应用应明确结果是否仍可发布；后端状态未知就报告待确认。

**为什么不直接给整个 schema，让模型自己找？** 多表不等于更多有效信息。先按认证上下文缩小数据域，再检索相关关系、字段与指标版本；信息不够就补检索或澄清。模型不能替应用批准读表，目录中的说明文字也不能变成扩大权限的指令。

**如何证明方案值得做？** 用固定且隔离的任务，比较参数化报表/BI、人工流程和候选 Agent。分别记录口径澄清、schema 选择、SQL 执行、语义结果、越权阻断与总耗时/成本，不用“SQL能跑比例”替代业务正确率。先有获准数据和独立判分，再谈收益；本章只提供确定性反例，不提供这些对照结果。
