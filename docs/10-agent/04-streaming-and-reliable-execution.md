### A24 SSE 与普通 HTTP、WebSocket 的区别是什么？

**优先级：P0** 

**知识点详解** 
- SSE 是基于 HTTP 的服务端事件流，不是“取代 HTTP”的协议。响应通常使用 text/event-stream，按事件格式持续发送 UTF-8 文本。
- 对浏览器 EventSource 来说，数据主要由服务器向客户端推送；客户端操作可另发 HTTP 请求。WebSocket 支持在同一连接中双向通信。
- Token 输出、任务进度通知通常适合 SSE；是否用 WebSocket 要看是否需要持续双向交互，而非哪个听起来更高级。

**具体例子** ：前端 POST 创建任务，得到 task_id，再订阅该任务的 SSE；取消时另发取消请求。

**30 秒答题主线** ：SSE 用一个持续的 HTTP 响应推送事件，适合服务端单向进度或文本流；普通请求通常一次返回，WebSocket 则适合持续双向交互。SSE 只是传输层选择，不提供任务持久化和执行保证。

**追问** ：事件为什么用空行分隔？原生 EventSource 能否随意设置请求头？

**常见错误** ：说 SSE 不使用 HTTP；认为流式展示就表示后台任务可靠。

**来源** ：[AG-T24](../../sources/catalog.md#ag-t24)。

### A25 SSE 断线重连，如何避免漏事件或重复展示？

**优先级：P0** 

**知识点详解** 
- SSE 支持事件 ID 和重连机制；浏览器可携带 Last-Event-ID，但服务器必须自行保存事件并实现续传，协议不会自动存日志。
- 可为每个任务维护递增序号，客户端按序号去重；服务端根据已确认位置回放。若历史已过期，返回完整状态快照再继续订阅。
- 心跳可以用注释行维持活跃，但它不能证明业务任务仍在健康执行；任务健康需单独监控。

**具体例子** ：客户端最后收到序号17，重连时回放18以后；若再次收到17，忽略重复，不再追加相同文本。

**30 秒答题主线** ：重连需要事件 ID、可回放的服务端记录和客户端去重共同实现。我会区分连接恢复与任务恢复，历史缺失时用状态快照兜底，不能仅依赖 EventSource 自动重连。

**追问** ：断线时任务继续还是取消？事件保存多久？

**常见错误** ：有 retry 字段就说绝不丢消息；把心跳当业务进度。

**来源** ：[AG-T25](../../sources/catalog.md#ag-t25)；回放/快照为应用层设计。

### A26 后端在逐条写 SSE，为什么前端还是最后一起显示？

**优先级：P0** 

**知识点详解** 
- 数据可能滞留在应用缓冲、中间件、反向代理或客户端解析层；调用 Write 不一定意味着浏览器已拿到数据。
- Go 可检查 ResponseWriter 是否支持刷新，完成一个合法事件后 Flush；但代理仍可能缓冲，因此要对整条部署链验证。
- 响应头发送后通常不能改成新的 HTTP 错误状态码；此时需发送结构化错误事件并结束流，前端区分业务失败与正常完成。

**具体例子** ：本地逐秒输出正常，上线后聚合输出，应检查代理缓冲、压缩和超时配置，而非先怀疑模型没流式生成。

**30 秒答题主线** ：我会逐层确认从模型流、应用写入与 Flush，到代理和浏览器的到达时间。服务端刷新只是必要环节之一。事件格式、错误事件和连接关闭都要测试，不能只看本地终端。

**追问** ：客户端很慢怎么办？什么时候还能修改响应状态码？

**常见错误** ：每个字节都强制 Flush；认为 Flush 保证数据立刻到达最终客户端。

**来源** ：[AG-T26](../../sources/catalog.md#ag-t26)。

### A27 长任务为什么要和 HTTP 连接解耦？恢复时从哪里继续？

**优先级：P0** 

**知识点详解** 
- HTTP 请求生命周期通常短于复杂研究任务。把任务仅放在请求 handler 内，刷新页面或进程退出可能丢失进度。
- 可将创建任务、后台执行、状态查询和事件订阅分开。任务状态机如 queued/running/succeeded/failed/cancelled 是应用层方案，需要持久存储。
- 检查点保存“已完成什么、下一步是什么”。恢复不等于从任意代码行继续；某个节点可能被重新执行，外部副作用仍需幂等。

**具体例子** ：报告检索已完成而写作失败，可从已保存证据继续；若只保存一句“执行到一半”，就无法可靠恢复。

**30 秒答题主线** ：我用独立任务 ID 和持久状态管理长任务，HTTP 只负责提交和观察。恢复以清晰的检查点为边界，并检查哪些步骤可能重跑。事件流断开不应自动被当作任务丢失或成功。

**追问** ：进程崩溃后谁接管？处于 running 的任务怎样判定失联？

**常见错误** ：把 goroutine 当持久队列；写了 checkpoint 就宣称所有工具恰好执行一次。

**来源** ：[AG-T27](../../sources/catalog.md#ag-t27)；HTTP 解耦与状态机为工程设计展开。

### A28 Go 中如何取消 Agent、限制并发和避免 goroutine 泄漏？

**优先级：P0** 

**知识点详解** 
- context 传递取消信号和截止时间，但取消是协作式的；模型请求、工具和数据库操作要实际监听或使用该 context。
- 并发不是无上限起 goroutine。可用有界 worker pool 或 semaphore 限制同时调用数，并让排队也响应取消。
- 下游退出后，上游若永远阻塞在 channel 发送就会泄漏；发送/接收、等待和收尾路径都需考虑取消及资源释放。

**具体例子** ：同时检索20个 query，却只允许4个外部请求；取消任务后，不再启动队列中剩余查询，并让在途请求尽快退出。

**30 秒答题主线** ：取消必须从任务传播到每层 IO，不能只改数据库状态。我会限制并发和队列长度，确保 channel 操作可退出，并在取消后等待必要清理，最后校验迟到结果不会写回已结束任务。

**追问** ：某第三方 SDK 不支持取消怎么办？cancelled 状态还能被 succeeded 覆盖吗？

**常见错误** ：认为调用 cancel 会强杀所有 goroutine；无限加缓冲掩盖阻塞。

**来源** ：[AG-T28](../../sources/catalog.md#ag-t28)、[AG-T45](../../sources/catalog.md#ag-t45)；迟到写回检查为工程建议。

### A29 模型或工具超时，怎么重试才不会越重试越糟？

**优先级：P0** 

**知识点详解** 
- 先分类：参数不合法、无权限不应原样重试；网络波动、部分服务端错误可能适合重试。限流要结合服务端返回的等待建议。
- 设置单次 timeout 和整体 deadline，采用有上限的指数退避加随机抖动，限制总尝试次数与费用。
- 多层都自动重试会放大流量。应明确由哪一层负责；有副作用的调用超时后还要确认是否已经生效。

**具体例子** ：模型调用失败若库内重试3次、业务再重试3次，最多可能产生9次调用，而非你以为的3次。

**30 秒答题主线** ：我会先判断错误是否暂时、操作是否可安全重试，再受总 deadline 和预算约束地退避重试。对持续过载要限流或降级，不能用更多重试把依赖压垮。

**追问** ：超时值如何确定？模型已生成但响应丢失是否仍可能计费？

**常见错误** ：所有异常统一立即重试；把超时理解成服务端肯定没执行。

**来源** ：[AG-T29](../../sources/catalog.md#ag-t29)。

### A30 Agent 工具副作用如何做到幂等？Exactly-once 能随口承诺吗？

**优先级：P0** 

**知识点详解** 
- 幂等指同一个业务意图重复执行不会增加额外效果，不是每次网络请求都只发送一次。创建任务等操作可使用调用方提供的幂等键。
- 去重记录与业务变更应尽量处于同一事务边界；记录请求摘要、执行状态和结果，拒绝同键不同参数造成的语义冲突。
- 外部服务不支持幂等时，只靠本地标记无法消除“外部已成功、本地未记账”的窗口，需要查询对账、补偿或人工介入。

**具体例子** ：保存报告使用 task_id+version 作为业务唯一标识；重试返回已有结果，不重复创建两份相同版本报告。

**30 秒答题主线** ：我通常保证可重试和去重后的业务效果，而不会笼统承诺全链路 exactly-once。必须明确幂等键、事务边界和故障窗口，外部结果不确定时先核实再重试。

**追问** ：幂等键保存多久？重复请求到达时第一次仍在运行怎么办？

**常见错误** ：仅对请求参数取 hash 就认为识别了用户意图；SSE 去重被误说成业务副作用幂等。

**来源** ：[AG-T30](../../sources/catalog.md#ag-t30)。
