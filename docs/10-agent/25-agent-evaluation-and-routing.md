# Agent评测、提示回归与模型路由

本章是原创教学补充。核查日期：2026-10-10。基本工具与状态见[A01–A08](01-agent-loop-tools-and-state.md)，检索诊断见[A16–A18](02-rag-retrieval-and-reranking.md#a16)，版本与Trace见[Harness](18-harness-runtime-and-observability.md)。下面的实验设计尚未跑模型、在线A/B或公开基准，不是项目成绩。

<a id="eval-contract"></a>
## 1. 怎样定义“做得好”，而不是让模型自称完成？

评测对象是模型、提示、上下文、工具和运行时的组合。先写任务初态、输入、允许动作、禁止动作、终态及失败分类，再设计评分。一次任务可以有多次独立试验；每次都重置数据、权限、缓存和外部状态，不能把第一次留下的产物当第二次能力。

原创任务例子：从三份授权规则中解释退款条件。验收包括引用支持每条条件、没有读越权规则、保留关键例外、无材料时承认缺证据。答案文风好看只是次级指标。下单任务则检查订单数据库的真实终态；“已下单”的回复不能当成功证据。[Anthropic评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)区分任务、试验、判分器、轨迹和环境结果。

安全要求先作为门槛，再比较质量、成本和耗时。不能用更高的平均完成率抵消一次严重越权。固定失败分类为参数、权限、依赖故障、证据不足、模型错误、执行器错误、评测器错误；“工具服务停机”不应自动计成模型推理错误。

**30秒主线：** 先定义可观察终态和安全门槛，用真实产物验证，再在可重置环境重复试验。保存组件版本、输入与判分依据；未测范围保持未知。

<a id="grader-choice"></a>
## 2. 代码、模型与人工判分怎样组合？

确定性要求优先用程序：文件内容、数据库状态、字段范围、工具ID关联、代码测试和是否发生未授权动作。开放性要求可用明确rubric，由模型辅助检查相关性、结构与表达。高风险、标签含糊或判分器冲突的样本进入人工复核。

LLM-as-a-Judge有速度与规模优势，但会受位置、长度、风格、同源偏好、评分尺度和事实能力影响。做成对比较时交换A/B位置，隐藏生成模型身份，提供必要参考证据，允许“不可判断”，并用人工标注校准。多模型投票仍可能共享错误，不自动形成独立证据。[MT-Bench与Chatbot Arena论文](https://arxiv.org/abs/2306.05685)讨论模型评审及偏差。

判分器也要回归：收集会误判的正确答案、刷分答案、长但错误答案和格式不同的等价答案。报告判分器对人工参考的混淆矩阵或一致率；不要用生成器能修改的测试文件作为唯一裁判。

**验收：** 同一个事实答案只改变长度、顺序和格式，检查评分波动；让评审遇到无证据主张，必须能拒绝强行给高分。

<a id="prompt-regression"></a>
## 3. Prompt调优“修好一类、坏了另一类”怎么办？

把角色、任务指令、示例、输出格式、工具说明和停止规则拆成可控变量。每次只改必要组件，保存版本与差异；同一冻结样本集比较旧版、新版和最简单基线。按任务类型、语言、输入长度、缺参数、无答案、否定需求和风险分桶，而不是只看总分。

训练/开发样本用于调参，留出集用于最终评估。近重复应按实体、模板、文档来源或时间分组隔离。重复试验报告成功次数与总次数；小样本差异要附不确定性，不把偶然涨分解释成稳定改进。提示越长不必越好，few-shot和结构化包装也可能增加token并引入错误类比。

若某类任务确需不同指令，使用任务路由或按需加载；不急于拆成多Agent。路由器本身要测误命中、未命中和边界案例。上线先灰度，明确严重错误、成本、时延和回滚条件；模型、索引、工具和Prompt同时升级会使归因困难。

**验收：** 对旧版正确、新版错误的样本做首错误定位，并给出单一修复层；回归集保留正常样本与原坏例，避免只测试刚修的错误。

<a id="first-error"></a>
## 4. Bad case怎样形成能复现的闭环？

保存请求身份、组件版本、必要输入引用、节点顺序、调用身份、结果状态与最终断言。沿理解→计划/路由→检索→工具→状态合并→生成查找第一个偏差；后续多处失败可能只是传播结果。日志与Trace描述过程，不能直接证明原因。

用干预对照验证假设：注入正确证据、固定正确工具参数、回放已核实工具结果，观察任务是否恢复。按频率×严重性×可修复性排优先级，修复对应层，增加反例并验证没有新回归。用户没点赞不等于答错，用户满意也不证明事实正确。

Trace应记录受控引用、状态、耗时与版本，避免默认存全部敏感原文或模型私有思维链。决策摘要和可验证动作足以解释多数故障；必须访问真实样本时使用授权和保留期限。[OpenTelemetry敏感数据说明](https://opentelemetry.io/docs/security/handling-sensitive-data/)给出观测数据处理原则。

<a id="metrics"></a>
## 5. 最终成功以外，哪些过程指标值得看？

|层次|例子|容易误读之处|
|---|---|---|
|终态|任务成功率、支持证据的答案、正确产物|回复宣称成功不是环境终态|
|行动|工具选择/参数正确率、非法动作率|一次请求可能有多个动作，分母要清楚|
|推进|子目标完成率、首错误位置、无进展步数|推进不是批准发布部分结果|
|恢复|重试后恢复率、重复副作用、未知结果率|重试次数高可能掩盖基础故障|
|效率|模型/工具次数、总token、费用、墙钟时间|只有完成任务的费用会遗漏失败成本|
|体验|首事件时延、首有效内容时延、完整完成时延|一个“正在处理”事件不能冒充有用内容|
|稳定性|重复运行一致性、关键切片表现|总体均值会掩盖少数高风险任务|

进度指标可以帮助区分“差一步完成”与“一开始就走偏”；[AgentBoard](https://arxiv.org/abs/2401.13178)是过程分析研究例子。上述表格是本章的工程测量设计，不是统一标准。实际指标需声明任务/动作/请求单位、去重规则、分母、样本和缺失处理。

<a id="model-benchmarks"></a>
## 6. 综合模型基准各测什么？

|基准或框架|主要观察对象|使用边界与一手来源|
|---|---|---|
|MMLU、MMLU-Pro|多学科知识问答；Pro加强推理和干扰选项|不是工具执行评测。[MMLU](https://arxiv.org/abs/2009.03300)、[MMLU-Pro](https://arxiv.org/abs/2406.01574)|
|GPQA|专家编写的高难科学问题|“Google-proof”是设计与论文观察，不代表永远不可检索或无污染。[GPQA](https://arxiv.org/abs/2311.12022)|
|BIG-bench、BBH|广泛任务和其中困难的多步问题|历史基准需保留数据与提示配置，不用老数字代表新模型。[BIG-bench](https://arxiv.org/abs/2206.04615)、[BBH](https://arxiv.org/abs/2210.09261)|
|HELM、HELM Capabilities|统一框架中的不同场景与评分器|Capabilities包含MMLU-Pro、GPQA、IFEval、WildBench、Omni-MATH等；不是单一能力题库。[Stanford介绍](https://crfm.stanford.edu/2025/03/20/helm-capabilities.html)|
|LiveBench|带版本更新、客观答案的多类别任务|动态出题是抗污染策略，不是永远无污染证明。[LiveBench](https://arxiv.org/abs/2406.19314)|
|Chatbot Arena|匿名对战的人的偏好|用户/题目分布与风格影响结果，偏好排名不能替代事实或安全评测。[Arena论文](https://arxiv.org/abs/2403.04132)|
|MMMU、MMMU-Pro|多学科视觉理解与推理|区分真实视觉依赖与可仅凭文字答题的样本。[MMMU](https://arxiv.org/abs/2311.16502)、[MMMU-Pro](https://arxiv.org/abs/2409.02813)|

以上保留机制与用途，不搬运来源中的旧题数、旧胜率和“最流行”判断。核查时HELM[官方文档](https://crfm-helm.readthedocs.io/en/latest/)说明已于2026-06-01进入维护模式；它的历史方法仍可学习，选新实验框架需核对维护状况。记录数据release、split、模型快照、prompt、采样、工具权限、评分器和运行日期，禁止用不兼容设置直接横向比较。

<a id="agent-benchmarks"></a>
## 7. Agent基准的环境和任务怎样构造？

- [WebArena](https://arxiv.org/abs/2307.13854)与[VisualWebArena](https://arxiv.org/abs/2401.13649)：可重置的网站任务，后者强化视觉观察；检查功能结果而非只看文字回答。
- [WorkArena](https://arxiv.org/abs/2403.07718)：企业知识工作与业务软件操作；页面状态、工作流程和动作空间影响难度。
- [OSWorld](https://arxiv.org/abs/2404.07972)：真实操作系统、桌面和跨应用任务，使用任务初态与执行式评测。
- [GAIA](https://arxiv.org/abs/2311.12983)：需要推理、浏览、文件/多模态和工具组合的助理问题，不能统一描述为GUI终态测试。
- [SWE-bench](https://arxiv.org/abs/2310.06770)：给仓库与issue，产生补丁并在固定环境测试；通过可见测试不证明所有隐藏需求或安全条件。
- [τ-bench](https://arxiv.org/abs/2406.12045)：用户互动、领域API与业务规则，检查终态及重复运行可靠性。论文的pass^k关注多次均成功，与“k次里至少一次成功”的pass@k口径不同。

原创企业评测可借鉴“初态→可用动作→预算→终态判分→环境重置”。不能把有权限在sandbox完成的动作直接搬到真实用户账户。版本升级可能改变任务、浏览器或判分脚本，回归应固定环境；本章没有运行以上基准或报告榜单成绩。

<a id="online-audit"></a>
## 8. 无用户反馈时怎样抽检，怎样发现漂移？

保留随机样本来估计总体，同时对风险、高费用、长循环、未知结果、解析失败、低支持证据和新版本任务加大抽样。过采样后直接平均会改变总体口径：按原流量权重汇总或分别报告风险切片，不把审查队列误当真实流量。

抽检rubric包括目标达成、证据支持、权限、输出合同、必要确认、恢复及效率。审查者不知道版本更有利于减少期待偏差；模型判分辅助筛选，人审校准。线上告警区分输入分布变化、供应商变化、索引滞后、工具故障和模型质量；Trace按版本聚类，候选修复回到冻结回归集。

监控SLO、质量与业务结果：延迟P50/P95/P99、错误率与可用性不等于正确率；用户反馈与留存又不能代替授权检查。没有业务标签时明确是代理信号，保留人工验证计划。安全问题先限制影响面，版本回滚不能撤销已经外传的数据或执行的订单。

<a id="model-routing"></a>
## 9. 子Agent该选哪个模型？

这是原创设计答案，不给每个角色固定品牌或参数量。先列任务合同：上下文/模态、工具schema、精度、时延、费用、部署与数据接收边界。提取、路由、规划、审查、视觉读取可能有不同需求，但更大模型不必在每一类任务净收益更高。

在同一任务集、工具结果、总预算和验收门槛下比较候选，记录失败成本、费用与完整时延。小模型在低风险分类上够用时可用；复杂步骤升级需有可测触发信号和次数上限。不要只靠模型自报置信度路由，采用可验证缺证据、结构失败或规则冲突等信号，再校准阈值。

模型适配器验证拒绝、截断、调用ID、并发工具、流式片段、用量与错误语义。统一HTTP形状不等于这些合同一致。配置固定精确provider/model/version，供应商价格、可用型号、上下文默认值在部署时查官方资料；本章没有真实API互通测试。

<a id="context-ablation"></a>
## 10. 为何保留20轮，而不是10轮或30轮？

这是原创补全；不把20轮当来源已经证明的答案。按token与信息结构预算，而不是只按轮数：固定指令、当前目标、权威状态、工具结果、检索证据、必要近期交互分开管理。输入窗口扣除预计输出、工具响应和修复余量后才是可用预算。

对最近10/20/30轮、结构摘要、检索历史等策略做消融。任务包含跨轮指代、否定条件、旧偏好被更正、未完成工具调用和跨主题实体。测约束保留率、任务成功、错误召回、重复执行、token和时延。摘要触发可按预算、阶段、主题变化联合设计，保护完整工具调用/结果单元；摘要不能代替可回查原始记录。[A20–A23](03-memory-and-context.md#a20)已有基础与验收，本节补具体对照设计。

## 自测

1. 同一新Prompt提高总体成功率，却降低付款确认切片：可以上线吗？为什么？
2. 两版费用都只统计成功任务，失败率不同：怎样重新计算一次请求及每个成功任务的成本？
3. 一个基准以最终答案评分，另一个以数据库终态评分：两者各能检出什么，漏掉什么？
4. 无反馈抽样只查超时请求：能否估计总体正确率？需补哪些样本与权重？
5. 模型升级同时更换索引和工具默认limit：怎样拆分实验获得可解释的归因？
