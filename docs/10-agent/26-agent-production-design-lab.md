# Agent生产设计：从模块图到可验证契约

[返回Agent目录](README.md) · [验证范围](../../coverage/AGENT_LABS_VALIDATION.md)

先修[A01–A08](01-agent-loop-tools-and-state.md)、[A19–A23](03-memory-and-context.md)、[A24–A30](04-streaming-and-reliable-execution.md)。本章练习模块划分、通信、规划与信息治理，把结构图转化为可验证的设计契约。核查日期2026-10-10；方案尚未实现或上线。

<a id="module-contracts"></a>
## 1. 一个完整系统有哪些职责，模块间如何通信？

输入层解析目标和必需参数；上下文层组装证据；模型适配器处理请求/流式/错误；规划器提出候选步骤；工具注册表描述能力；执行器检查权限和预算再调用；状态存储保存权威任务；验证器检查结果；观测层记录必要诊断。它们是职责，可以放在单进程，也可以按故障域与部署需求拆服务，不必每项都做一个Agent。

消息契约至少说明task_id、call_id、parent_call_id、schema_version、输入/产物版本、deadline、状态与有界结果引用。共享状态需字段所有权和合并规则：集合按身份去重、计数按确定的语义累积，不能让两个分支覆盖同一全局字典。队列解耦能改善削峰和独立部署，却增加重复投递、延迟、一致性与运行成本。

设计评审用一条完整轨迹验证接口：用户目标→授权资料→候选计划→工具执行→结果核查→阶段状态→最终产物。逐层回答谁决定、谁执行、谁保存、谁验证、失败怎样退出。不要用“LLM+Tool”替代这些契约。

多模态可选联合理解模型，也可组合OCR、语音识别、图像检索等工具管线。前者直接处理相应模态，后者把观察转换成有来源与置信信息的中间产物；两者都要核对转写、识别与实际动作。调用视觉模型不自动产生执行能力，文本转写也可能丢掉版式、语气或图像条件；按任务测这些损失。

<a id="planning-strategies"></a>
## 2. 逐步推导、ReAct、树搜索、Plan–Execute与反思如何选择？

|模式|信息与控制特点|主要代价/故障|
|---|---|---|
|逐步推导|在已有输入上组织推理步骤|没有外部动作就得不到新事实；不能把文字当执行|
|ReAct|行动后读取环境观察，再决定下一步|工具往返与错误传播，需要有界循环|
|树状搜索|生成、评价、剪枝和回溯多个候选|评价器可能选错，分支数增加费用|
|Plan–Execute|显式分解依赖后执行，可局部重规划|初始计划过时、遗漏依赖或把问题拆错|
|反思重试|由失败证据形成候选经验，改善下一次|模型解释可能错，经验可能过拟合或污染记忆|
|高层控制器|根据状态动态路由、调用子任务并合并|控制器瓶颈、调度错误与协调开销|

这是一组比较维度，不是唯一分类或可靠性排名。[Tree of Thoughts](https://arxiv.org/abs/2305.10601)研究分支搜索，[ReWOO](https://arxiv.org/abs/2305.18323)研究规划与工具观察解耦，[Reflexion](https://arxiv.org/abs/2303.11366)研究反馈和语言记忆。保留方法差别，不照搬论文最佳结果到项目。

依赖明确的阶段计划可要求DAG并做拓扑检查；Agent控制循环可以有环，但环必须有停止/取消/预算。两者并不矛盾。设计中还可以使用路由Skills、子任务监督、任务交接、生成后评审和有界搜索。按任务不确定性、反馈速度和验证能力选最简单可用结构，而非按Agent数量选架构。

<a id="multi-agent-contract"></a>
## 3. 单体不可靠，拆成多个就会改善吗？

先做单Agent基线，固定输入、工具能力、总预算和验收指标。并行独立调研、上下文隔离或不同专业能力可能获益；强依赖步骤、共享修改和频繁通信可能更慢。提示过长先尝试按需加载、上下文预算与工具筛选，再评估拆分。

能力路由回答“谁能做”，语义路由回答“这次需要什么”，负载均衡回答“由哪台可用执行器做”，不能混为同一分类器。中心协调便于一致状态和裁决，亦有瓶颈；去中心协商减少单点但提高冲突、一致性和终止难度。子任务权限取自当前授权范围，角色名称不能扩大它。

交付契约包含结论、受控证据引用、产物、假设、未解决问题、执行检查和覆盖缺口。不要传全部日志、秘密或私有思维链。主控核对结构和证据，再作独立验证；多个同源模型赞同不证明事实正确。

**验收：** 一个必要子任务失败、一个可选子任务失败、两分支结论矛盾、两分支修改同一资源。结果应按契约分别阻止依赖发布、明确部分覆盖、保留争议证据或拒绝冲突写入。

<a id="permission-boundary"></a>
## 4. 权限、注入、参数与租户隔离放在哪里？

认证确认调用者，授权确认该调用者此刻能对该资源做该动作；Schema检查结构，业务校验检查值与实际对象。模型返回合法user_id不意味着那就是认证身份。检索先按身份/资源过滤，执行入口再授权；缓存和索引也按租户、权限版本及数据版本隔离。

例如员工档案、财务报表和公共技术文档可有不同可见范围，但角色名称与等值判断只是示例，不能直接作为通用ACL。策略应默认拒绝，处理资源所有者、属性、当前角色与撤权；已排队调用在真正执行时再次检查。高影响动作还需绑定具体参数及版本的批准。

注入可能来自用户输入、检索文档、网页、工具返回、图片文本和日志。把外来指令标成数据、限制工具与网络能力、隔离执行环境并检查产物；“不要理会恶意指令”只是辅助。防护测试应验证运行时没有越权动作，而不是只看模型说了拒绝。[OWASP提示注入](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)、[授权检查](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

<a id="tool-contracts"></a>
## 5. 工具说明、失败和幻觉怎样分层控制？

说明写清何时用、何时不用、必需输入、参数范围、返回含义、常见错误和副作用。工具名称稳定、职责清楚；结果有界，保留来源或业务操作ID。类型和自然语言描述不能替代资源级授权。

调用前检查参数/权限/预算；调用中有deadline、并发限额和取消策略；调用后核对目标、版本与真实产物。暂时错误才考虑重试，未知副作用先查状态，不以“超时”推断未执行。对模型事实主张核对证据，对模型动作主张核对环境状态。

置信度门控、评审、检查点和熔断各解决不同问题：自报置信度未经校准不能当概率，模型评审可能共享错误，检查点不能撤销外部动作。高可用也需要服务容量、依赖隔离、队列背压、告警与故障演练，不能只靠工具retry。基础契约详见[A29–A30](04-streaming-and-reliable-execution.md#a29)。

<a id="memory-write-path"></a>
## 6. 短期内容怎样变成长期记忆？

当前工具调用与结果保留关联身份、状态和必要摘要，避免重复执行或把旧错误当新观察。对长期候选依次检查是否有未来价值、来源可信、授权保存、作用范围与有效期，再结构化去重和版本化。稳定偏好、事件经验与领域知识有不同更新机制；聊天里每句话都保存会制造噪声和冲突。

显式表达、重复行为和模型推断分开标记。当前用户要求“这次用英语”可以只作任务覆盖，不应直接改掉全局中文偏好；明确说“以后都改英语”则按真实指示更新。冲突比较来源、时间和适用范围，无法决定时澄清；不能按向量相似度自动挑真相。

|比较维度|工作/短期记忆|持久/长期记忆|
|---|---|---|
|职责|当前目标、计划、工具状态|跨任务事实、偏好和验证经验|
|存储|内存、任务表、缓存或检查点|关系/文档/对象存储及可选索引|
|保留|依任务/会话生命周期|依用途、授权和有效期|
|粒度|近期事件与执行细节|经过治理的事实/经验单元|
|读取|当前状态直接加载|先作用域/权限过滤，再检索|
|更新|随着每步结果推进|提炼、核验、更正、版本和删除|
|失效|任务结束、状态被替换|过期、来源撤回、冲突或用户删除|

存储介质不定义语义：Redis可保存长期数据，数据库也可保存短期状态，耐久性取决于具体配置。向量和图是检索表示，不是唯一真值。基本读写与删除见[A19–A23](03-memory-and-context.md)。

<a id="context-isolation"></a>
## 7. 上下文污染和改写丢槽怎样发现？

为用户、任务、话题和分支建立明确作用域。共享只包含必要字段及来源/版本；摘要、推断与已验证事实分开。并发写使用版本检查和字段所有权；旧分支结果不覆盖新用户更正。结构化JSON减少格式歧义，字段值仍可能错。

改写前后核对实体、时间、地点、版本、否定、数量和动作范围，保留原查询与改写版本。用带关键槽位的配对样本、回放与线上用户纠正信号测丢槽；精确ID或已清晰的查询可跳过改写。阶段摘要保存目标、限制、证据、未知与剩余事项，不能只保存正面结论。

长任务恢复从权威状态与可回查产物重建必要上下文，而非把所有旧消息重新塞入窗口。跨话题相关的稳定偏好可复用，不相关的旧任务数据不注入。进一步实验见[上下文消融](25-agent-evaluation-and-routing.md#context-ablation)。

<a id="sdk-and-performance"></a>
## 8. SDK、Token与性能优化怎样讲边界？

SDK通常包装认证、请求、流式、消息结构、错误和用量；应用仍决定业务状态、工具执行、授权与验证。用假响应契约测试拒绝、截断、重复/倒序工具结果、取消和错误，不能用“换了SDK”证明正确性。

Token数由目标tokenizer与输入共同决定，中文、字符和字节不能互换。预留输出及工具响应预算，测实际组装后的输入。稳定前缀缓存可能节省重复prefill工作或费用，并不删除上下文，也不保证decode同样加速。按“减少无效调用→缩小无关输入→安全缓存→并行独立步骤→路由模型”逐项测净收益。

区分总完成时延、首事件/首有效内容、吞吐与尾延迟。并行不能绕过依赖，缓存不能跨租户或继续使用撤权结果。没有实际压测数据时，只报告假设与验证设计。推理机制沿用[采样与服务边界](24-inference-and-serving-boundaries.md)。

<a id="application-map"></a>
## 9. 企业项目该怎样选练习场景？

客服以规则证据、升级和真实工单终态验收；分析以数据权限、口径与可复现查询验收；研究以来源覆盖、结论支持和缺口说明验收；文档处理以格式、内容完整和产物版本验收。模糊目标先澄清影响验收的关键条件，不能用“智能”掩盖需求缺失。

比较一次回答、固定流程、工具循环、规划执行、协作与人工审批，列出每一种失败出口和成本。面试里的“进程”先确认指业务过程还是OS进程：前者是控制流，后者是地址空间/调度等运行载体，二者不能用同一套名词作答。本章不把业务流程说明当操作系统知识的替代。

项目表达按事实分层：已实现机制、实际运行证据、尚未验证的设计。说明为什么拆、失败如何处理、稳定性怎样测；不要把本章的例子写成自己的上线经验。

<a id="graph-pipeline"></a>
## 10. 知识图谱怎样构造，何时值得付出维护成本？

先定义业务问题、实体/关系Schema、来源与质量要求。多源材料经解析与有界抽取，形成带原文位置、时间、置信和权限的候选；做实体消歧、别名归一、关系方向与否定/条件校验，再融合入图。不能把模型抽出的三元组直接当业务真值，关系看似连接成功也可能来源不支持。

持久层保留稳定实体身份、来源引用、有效版本与变更状态；数据更新可能撤回旧关系，删除与权限变化要同步到图及派生检索。抽取错误、错误合并和过时关系分别测量，审查重点覆盖高影响关系；图数据库是否适合还取决于更新、查询、容量和团队维护能力。

精确关系、多跳路径或全局连接需求可能受益；语义相似查找仍适合向量/词法等信号。按单跳、多跳、改写和无答案查询分桶，对向量、图与混合做同权限、同预算消融。基础ANN、证据和图谱收益边界见[RAG索引章节](17-rag-indexes-and-evidence.md#dynamic-top-k-and-graph-ablation)。这里的管线是原创工程设计，未运行实体抽取、图数据库或图谱评测。
