### A19 短期记忆、长期记忆、RAG 的关系是什么？

**优先级：P0** 

**知识点详解** 
- 短期记忆是当前线程或任务需要的状态，如最近消息、当前计划和工具结果；长期记忆跨会话保留事实、偏好或经验。
- RAG 是检索外部信息并辅助生成的方法。长期记忆可以用 RAG 检索，但长期记忆管理还涉及写入、更新、冲突、删除和权限。
- 聊天全文只是原始日志，不自动成为可靠记忆。长期记录要区分用户明确说过的事实与模型推断，并保留来源和时间。

**具体例子** ：当前调研进度属于任务状态；用户长期偏好简洁表达属于偏好记忆；一本技术手册属于知识库。

**30 秒答题主线** ：我按生命周期和用途区分记忆。短期支撑当前任务，长期跨会话复用；RAG 是读取这些知识的一种手段。写入长期记忆前要抽取、去重并记录来源，不能把每次聊天都永久塞进 prompt。

**追问** ：长期记忆必须用向量库吗？用户更正旧偏好如何处理？

#### 参考答案

长期记忆可以用关系表、键值存储或文档存储，向量索引只是一种检索方式。更正偏好要保留更新来源/时间，使新值成为有效记录，并让旧版本退出默认召回。

**验收点：** 更正一个偏好后再检索，当前有效值及其来源可见，旧值不会被默认当成当前偏好。

**常见错误** ：只用“Redis 短期、数据库长期”解释语义；把存储介质当作记忆类型的定义。

**来源** ：[AG-T19](../../sources/catalog.md#ag-t19)。

### A20 上下文太长怎么压缩？怎样验证没压坏？

**优先级：P0** 

**知识点详解** 
- 先删重复和低价值工具原文，再摘要旧对话；保留目标、约束、已完成结果、失败原因、未决事项和证据引用。
- 全量历史可保存在受控存储里，模型只读摘要和必要片段。摘要是可丢失信息的派生物，不应成为唯一原始记录。
- 验证不能只检查变短了：应建立压缩前后的事实/约束核对题，检查禁止事项是否丢失、任务是否重复、工具调用与结果是否仍对应。

**具体例子** ：可以把200行搜索结果缩成3条证据及文档 ID，但不能丢掉“只分析、不修改文件”的任务边界。

**30 秒答题主线** ：我先减少低价值内容，再做有结构的摘要，并保留可回查原文的引用。压缩效果用关键事实、约束和任务连续性来测，而不是仅看 token 降幅；损失不可接受时回读原始片段。

**追问** ：为什么工具调用与结果不能随意拆开？何时触发压缩？

#### 参考答案

工具调用与结果是有关联身份和顺序的协议单元；任意拆开可能让结果失去对应调用或破坏消息合同。预留模型输出和工具响应预算，按 token 阈值提前压缩，再用未压缩对照检查约束、未完成任务和引用是否保留。

**验收点：** 压缩包含未完成工具调用的记录；协议关联、剩余任务和关键限制仍能恢复。

**常见错误** ：按字符串长度直接截掉最早消息；让摘要覆盖原文且不留来源。

**来源** ：[AG-T20](../../sources/catalog.md#ag-t20)。

### A21 “三层记忆”应该怎样解释，才能不是背架构词？

**优先级：P1** 

**知识点详解** 
- 分层是把快速、小容量的当前上下文与较慢、大容量的外部存储分开。具体分三层还是四层属于系统设计，不是统一标准。
- 一种教学划分是：当前工作区、任务摘要/检查点、跨任务知识。每层必须说明保存什么、何时写、何时读、失效和容量限制。
- 真正难点是数据迁移与检索：把内容移到外部后，要能找到它；摘要无法还原的细节需要凭 ID 回读原文。

**具体例子** ：近期工具观察放当前上下文；已验证的阶段结果写任务摘要；可复用技术结论保存带来源的笔记。

**30 秒答题主线** ：分层记忆的目的，是在有限上下文中保持连续性。我会逐层解释读写策略、容量和来源，而不是只画三层图。原始记录和压缩结果分开保存，需要细节时再加载。

**追问** ：外部记录找不到怎么办？层间冲突以哪个为准？

#### 参考答案

外部记录找不到时保留可验证的索引身份并降级为未知，不能从摘要补造原文。冲突按记录权威性、用户显式更正、时间和有效版本解决；层级高低不是事实真伪的自动裁决器。

**验收点：** 使摘要指向一个已不存在的记录；输出未知或缺证据，不能补造引文。

**常见错误** ：说三层记忆是所有 Agent 的标准；把磁盘容量和模型上下文容量混为一谈。

**来源** ：[AG-T21](../../sources/catalog.md#ag-t21)；三层示例为原创教学设计，非论文固定结构。

### A22 长期记忆不断增长、相互矛盾或过期怎么办？

**优先级：P1** 

**知识点详解** 
- 对每条记忆附加主体、类型、来源、创建/更新时间、有效期和状态；同一事实可以更新版本，而不是无限追加互相冲突的句子。
- 读之前按用户、项目和权限过滤，再按相关性取有限结果。保存量可以很大，但每轮注入量应有预算。
- 事实冲突先比较明确更正、来源可靠性和时效；无法判断时保留冲突并澄清。删除应覆盖原存储及其索引派生物。

**具体例子** ：用户先说“周二可用”，后说“这周二改成不可用”；旧记录标为失效，不能因相似度更高又召回旧安排。

**30 秒答题主线** ：我把长期记忆当有生命周期的数据。写入时去重和版本化，读取时先隔离再检索，过期和更正要进入清理流程。冲突不能交给模型随意挑一句，必要时向用户确认。

**追问** ：删除数据库记录后，向量索引何时删除？如何测试跨用户泄漏？

#### 参考答案

主数据删除后索引可能异步收敛；在收敛前应有 tombstone/版本校验或读时过滤，且备份与缓存的删除范围另行说明。跨用户测试包含相同文本/ID、猜测记录身份和恶意过滤条件，断言所有召回、日志和缓存均遵守租户边界。

**验收点：** 两个租户写入相同文本和相同外部ID，再删除其中一个；检索、缓存和日志均不跨租户。

**常见错误** ：只按相似度读记忆；声称做了 TTL 就不会出现过期或冲突。

**来源** ：[AG-T22](../../sources/catalog.md#ag-t22)、[AG-T35](../../sources/catalog.md#ag-t35)；生命周期细节为工程设计建议。

### A23 模型支持长上下文，还需要检索和压缩吗？

**优先级：P1** 

**知识点详解** 
- 窗口容量表示能接收多少输入，不等于每条输入都能同样有效地使用。原始长上下文研究观察到相关内容的位置会影响结果。
- 结论不能机械套到所有新模型；实际应测试所用模型、文档长度和任务类型。检索仍能控制无关内容、费用和延迟。
- 长上下文与检索可以组合：先找到相关文档，再给足该文档必要的上下文，避免检索碎片和全量堆砌两种极端。

**具体例子** ：把所有历史日志放进去可能掩盖唯一的失败栈；先筛出相关任务，再按时间提供关键片段更便于定位。

**30 秒答题主线** ：窗口更长缓解容量限制，但不保证有效利用。是否全量输入要通过质量、时间和成本对照。我的目标是让模型看到足够且相关的证据，而不是尽量填满窗口。

**追问** ：如何构造位置敏感测试？全量输入在什么情况下反而更合适？

#### 参考答案

将同一关键证据放在开头、中间、末尾，固定任务并重复试验，观察答案支持度与延迟。全量输入适合文档规模可控且任务需要全局比较的场景，但仍需核对成本、模型长度边界和证据定位。

**验收点：** 固定同一问题，在不同位置放关键证据并重复采样，报告支持度而不是一次成功截图。

**常见错误** ：拿旧论文断言所有当前模型一定相同；把 token 越多等同于答案越好。

**来源** ：[AG-T23](../../sources/catalog.md#ag-t23)。
