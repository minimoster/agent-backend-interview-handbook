### G27 [P0] HTTP Client 为什么要复用？响应 Body 怎么处理？

**知识点详解**

HTTP 请求不只是发字符串，还涉及连接建立、TLS、连接复用、等待响应、读取响应体。Go 的 Client 与 Transport 可并发使用，通常应复用，避免每个请求重复建立连接和 TLS 握手。Transport 管理连接资源，也需要合理配置连接数和空闲连接参数。

拿到响应后要关闭 Body。对正常且大小受控的响应，读到 EOF 并关闭有助于连接复用，尤其 HTTP/1.x；不能为了复用无上限地读恶意或巨大响应。遇到异常响应也不能忘记处理 Body。请求成功返回 response 不等于业务状态码一定成功。

**具体例子** ：并行抓网页用同一受控 Client，但每个请求带自己的 context。限制下载大小，处理 429/5xx，完成后关闭 Body；不能把默认无总超时的客户端直接当成所有场景都安全的默认配置。

**面试答法** ：复用 Client/Transport、设超时和连接边界、关闭响应体、验证状态与大小，再说明流式读取需要不同超时策略。

**常见追问** ：每次 new Client 一定不能复用连接吗？若仍共用同一 Transport，连接可能复用；关键是 Transport 的生命周期，不只看 Client 变量。

**误区** ：err 为 nil 就代表 HTTP 200；只 defer Close 就保证所有情况下连接可复用。

### G28 [P0] HTTP 服务端和客户端各有哪些超时？

**知识点详解**

客户端总超时与连接阶段、TLS 握手、响应头等待等超时解决不同问题。服务端则要考虑读请求头、读请求体、写响应及空闲 keep-alive。只给业务逻辑套一个 context，不一定覆盖慢速发送请求头的客户端；只设置网络写截止，也不等于业务计算及时停止。

流式接口需特别注意：WriteTimeout 不是每个 token 自动刷新的“空闲超时”。需要根据协议、代理和 ResponseController 能力设计写截止与刷新策略，并设置任务上限、心跳和断连清理。不同 HTTP 版本和服务器包装层可能影响行为，必须测试真实链路。

**具体例子** ：普通查询 5 秒截止可能合理，持续 2 分钟生成报告若照搬这一设置就会中断。可把普通 API 和流式路由分开配置，并模拟慢读者、代理空闲断连、模型首 token 很慢等情况。

**面试答法** ：把超时分为入口防护、下游调用、业务预算和流式空闲检测，解释每一个在防什么。

**常见追问** ：超时返回后 handler 的 G 会立即退出吗？未必，业务必须响应取消并清理。为什么只设置 ReadTimeout 有时不合适？大请求体与慢请求头的需求不同。

**误区** ：所有 timeout 都是同一计时器；一律把全部超时调大解决失败。

### G29 [P0] SSE 为什么适合大模型输出？与 WebSocket 有何区别？

**知识点详解**

SSE 是服务器沿 HTTP 响应持续发送事件的文本协议，适合服务端单向推送。浏览器 EventSource 会按事件格式解析，并具备重连行为。事件以空行分隔，常见字段有 data、event、id；内容使用 UTF-8，响应类型是 text/event-stream。

WebSocket 在连接升级后提供双向消息通道，更适合双方频繁低延迟交互。选择取决于方向、消息模式、鉴权、代理兼容与运维复杂度，而不是“WebSocket 一定更高级”。SSE 的底层是否 HTTP/1.1 或 HTTP/2 不改变事件格式的基本职责。

**具体例子**

```text
event: token
id: 12
data: {"text":"你好"}

```

末尾空行很重要。用户发起任务可用普通 POST，后续事件流承载增量结果；原生 EventSource 的使用约束与 fetch 流式读取方式要区分。

**面试答法** ：模型输出通常单向，SSE 足够简单；需要连续双向语音或高频交互时再评估 WebSocket。

**常见追问** ：SSE 自动保证断点续传吗？不保证，id/Last-Event-ID 只是机制，服务端还要保存、重放并定义过期策略。

**误区** ：任意把 JSON 分段 Write 就符合 SSE；SSE 必须一个 token 对应一个网络包。

### G30 [P0] Go 写 SSE 时，如何处理 Flush、慢客户端和用户断连？

**知识点详解**

Write 可能只写到用户态或中间缓冲区，需要合适的 Flush 让事件及时向下发送；但应用调用 Flush 不等于代理立刻转发，更不等于用户已经消费。中间件若包装 ResponseWriter，还要保留流式能力。

慢客户端会让写入阻塞或内部缓冲增长，这叫背压：下游处理速度反过来限制上游。设计时限制每连接待发送事件量，明确能否合并 token、拒绝慢读者或终止任务；不能给每个用户建无限队列。断连通过请求 context、写错误等触发清理，并取消不再需要的模型请求。

**具体例子** ：模型每秒产 100 片，浏览器只消费 10 片，持续一分钟会积累大量片段。可按很短时间窗口合并文本后推送，同时保留有界缓冲与写截止；窗口大小是压测选择，不是协议常数。

**面试答法** ：我会说清入口请求、模型流、事件缓冲和网络写入四段取消链，再展示慢读者与断连测试。

**常见追问** ：已发送 HTTP 200 后失败怎么报错？用约定的错误事件或关闭流，不能当成尚未写响应那样重新改 HTTP 状态码。

**误区** ：Flush 成功代表用户已看到；只在正常结尾关闭模型流；广播时一个慢用户拖住全部用户。

### G31 [P1] gRPC 的价值、deadline 与流控是什么？

**知识点详解**

gRPC 用服务接口描述和生成代码组织远程调用，可支持一元请求、服务端流、客户端流和双向流。它适合内部服务的结构化通信，但不是用了它就自动解决超时、幂等或跨服务事务。

deadline 防止客户端无限等待，服务端工作也要响应取消。流控避免发送端无限压过接收端；发送 API 返回可能只表示消息交给框架，不代表对方业务已处理。应用层仍应控制消息大小、队列长度及每个连接的任务数。

**具体例子** ：Agent 服务调用独立的检索服务，用 protobuf 描述查询与结果；调用继承入口剩余时间。流式检索结果到达后逐步汇总，但消费者停止时须取消流，而不是让服务端继续遍历全部文档。

**面试答法** ：我会从接口契约和调用模式解释收益，再讲 deadline、状态码、流控、可观测性这些仍需配置的工程项。

**常见追问** ：deadline 到了可确认服务端没写数据库吗？不能。双向流两边都只写不读有什么风险？流控窗口耗尽时可能彼此等待。

**误区** ：gRPC 自带合理默认 deadline；Send 返回就是对方业务确认；内部 RPC 不需要鉴权。

### G32 [P0] 下游失败要不要重试？怎样避免重复执行和雪崩？

**知识点详解**

重试是在不确定结果下再次尝试，会增加下游压力。先区分可重试的瞬时失败、不可重试的参数或权限错误，以及“请求可能成功但响应丢失”。写操作要有幂等设计，例如调用方携带稳定操作 ID，服务端把去重状态和业务结果放在一致的提交边界中。

重试需受总 deadline、次数、退避和抖动限制。指数退避逐渐拉长等待，抖动避免大量客户端同一时刻再次冲击。多层各重试三次会放大请求量，因此要统一重试负责层，监控原始请求量与实际尝试次数。

**具体例子** ：模型请求超时后重试可能再计一次费用；工具执行“发送邮件”超时后重试可能发两封。必须依据供应商幂等能力和任务执行记录判断，不按 HTTP 方法名直接推断整个工具流程幂等。

**面试答法** ：先判断是否安全重试，再谈退避、预算、重试层级与结果去重；已经输出部分文本的流式响应还要单独定义恢复策略。

**常见追问** ：为什么不要每层都重试？次数乘法放大负载。429 怎么处理？尊重供应商提示及本方预算，避免无间隔循环。

**误区** ：所有 5xx 都必然可以安全重放写操作；设置重试次数就算有容错。

### G33 [P0] 限流与并发限制的区别？令牌桶如何工作？

**知识点详解**

速率限制关注单位时间允许多少请求；并发限制关注此刻有多少在途请求。下游耗时上升时，即使 QPS 不变，在途量也会增加，所以二者常一起用。令牌桶按一定速度补令牌，每次请求消耗令牌，桶容量决定允许的短时突发量。

`x/time/rate` 的 Allow 可立即判断，Wait 会等待令牌或 context 取消，Reserve 表达未来可执行时刻。排队不是免费的，仍占用连接、内存和请求时长。单进程 limiter 不等于整个集群的总额度，扩容后要考虑每实例预算与全局协调。

**具体例子** ：假设供应商限制 60 次/分钟，本地设平均每秒 1 次、突发 3 次，还要限制最多 5 个并发；这些是假设配置，真实需看供应商口径与是否按 token 计费。多副本不能每台都随意拿满同一全局额度。

**面试答法** ：先明确限制维度、作用范围和超限策略，再用速率与并发两层保护慢下游。

**常见追问** ：为什么队列长度必须有上限？否则高峰只是从错误率转成内存上涨和超时堆积。按用户限流还是全局？常需要两者，防单用户占满资源。

**误区** ：并发设为 10 就代表每秒 10 次；令牌桶能精确保证任何自然分钟窗口都不超限。

### G34 [P0] Go HTTP 服务如何优雅退出？

**知识点详解**

优雅退出是有顺序且有截止时间的收尾：先让新流量停止进入，再等待在途工作，停止后台消费者，最后关闭依赖并退出。可用 signal.NotifyContext 等接收终止信号；HTTP Server.Shutdown 会停止接收新连接并等待符合其管理范围的活动请求完成。

Shutdown 不等于处理所有后台任务，也不会替你管理全部被 hijack 的连接。SSE 或持续任务可能长时间不结束，需定义最大等待、主动通知或取消。退出 context 应使用新的、带上限的 context，不要直接复用刚被信号取消的那个，否则 Shutdown 一开始就失败。

**具体例子** ：收到 SIGTERM 后先标记实例不就绪，给负载均衡传播时间；随后等待短请求、通知长流结束，再停止 worker 和关数据库。若宽限期耗尽，按部署策略强制结束并记录未完成任务以便恢复。

**面试答法** ：讲清接收流量、在途任务、后台 G、外部连接四类资源的所有者和关闭次序，并证明 main 没有在 Shutdown 完成前提前返回。

**常见追问** ：SIGKILL 能优雅处理吗？不能。为什么先关 DB 不合适？在途请求可能还需要它。

**误区** ：ListenAndServe 返回后 main 直接结束；只加一个 defer Close 就完成优雅退出。

### G35 [P1] Go HTTP 中间件怎样组织？Agent 接口额外防什么？

**知识点详解**

中间件是包装 handler 的函数，用于统一处理请求标识、日志、鉴权、限流和异常恢复。顺序很重要：要确定鉴权发生在昂贵业务前，错误响应能被观测，流式接口的包装器仍支持 Flush 等必要能力。

输入防护包括限制请求体大小、校验 JSON、限制模型输入与工具参数、避免把密钥或完整敏感 prompt 直接写日志。对需要访问用户 URL 的 Agent，更应把 URL 当不可信输入：按业务允许范围校验，并防止访问内网、元数据等不该触达的目的地；仅检查原始字符串不足以覆盖 DNS 与重定向变化。

**具体例子** ：用户提交 URL，服务在鉴权、任务配额和目标地址校验后才抓取；重定向每一跳也要检查。这个设计建议不代表任一具体项目已经具备这些能力，需实际核代码和测试。

**面试答法** ：先画请求经过的处理顺序，再说明入口资源限制、工具执行边界和安全日志；不要只列 Gin 中间件名字。

**常见追问** ：panic 恢复后为什么可能改不了状态码？响应已经发送。为什么限流不能只靠前端？攻击者可绕过前端。

**误区** ：有鉴权就没有 SSRF；HTTP 状态正常代表整段 SSE 一定成功。
