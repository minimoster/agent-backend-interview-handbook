# 面试准备：真实贡献、决策与证据

[返回面试准备目录](README.md) · [验证范围](../../coverage/AGENT_LABS_VALIDATION.md)


这是一份原创准备框架。它提供问题清单和回答结构，不替任何人编造经历、成绩、薪资或职业立场。没有亲自实施的工作可解释原理或方案，但要明确说“设计/阅读过”，不能借团队共同成果声称个人实现。尚未实现、尚未测量和不确定的部分同样值得讲清。

<a id="evidence-portfolio"></a>
## 1. 自我介绍、成就项目、岗位匹配和团队角色

**准备问题：** 你是谁、做过什么？哪个项目最能体现能力？你与岗位为什么匹配？项目中负责什么角色，亲自解决了什么？

建立一页证据表：背景/目标、个人责任、关键决策、具体产物、验证方法、结果与未覆盖范围。把团队职责与个人职责分开；证据可以是自己的设计、代码、测试、故障排查或经授权可展示的产物，不能泄露原公司的私有日志、客户数据或代码。

自我介绍先用一两句话说明方向，再选择一项最贴近岗位的真实工作，最后说明寻找机会的目标。后端能力可连接服务设计、数据库、性能、稳定性与故障处理；Agent能力可连接工具合同、检索、上下文、状态恢复与评测。没有生产上线证据时，说清是课程练习、原型或设计验证。

**填答结构：** “我负责[明确范围]。为解决[业务问题]比较了[候选方案]，选择[决策]。产物是[可核查项]，用[验证方法]观察到[实际结果]，仍未验证[边界]。”没有数据就删去结果数字，保留可复查证据与下一步。

<a id="motivation-and-fit"></a>
## 2. 跳槽、公司选择、机会范围与优先级

**准备问题：** 为什么考虑变化？为什么这家公司？还在看哪些方向？择业优先级是什么？方向调整能接受到哪里？3–5年想积累什么？

动机从真实匹配解释：希望承担的业务、技术问题、职责和成长，与当前情况有什么差异。避免情绪化指责，也不要套用与自己无关的“更大平台”。公司理由先核验公开业务、岗位描述和团队需求，再连接自己的证据；不以品牌名气替代岗位判断。

把筛选标准排序，并准备一个取舍例子：业务方向、责任范围、团队协作、成长、工作方式和完整报酬等。对合理方向变化说明可以接受的范围与希望保持的核心积累，不作无限承诺。中期规划用能力与责任目标表达，不把职位晋升或市场发展当必然结果。

**填答结构：** “[岗位的具体任务]与我希望深入的[方向]相连；过去的[证据]能够帮助我起步。仍想了解[真实未知]，以确认职责与成长的匹配。”

<a id="backend-to-ai"></a>
## 3. 从后端到AI、平台/应用/算法的取舍

**准备问题：** 为什么转向Agent/AI？偏平台、应用还是算法协同？为什么不是纯算法岗？怎样看方向前景？

新写的回答应连接实际兴趣与可迁移能力：可靠接口、数据治理、异步任务和观测怎样支撑模型应用；哪些模型/算法问题仍是能力缺口。平台偏重共用运行能力，应用偏重业务闭环，算法偏重模型与数据实验，实际岗位可能组合这些职责，不能只按名称判断。

对未来讨论明确假设和不确定性：目前哪些任务可验证、在哪些权限或数据限制下有价值、什么证据会改变自己的判断。说明学习路径和已完成的练习，避免“AI必然替代某职业”或“几年必到AGI”式预测。没有真实转型经历时，表达目标与准备，不编造已经成功的路径。

<a id="collaboration-and-pressure"></a>
## 4. 协作、分歧、压力、挫折和非技术复盘

**准备问题：** 与产品/算法/前端如何合作？与同事有分歧怎么办？压力和重大挫折怎样处理？项目有哪些非技术困难？

选一个真实事件，按目标→约束→分歧→自己的行动→结果→复盘讲述。说明怎样澄清验收、拆解风险、比较方案、同步影响和推进决定，而不是只说“积极沟通”。技术分歧以数据、可逆实验和共同目标作依据；意见不同不等于对方能力不足。

压力处理说明优先级和风险：必须先保证什么，哪些范围可协商，什么需要及时升级。挫折要包括自己的责任及改变了什么，不把所有问题归咎外部。阶段性高强度是否接受，应诚实讨论可持续边界，不提供自己无法兑现的承诺。

**准备证据：** 需求变更记录、方案比较、你做的关键协调、风险沟通和事后检查。材料私有时只用脱敏的结构和经过授权的信息。

<a id="strengths-and-onboarding"></a>
## 5. 个人特征、优缺点、影响者与入职挑战

**准备问题：** 有哪些优势和不足？什么人影响了你？入职最可能遇到什么挑战？

优势用与岗位相关的具体行为和产物证明。不足选真实但可讨论的一项，解释影响、改进措施和检查进度；“太追求完美”这类标签本身没有证据。影响者讲清一次具体建议或示范怎样改变自己的做法，避免只有评价词。

入职挑战从业务知识、系统依赖、协作流程和能力缺口出发，制定一个小步验证计划：先读关键材料与当前指标，再与负责人确认验收，完成一个可回滚的小任务并复盘。不要在不了解环境时承诺立即大规模重构。

<a id="availability-and-compensation"></a>
## 6. 薪资与到岗时间怎样准备？

核实自己愿意提供的信息、实际可到岗日期和现有安排；不为了显得积极承诺做不到的日期。薪资讨论区分固定、浮动、权益、福利与工作方式，不只比较一个总数。期望范围应基于已核实的岗位职责和自己的选择标准，本章不提供行情数字或法律建议。

可以先问清级别、责任和报酬结构，再表达真实范围。涉及合同、竞业、离职手续或其他法律约束时，使用正式文件和适当专业意见，不能根据面试范文作判断。不要把教材中的范例报酬、交接周期或个人选择当自己的事实。

<a id="demo-versus-production"></a>
## 7. 你的Agent是Demo还是线上系统？

按证据分阶段：概念设计、可运行原型、离线回归、受控试用、真实生产。说明模型与工具版本、真实用户/数据范围、权限、监控、失败处理和谁承担运行责任。能跑一次不等于稳定上线，用户量也不能代替任务质量。

准备能证明所处阶段的最小材料，例如测试命令、实际运行输出、版本记录或经授权的指标。明确未验证的并发、恢复、成本和安全边界。面对追问，区分“实现了”“测过了”“计划做”，不要把完整架构图全部说成亲自完成。

<a id="causality-and-metrics"></a>
## 8. 指标提升怎样证明，换场景后怎样选指标？

**准备问题：** 改动与变化是因果还是相关？提升多少、怎么算？新场景该看什么？解决了真实需求吗？优化过程有什么反例？

先解释指标定义、分母、样本、时间窗口、版本、对照与代价。前后对比可能受流量、外部服务、季节或其他改动影响；没有合适对照时明确归因限制。可随机分配或进行可控干预时，预先定义测量和停止规则；不能从一次截图证明提升。

按业务目标选指标：检索找全证据、代码修复满足测试及不变量、任务执行达到真实终态。用户需求可通过行为、反馈与完成结果共同核对，不能只看按钮点击或模型回复。优化复盘按瓶颈→假设→改变→对照→结果→反例组织；失败成本和安全回归也要报告。[Agent评测](../10-agent/25-agent-evaluation-and-routing.md)提供技术实验结构。

<a id="technical-depth"></a>
## 9. 算法应用、两轮间学习与研发分工

**准备问题：** Transformer、KV Cache、FlashAttention等机制在场景里怎样取舍？上次面试后补了什么？未来想做什么？AI优化/研发与微调怎样分工？

对每种机制说明问题、输入/资源条件、收益来源、代价和验证方法。读过原理不等于部署过，调用已有模型不等于训练过。给出自己的学习或实验记录，未运行的部分明确保留；不要背“显存下降多少”却解释不了模型、序列与测量条件。

岗位分工以真实任务和产物说明：数据质量/标注、检索与工具、服务性能、模型训练、评测及发布都有不同责任。微调需要数据授权、目标与独立评测，不是每个AI工程师都必做的工作。兴趣表达结合具体能力目标和已经开始的准备，而非借用别人项目叙述。

<a id="ai-native-research"></a>
## 10. AI原生调研、落地瓶颈和合成受访者

**准备问题：** 用AI做新品调研怎样设计？理论依据、壁垒与难点是什么？Agent落地卡在哪里？

从真实决策需求出发，明确需要知道的人群、行为和不确定性。设计资料搜集、任务分解、来源核验、分析与产物验证；模型能力、上下文与工具质量都可能成为瓶颈，应通过具体失败证据定位。系统特色要能转成独有数据、可靠反馈或流程效果的证据，而不是只说“用了最新模型”。

合成受访者可用于提出假设、检查问卷措辞或生成测试场景，不能直接当真实消费者比例、市场需求或因果证据。以真实样本校准不同人群误差，区分生成模型的先验与观察到的事实，保存可复查设计并对结论标注限制。涉及真实人群的重大决策应依据合适真实证据，本章未执行调研。

<a id="coding-tools-and-harness"></a>
## 11. 编码工具、Vibe coding与Harness怎样比较？

**准备问题：** 实际用过哪些工具，怎样避免错误？工具之间差别是什么？Harness提供了什么？

没有使用记录时不要编体验。用同一小任务比较上下文选择、编辑范围、工具/测试能力、错误恢复、审批、产物质量、费用与时延；保留精确版本和命令。品牌、宣传和一次成功不足以证明优劣，具体产品功能在使用时查官方资料。

工作方式可从规格→小步修改→差异审查→类型/lint/测试→必要人工验证组织。测试自身也须审查，模型可能删断言或只满足可见样例。Harness是受约束的执行与反馈系统，不必只是一个固定DAG；基线见[Harness专题](../10-agent/18-harness-runtime-and-observability.md)。

<a id="interrupted-task"></a>
## 12. 任务做一半中断，怎样恢复？

恢复读取权威任务与已验证产物，核对环境、依赖版本、权限、检查点及未决外部动作。记录“做了三项”不够，需知道三项的真实产物、版本和验证结果。工具结果未知时先查询或对账，不重新执行所有步骤。

任务清单、上下文摘要与checkpoint有不同职责。保留目标、未完成项、限制、失败原因和证据引用，从安全检查点继续；过时产物只重做受影响依赖。详见[A27–A30](../10-agent/04-streaming-and-reliable-execution.md#a27)。面试可以讲这种设计，只有实际故障演练后才能声称恢复测试通过。

## 最后一轮检查

- 每个“我做了”都有自己的责任与产物，不借同事贡献补经历。
- 每个数字都有定义、样本和原始依据；不确定性不藏在漂亮结论后。
- 范例、设计与实际实施分开，公开内容不包含前公司的私有资料。
- 业务价值、工程取舍、失败与复盘都能连接到同一个真实项目。
