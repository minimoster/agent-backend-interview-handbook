## 二、原创模拟追问 1：转写错误率下降，会议纪要就一定更准吗？

**场景。** 一个会议助手先把音频转成文本，再提取决定、负责人和截止时间。你替换了 ASR 服务，平均字错词错更少，但用户仍反馈行动项不对。如何评价与定位？

### 先把链路拆开

至少保留三份可对照材料：音频、人工标注的转写文本、人工标注的会议行动项。把问题分成两层：

1. **识别层**：音频里的内容有没有被正确转成文本？
2. **任务层**：已经写进文本的决定、否定关系、负责人和日期，有没有被正确提取？

词错误率 WER 按最优对齐中的替换数 S、删除数 D、插入数 I 计数，分母 N 是参考文本的词数：`WER = (S + D + I) / N`。若 N 为 100，发生 4 次替换、3 次删除、2 次插入，WER 为 9%。N 为零时应单列空参考样本，不能直接相除。大量插入可使 WER 超过 100%，因此不能把 `1 - WER` 一律当成普通准确率。[Microsoft Speech 官方评测说明](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-custom-speech-evaluate-data#evaluate-word-error-rate-wer)

比较模型前先固定文本规范化、分词与计分规则。中文若按字评价，就明确称为 CER；不能把一种分词下的 WER 与另一种规则的结果直接比较。

### 为什么整体错误率会掩盖业务问题

“由王敏负责”被转成“由黄敏负责”，与漏掉一个语气词，可能都只增加少量编辑错误，但对行动项的影响不同。除了整体识别误差，练习中还应记录：

- 人名、项目名、日期和数字的正确性。
- 行动项是否有原文依据，负责人及截止时间是否对应正确。
- 没有明确负责人或时间时，是否如实留空，而非补全一个看似合理的值。

这些是本练习建议的任务指标，不是原帖报告的实验结果。

### 一个能定位问题的对照实验

同一总结器分别接收人工转写和 ASR 转写。如果人工转写条件下仍错，先查提取规则、提示或模型；若主要在 ASR 条件下错，再检查错字是否集中在人名、日期或重叠语音。两组结果的差异是定位线索，不自动等于严格的因果贡献，因为错误之间可能相互影响。

**验收。** 能拿出一例“整体 WER 更低，行动项却更差”的自造样本，并指出是哪一个字段改变了业务含义。数据按场景分组，单列噪声、多说话人和专业术语，不只报一个平均值。

## 三、原创模拟追问 2：证据明明在上下文里，模型为什么答错？

**场景。** 一份答案所需的证据已经成功召回，也确实放进了模型输入。把窗口扩大后，错误却没有明显减少。怎样判断是检索问题，还是上下文使用问题？

### 区分三个环节

1. 证据有没有被召回？
2. 证据有没有真正进入最终请求，是否被截断、摘要改写或模板覆盖？
3. 模型有没有正确利用证据并给出有依据的答案？

“窗口支持多少 token”只回答能接收多大的输入，不能直接回答第三项。

《Lost in the Middle》用多文档问答和键值检索研究证据位置的影响。论文观察到，被测模型在相关信息位于输入开头或末尾时往往表现更好，位于中部时可能明显下降。这是论文在其模型与任务上的实验发现；实际使用的模型需要做自己的位置实验。[原论文，TACL 2024](https://aclanthology.org/2024.tacl-1.9/)

### 设计一个最小位置实验

固定问题、正确证据、干扰文档集合、模型与生成配置，只改变正确证据的位置，分别放到靠前、中间和靠后。控制总输入长度，记录最终答案正确性和引用证据正确性。换多道题、多种干扰文档排列，并做重复运行，避免用一次随机输出下结论。

接着比较两种改动：

- 只移动证据，不减少内容：检查位置敏感性。
- 删除低相关干扰内容：检查上下文筛选是否有帮助。

如果同时换模型、重排证据、改摘要和改提示，就无法判断是哪项改动有效。把关键证据置于更合适的位置可以作为候选方案，但仍要测多证据组合、矛盾信息和否定条件，避免只优化单段摘录题。

**验收。** 保存模型实际收到的最终输入、证据位置、总 token 数及判分结果；能指出“召回成功但引用错误”和“证据被截断”是不同失败类型。这里给出的是实验设计，没有填入未运行的准确率。

## 四、原创模拟追问 3：Agent 从 5 分钟变成 20 分钟，先查什么？

**场景。** 相同任务类型的一次运行明显变慢。你能看到用户开始等待的时间，却没有定位到慢在哪里。如何补齐证据，并决定优化顺序？

### 先统一计时范围

把用户请求进入系统作为起点，把任务结果真正可用作为终点。单独计量排队、模型请求、工具执行、重试退避、人工等待及结果写回。若“平时 5 分钟”只计执行时间，而“这次 20 分钟”包含排队，两者不能直接比较。

用 `run_id` 关联整次任务，用 trace/span 描述各段工作。OpenTelemetry 的 span 表示一个工作单元，包含开始结束时间，并通过父子关系和上下文传播串联请求；异步任务还可以用 span link 关联。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

### 按三类假设排查

| 假设 | 应观察的证据 | 针对性的处理 |
|---|---|---|
| 执行路径变长 | 模型轮数、工具次数、重复调用签名、重规划次数 | 查循环终止条件、失败恢复与任务拆分；设置步骤预算 |
| 单步变慢 | 同类模型调用或工具调用的耗时分布、输入输出长度 | 定位具体下游、输入膨胀或输出过长，再做缓存、裁剪或服务优化 |
| 等待变多 | 排队时间、限流响应、退避记录、并发占用、审批等待 | 调整容量或调度，检查重试策略与等待状态展示 |

表中的措施是排查后的候选行动，不是没有证据时全部打开的“优化套餐”。例如独立的两个只读查询可能并行，但后一项依赖前一项结果时不能硬并发。

### 并行时间不能简单求和

假设模型阶段耗时 2 秒，随后两个工具并行耗时 8 秒和 11 秒，汇总阶段再耗时 2 秒，且忽略其他开销：整条路径约为 `2 + max(8, 11) + 2 = 15 秒`，不是 23 秒。

因此要看开始结束时间、依赖关系和最长的依赖路径，而不是把所有子 span 相加。一个慢任务也不等于服务整体变慢：再按同类请求比较延迟分布、成功率、重试率和成本。

**验收。** 画一条能区分“多跑了 10 轮”和“只跑 3 轮但每轮排队”的时间线。改动后同时检查尾延迟、成功率和成本；只有延迟变小而任务被过早终止，不算优化成功。

## 五、原创模拟追问 4：乱序列表构树，为什么两遍哈希表还不够？

[完整构树代码](../../examples/retrieval_worked_examples/interview_build_forest.py) · [边界测试](../../examples/retrieval_worked_examples/test_interview_build_forest.py)

**场景。** 输入是数据库导出的记录，每条包含 `id` 和 `parent_id`。记录顺序任意，要求输出嵌套的 `children`。数据还可能包含重号、缺失父节点和环。

### 先定数据合同

本练习约定：`id` 是非空字符串；`parent_id` 为非空字符串或 `None`，`None` 表示根；允许多个根，返回森林；根和同层孩子都保留输入顺序。重复 ID、未知父节点及任意有向环都报错，不把错误数据悄悄挂到根上。

### 解法分成校验与组装

1. 第一遍建立 `id -> 节点` 索引，同时检查重复 ID。为输出节点创建新的 `children` 列表，避免修改输入记录。
2. 第二遍检查每个父 ID 是否存在，得到 `节点 -> 父节点` 的依赖图。
3. 对全部节点做环检测，而不只是从根出发。否则“一棵正常树 + 一个独立环”会被漏掉。
4. 校验成功后，再按原输入顺序挂接父子关系并收集根节点。

下面用 Python 标准库完成第三步。`TopologicalSorter` 的映射值是该节点的前驱集合，因此这里用父节点作为前驱；`prepare()` 会检测有向环并抛出 `CycleError`。官方实现会自动补入未显式提供的前驱，所以本题必须先自行拒绝未知父节点。[Python graphlib 文档](https://docs.python.org/3/library/graphlib.html)

```python
from graphlib import CycleError, TopologicalSorter


def build_forest(rows):
    rows = list(rows)
    nodes = {}
    for row in rows:
        ident = row["id"]
        parent = row["parent_id"]
        if not isinstance(ident, str) or not ident:
            raise ValueError("id must be a nonempty string")
        if parent is not None and (
            not isinstance(parent, str) or not parent
        ):
            raise ValueError("parent_id must be a string or None")
        if ident in nodes:
            raise ValueError("duplicate id")
        nodes[ident] = {**row, "children": []}

    graph = {}
    for row in rows:
        ident, parent = row["id"], row["parent_id"]
        if parent is not None and parent not in nodes:
            raise ValueError("unknown parent")
        graph[ident] = () if parent is None else (parent,)
    try:
        TopologicalSorter(graph).prepare()
    except CycleError as exc:
        raise ValueError("parent cycle") from exc

    roots = []
    for row in rows:
        ident, parent = row["id"], row["parent_id"]
        if parent is None:
            roots.append(nodes[ident])
        else:
            nodes[parent]["children"].append(nodes[ident])
    return roots
```

### 为什么正确，复杂度是多少

唯一 ID 保证每条输入只对应一个输出节点；父节点存在保证挂接目标有效；每条记录至多有一个父节点，配合无环条件，保证每个连通分量最终通向一个根。最后按输入顺序挂接，每个非根节点恰好进入一个父节点的孩子列表。

若有 n 条记录，则边数不超过 n。忽略业务字段复制体积，并按哈希表操作平均 O(1) 计算，索引、校验、环检测和挂接合计 O(n) 时间、O(n) 额外空间。若输入包含大对象字段，复制成本也要计入；这里对额外字段仅作浅复制，不承诺深层对象相互隔离。

**验收。** 覆盖空输入、单根、乱序孩子、多个根、重复 ID、未知父节点、自环、独立于正常树的环，以及深链。对于深链，构造过程通过不代表递归的 JSON 序列化器一定能处理同样深度；数据结构组装与序列化上限是两个问题。

#### P18-01 经历介绍与选择 Agent 方向

**答案与口述：**“我用研究/文档Agent案例介绍工程问题：Saber把资料变成可检索证据，Openresearch把任务依赖、执行和评测串起来。我重点准备检索、运行治理和结果验证，而不只介绍模型API。”随后补充自己真实负责的模块、遇到的问题及可展示证据，不编实习、用户量或个人动机。

**原理与项目：** 按“问题→输入输出→机制→证据→边界”讲。S-RAG、O-RUN、O-EVAL分别提供技术主线，但仓库所有权和函数存在不能证明某段代码由本人独立完成。

#### P18-02 音视频怎样变成可用的转写文本

**答案与口述：**“现有两个案例不是已核实的会议ASR系统。如果迁移到会议场景，我会先解封装提取音轨，统一采样/声道，按需做语音活动检测与分段，ASR后保留时间戳，再按需要处理说话人和标点，最后让总结器输出带原文位置的行动项。”不能把说话人分离当作ASR自然附带的保证。

**原理与项目：** 音频识别、说话人归属与任务提取是不同误差来源。S-RAG可承接文本检索，O-EVAL可借鉴证据和结构校验；音频上传、ASR服务和说话人能力属于新增设计，不能声称源码已有。

#### P18-03 ASR供应商如何选择与比较

**答案与口述：**“我不会先报一个供应商最好。先固定中文术语、人名、噪声、重叠说话等授权测试集，用同一规范比较CER/WER、关键字段、首段/最终转写延迟、失败率、费用及数据去向，再选符合部署要求的方案。”流式与离线、云服务与本地部署要分组，不能只比一段安静录音。

**原理与项目：** 选型是多目标约束，不是榜单排名。可复用O-EVAL的版本/hash、逐样本与失败记录思想；没有供应商实测，所以不填写“某家提升多少”或说已经上线某ASR。

#### P18-04 识别质量怎样评价，错漏怎样优化

**答案与口述：**“固定参考转写与分词规则，算CER/WER，并单列人名、日期、金额和否定词。再用人工转写/ASR转写分别驱动同一总结器，看错误先发生在识别还是提取。按噪声、术语、多人重叠分类修复后重跑同集。”公式、空参考与业务字段见[深入练习1](#二原创模拟追问-1转写错误率下降会议纪要就一定更准吗)。

**原理与项目：** 编辑距离平均值不能代表行动项正确性。O-EVAL的逐样本重算是可借鉴机制，不能把其分类/回归指标直接叫作现成ASR评测。

#### P18-05 通话与会议隐私怎样保护

**答案与口述：**“先确认录音目的、参与者知情和数据允许去向，只采必要内容；按租户/角色控制原音频、转写、向量与摘要的访问，传输与存储加密，日志脱敏，并落实保留期限、更正和删除传播。外部ASR/模型的数据政策单独确认。”敏感原音频不能因为转成向量就视为匿名。

**原理与项目：** 权限应在读取与召回边界生效，而非只在最终prompt提醒。S-RAG演示证据流，但本轮不宣称已审计其端到端隐私合规；增加权限过滤、日志检查和跨租户反例属于验收建议。详见[证据治理](../10-agent/17-rag-indexes-and-evidence.md)。

#### P18-06 中心化与去中心化怎样取舍

**答案与口述：**“中心编排便于统一任务状态、预算、审计和失败恢复，但会有瓶颈与单点；去中心化可独立扩展，却需要处理发现、冲突、重复执行与全局终止。按控制面的可靠性需求选，不把多Agent自动等同去中心化。”

**原理与项目：** O-RUN是可讨论的中心调度案例：依赖决定就绪，槽位约束并发，执行器路由能力。单机执行身份检查不等于分布式fencing；不能凭这个案例声称集群高可用已经验证。

#### P18-07 RAG怎样切块，块大小怎么定

**答案与口述：**“先按标题、段落、代码或表格边界切，再用目标模型token预算限制长度；必要时用重叠、父子块或邻块扩展。小块利于命中，大块保留条件，但也增加噪声和成本，所以参数要在冻结问题集上选。”

**原理与项目：** S-RAG的 `IngestWithMetadata` 先父块后子块，建立父子关联；`QueryWithHistory` 优先使用父块。固定代码使用可配置大小，**这里不把字符/切分器长度直接叫token，也不把某个默认值说成已验证最优**。详见[切分实验](../10-agent/30-rag-data-and-chunking-lab.md)。

#### P18-08 为什么这样切，如何证明影响

**答案与口述：**“固定语料、问题、Embedding、召回/重排和生成配置，只改切片策略。候选层看Recall，排序看MRR/nDCG，最终上下文看关键条件覆盖，再看有依据答案、时延和token；检查表格拆断、跨块否定与父块重复等失败样本。”

**原理与项目：** 在S-RAG的索引、融合、重排、最终父块四处留证据身份，才能知道改动作用在哪层。现有源码可解释边界，但本章手算不是项目实际收益。可直接练习[指标与配对比较](../10-agent/35-retrieval-evaluation-worked-example.md)。

#### P18-09 tokenizer如何把文本编码

**答案与口述：**“Tokenizer按固定词表与算法把文本变成ID序列。BPE常从较小单元逐步合并高频组合，其他模型可能用WordPiece或Unigram；同一个词可拆多段，中文、空格和代码也受具体版本影响。必须用目标模型的tokenizer计数，不靠字符数估成精确值。”

**原理与项目：** ID用于Embedding查表，但切词不是模型语义理解本身。Saber分块参数与模型token预算要另外对齐，本轮没有运行真实tokenizer。基础见[Transformer先修](../10-agent/05-transformer-prerequisite.md)。

#### P18-10 为什么不直接按整词或单个字符建模

**答案与口述：**“整词词表很大，未见词、拼写和多语言难覆盖；纯字符虽然覆盖灵活，但序列更长、计算和长距离学习成本更高。子词在词表大小、序列长度和可组合性间折中，不保证一个token等于一个字。”

**原理与项目：** token长度影响S-RAG最终证据预算、调用费用和推理延迟。字节级或带回退方案可改善覆盖，但具体保证应查对应tokenizer，不能把所有模型算法说成BPE。

#### P18-11 Transformer、QKV与注意力怎么解释

**答案与口述：**“输入Embedding加位置信息后经过注意力、前馈、残差和归一化等层；解码器自回归时需要因果掩码。对输入X投影得到Q、K、V，计算softmax(QKᵀ/√d_k＋mask)V，多头分别建模后拼接并做输出投影。QK给匹配权重，V提供被聚合内容。”

**原理与项目：** 缩放缓和点积分布随维度增大的问题；mask阻止读取不允许的位置，位置编码补充顺序。S-RAG使用外部模型不等于项目实现/训练Transformer。可按[QKV算例](../10-agent/05-transformer-prerequisite.md#transformer-qkv)与[形状](../10-agent/05-transformer-prerequisite.md#transformer-shapes)手算，不只背公式。

#### P18-12 为什么中间证据容易用不好，怎么改

**答案与口述：**“先确认正确证据真正进入最终请求，再固定内容与长度，只改变证据位置，多题重复测答案与引用。若有位置效应，再评重排、去噪、分段提取或关键证据前置；不能把中间失效全归因检索，也不能保证移到开头总能解决。”

**原理与项目：** 训练分布、位置表示、注意力与干扰都可能相关，论文现象不提供对所有模型的唯一因果解释。S-RAG的父块回填、preview重排与最终prompt是核对点；源码中出现证据不等于模型真正利用。见深入练习2与其原论文链接。

#### P18-13 Context是什么，包含哪些内容

**答案与口述：**“Context是这次推理实际可见的信息，包括系统/开发指令、当前问题、历史、工具定义与返回、检索证据等；不是数据库全部内容，也不等于长期记忆。长期记忆要检索、筛选后才进入本次上下文。”

**原理与项目：** S-RAG的 `QueryWithHistory` 把历史与当前检索结果组织为模型输入；O-RUN的 `buildTaskInputs` 从声明输入和上游产物组装任务数据。回答时沿最终请求核对，不以UI显示了聊天记录推断全量进入模型。

#### P18-14 窗口上限由什么决定

**答案与口述：**“要同时看精确模型的训练/位置机制、推理实现与服务允许的总长度，再分清输入、最大输出以及推理等额外预算。硬件内存是实际约束之一，但不能只加显存就让未适配模型可靠处理任意长度。”

**原理与项目：** 模型容量上限、服务策略上限和任务有效长度不同。组装S-RAG请求时要给输出和工具结果预留空间；压缩历史降低输入占用，并没有扩大模型本身窗口。

#### P18-15 Codex到底多大窗口，不同模型一样吗

**答案与口述：**“Codex是产品和模型系列，不能给一个永久数字。先问具体模型ID、客户端/服务及核查日期，再引用官方限制。作为历史型号示例，2026-10-15读取的GPT-5.3-Codex API页列400,000上下文、128,000最大输出，并已标弃用；这不等于当前所有Codex会话或其他模型限制。”[官方型号页](https://developers.openai.com/api/docs/models/gpt-5.3-codex)

**原理与项目：** 总窗口不是400,000输入再额外加128,000输出。客户端可预留预算或做压缩，不能拿产品展示值、API上限与实际剩余可用量混为一谈。本题不建议切换到该弃用型号，也不推测题帖当时使用的是哪一个模型。

#### P18-16 能否调大窗口，参数与能力有什么区别

**答案与口述：**“在模型和服务本来支持的范围内，可以调整客户端预算或服务允许长度；调max output只改输出额度，不等于扩模型窗口。超出原适配长度可能涉及位置编码缩放、长序列继续训练与推理实现，之后还必须评长任务质量。”

**原理与项目：** RoPE缩放等方法是在扩展位置处理范围，不自动保证推理、检索或多证据质量。不能虚构Codex内部训练方法；Saber/Openresearch本轮也没有窗口扩展实验。公开方法可参考[YaRN原论文](https://arxiv.org/abs/2309.00071)。

#### P18-17 大窗口有什么代价

**答案与口述：**“常规稠密自注意力prefill的计算随序列长度可达平方量级，KV缓存随长度增长；长输入还增加传输、费用和首次输出时间。FlashAttention减少中间存储与访存，但不自动把稠密注意力的全部算术变成线性。更大窗口也可能增加干扰。”

**原理与项目：** S-RAG回填父块会扩大最终输入，因此要测去重、预算和关键条件覆盖。延迟还取决于模型、批处理、缓存和输出长度，不能用一个O(L²)公式直接推断真实端到端速度。见[推理与缓存](../10-agent/24-inference-and-serving-boundaries.md)。

#### P18-18 怎样训练或适配长上下文

**答案与口述：**“通常结合位置机制适配与长序列数据训练，混合不同长度，训练跨段检索、跨文档组合等任务；评测不仅看单针检索，还看多证据推理、否定条件、位置变化及短任务退化。再控制显存、并行和数据泄漏。”

**原理与项目：** 长度外推、继续预训练、SFT和服务预算配置不是同一件事。YaRN是公开方法案例，不是任何闭源模型训练配方的证据；两个项目固定源码在此只展示应用层调用，不宣称已经训练长窗口模型。

#### P18-19 SFT、PPO、DPO、GRPO各做什么

**答案与口述：**“SFT用示范输出做监督学习；PPO从策略采样、以奖励/优势更新，常用clip限制更新幅度；DPO用chosen/rejected偏好对相对参考策略优化，不必先另训奖励模型再跑PPO；GRPO对同题多次采样，以组内相对奖励估优势，省去独立value critic，但仍有采样成本和奖励质量问题。”

**原理与项目：** SFT学示范，偏好优化比较好坏，在线RL还涉及探索/采样；四者不是必经升级链。PPO在语言RLHF中常与奖励模型、critic及KL约束组合，不能把这套组合当PPO定义本身。GRPO组内全同奖励时学习信号会弱。参考[PPO](https://arxiv.org/abs/1707.06347)、[DPO](https://arxiv.org/abs/2305.18290)、[DeepSeekMath/GRPO](https://arxiv.org/abs/2402.03300)。O-EVAL是应用评测代码，不是上述训练算法实现。

#### P18-20 为什么需要多个Agent，而不只用一个

**答案与口述：**“只有角色知识、工具权限、上下文或独立并行确有差异时才拆。先用单Agent基线测任务成功率、回归、成本与延迟；拆分可能提升专门性，也可能增加协调成本、错误传递和重复工作，不保证更多Agent更强。”

**原理与项目：** O-RUN把DAG依赖与类型路由分开，`resolveRunner` 中coder/sandbox/general共用Coder，其他分支有对应runner；因此多个角色标签不证明每个角色有独立模型或完全不同实现。项目是否因拆分获益，须有实测而非架构图。

#### P18-21 多Agent为什么可以采用中心调度

**答案与口述：**“中心调度让一个位置负责依赖就绪、并发槽位、预算和终态，便于避免后继抢跑并追踪失败；代价是控制面可用性和吞吐约束。执行器可以分散，控制面仍可逻辑集中，两者不矛盾。”

**原理与项目：** O-RUN提供具体例子，但执行身份检查不等于对所有外部副作用的分布式互斥。需要检查取消、重试、迟到回写、状态持久化和中心故障恢复。详见[项目A39/A40](../50-projects/public-repository-case-studies.md#a39)，不宣称已做集群压测。

#### P18-22 乱序记录怎样变成JSON树

**答案与口述：**“先建立ID索引并拒绝重复，再检查父ID存在及全部节点的环，校验后按输入顺序挂接。允许多根就返回森林；不知道缺父节点策略时先明确合同，不悄悄改成根。”完整解法、正确性、平均O(n)时间/空间及代码见[深入练习4](#五原创模拟追问-4乱序列表构树为什么两遍哈希表还不够)。

**原理与项目：** 这是通用结构题，不把教学函数冒充O-RUN已有图校验；树每节点至多一个父节点，而任务DAG可以有多依赖，数据模型不能混用。深链组装能通过，也不保证递归JSON序列化同样深度能通过。

#### P18-23 二叉树之字形层序怎样写

**答案与口述：**“用队列做BFS，每轮冻结当前层大小，孩子始终按左、右入队；本层结果按奇偶层反转后加入答案。这样遍历顺序始终稳定，展示顺序交替，不让反转入队破坏下一层。”空树返回空列表。

```python
from collections import deque


def zigzag_level_order(root):
    if root is None:
        return []
    queue = deque([root])
    answer = []
    reverse = False
    while queue:
        level = []
        for _ in range(len(queue)):
            node = queue.popleft()
            level.append(node.val)
            if node.left is not None:
                queue.append(node.left)
            if node.right is not None:
                queue.append(node.right)
        answer.append(level[::-1] if reverse else level)
        reverse = not reverse
    return answer
```

**原理与边界：** 每节点出入队一次，逐层反转总长度也是n，时间O(n)；不含返回值的队列/本层额外空间O(w)，w是最大层宽，含结果为O(n)。输入须为无环二叉树，不能把有环的任意图直接代入。配套代码与测试在本章已有构树文件中；对 `[3,9,20,null,null,15,7]` 输出 `[[3],[20,9],[15,7]]`。

### B篇：项目4项、基础6项与算法1项逐项作答

#### P19-01 自我介绍怎样避免泛泛而谈

**答案与口述：**“我用Saber的证据检索和Openresearch的任务执行介绍研究/文档Agent，从一次请求的输入、依赖、工具到验证后的产物讲清楚。我能解释已核对的源码机制，并把未运行的效果与待验证风险单独列出。”再补真实职责和经历，不照搬原帖的简历评分项目。

**原理与项目：** 技术介绍应能落到S-RAG/O-RUN的路径、函数与边界；项目堆栈不是成果证明，数字必须有运行记录。

#### P19-02 AI项目全链路如何讲

**答案与口述：**“Saber从文本摄入、父子块关联与索引，到历史相关检索、多查询融合、LLM重排和带父块的生成；Openresearch从任务依赖、就绪与路由，到产物传递和评测验证。我会选择一条真实请求走读，而不是把两个仓库拼成一个已经部署的系统。”

**原理与项目：** 对应S-RAG的 `IngestWithMetadata`→索引入口、`QueryWithHistory`→`SearchMulti`→重排；O-RUN的scheduler→executor。PG、ES、Milvus写入存在分步失败窗口，不能因有多个写入函数就宣称跨库事务。

#### P19-03 评分如何结构化，维度如何设计

**答案与口述：**“我的固定项目证据是研究评测，不是已核实的招聘评分。若设计技术练习反馈，我会先冻结rubric_version、criterion_id、评分范围、evidence_refs、reason和unknown，再分别评价技术正确性、证据/推理、完整性；权重和规则由评测侧维护。无法证明的项标缺证据，不让模型编出分数。”

**原理与项目：** O-EVAL的 `normalizeClaimRubric`、`claimRubricSHA256` 与证据校验可说明合同和溯源；benchmark按逐样本预测重算指标说明不能信模型自报。JSON合法仅证明结构，不证明评分公平、事实或一致性。上述维度为迁移设计，不是当前功能；更不能用这些练习分数自动决定真实招聘结果。

#### P19-04 知识类型、离线摄入与在线问答

**答案与口述：**“先区分原始文档、版本元数据、块与派生索引，再区分写入路径和读取路径。Saber固定源码里，文本进入 `IngestWithMetadata`，父子切片后带元数据写PG，并尝试写ES/Milvus；在线 `QueryWithHistory` 改写/检索、融合重排，优先用父块生成。实际支持哪些上传格式和解析器，要继续沿HTTP上传入口核对，不能从文本摄入函数推断。”

**原理与项目：** PG主记录、向量相似度和关键词索引职责不同；索引失败可能导致召回缺失。离线更新须考虑版本、删除、权限和重建，不能把长期记忆outbox机制扩大成文档RAG所有索引的保证。对应S-RAG与[项目A42–A44](../50-projects/public-repository-case-studies.md#a42)。

#### P19-05 Harness是什么，为什么不只是prompt

**答案与口述：**“Harness是围绕模型的执行支撑与治理：组上下文、调用工具、维护状态、限制权限/预算、验证结果和恢复失败。Prompt告诉模型目标，运行时代码落实边界；一个while循环只是最小骨架，不能保证生产可靠性。”

**原理与项目：** O-RUN的scheduler/executor提供状态、预算和能力路由，O-EVAL提供执行后证据校验。它们是不同模块，不能把某个名为benchmark_harness的文件当整个系统全部Harness。详见[Harness章节](../10-agent/18-harness-runtime-and-observability.md)。

#### P19-06 长任务越来越慢怎样定位

**答案与口述：**“统一端到端起止，用run/task与trace关联排队、模型、工具、重试和写回，区分轮数增加、单步变慢与等待增加。先比较同类任务的输入输出长度、调用数、下游耗时和限流，不直接升级模型或机器。”

**原理与项目：** O-RUN可沿 `ExecutePlan`、`findReadyNodes`、`runReadyNodes` 与执行器拆阶段；S-RAG可区分多查询、单路召回和LLM重排。上述是建议观测点，不声称项目已有完整OpenTelemetry。并行按关键路径而非span耗时总和计算，见深入练习3。

#### P19-07 定位后怎样优化延迟

**答案与口述：**“循环变长就查停止条件与步骤预算；输入膨胀就先去冗余并保关键证据；独立只读步骤才并行；下游等待则处理限流/容量与有界退避。缓存要带模型、版本、权限和内容身份，避免错用旧结果。一次只改能验证的原因。”

**原理与项目：** S-RAG已核实多query并发，但单query内Milvus、ES按代码顺序调用，不能宣称已全面并行。O-RUN有并发槽位与预算，调大槽位可能恶化下游限流。改后同看成功率、P95/尾延迟、成本和回归，没有性能记录就不填提升比例。

#### P19-08 参数固定的工具为什么也会不可靠

**答案与口述：**“工具名或参数模板固定，不代表运行输入、权限、网络、状态和副作用固定。先校验schema与语义，再做授权、超时、取消、结果校验和错误分类。只对可安全重试的错误重试；写操作用幂等键/状态核对，未知结果先查是否已执行。”

**原理与项目：** S-RAG的LLM重排解析失败会回退RRF顺序，是有界降级案例，不是结果永远正确；O-RUN完成/失败路径校验execution身份，可处理部分迟到结果，但不自动撤销外部副作用。固定prompt不能代替执行器治理。详见[工具契约](../10-agent/31-tool-mcp-and-skill-contracts.md)。

#### P19-09 对话增长后怎样管理上下文

**答案与口述：**“按实际模型token预算保留当前目标、约束、最新决定和未完成动作，历史按重要性检索或分层摘要；大工具结果外置并保引用，去重无关内容，为输出预留空间。权限和用户最新撤销不能被压缩掉。”

**原理与项目：** S-RAG的 `QueryWithHistory` 是核对最终输入的入口，O-RUN的任务输入与产物引用可避免把整个全局状态重复塞入。`truncateArtifactValue` 是截断，不等于语义保真摘要；本轮未核实完整自动压缩策略，不能把建议当既有实现。

#### P19-10 如何证明摘要没丢关键信息

**答案与口述：**“先列必须保真的事实槽：目标、限制、否定、数字/单位、身份、来源、最新决定与待办；摘要逐项回链原文，缺项标缺失，矛盾标未决。用同一后续任务比较完整历史和压缩历史，检查答案、工具参数与授权是否回归，再控制压缩率。”

**原理与项目：** 文字流畅、词面相似或更短都不等于信息完整。O-EVAL的证据关联与rubric可借鉴为验收思路，但未运行摘要效果实验；S-RAG父块/引用要保持可回查。反例是把“不要发送”压成“准备发送”，即使大部分文字相似也必须判失败。

#### P19-11 限定数字集合构造严格小于n的最大数

**答案与口述：**“先问清数字能否复用、零和前导零、是否必须同位数、n是否为正。按已有X04合同，尝试与n同长度从高位尽量匹配；一旦某位可选更小数字，就用最大合法数字填满后缀。若后续无可行选择，回溯到可减小的前一位；同长度无解再尝试更短长度。不能只贪心匹配到一半就宣告失败。”

**原理与代码：** 最高位第一次变小后，后缀越大整体越大；严格小于不能返回n本身，前导零要单独处理。完整实现、独立暴力对拍、复杂度和无解合同复用[X04](../70-practice/interview-algorithm-supplements.md#x04)，不为同一道题复制第二份可能分叉的实现。本题是算法练习，不宣称两项目已有数位构造功能。
