## 一、先把项目介绍讲清楚

### KnowFlow：30 秒介绍模板

> KnowFlow 是一个把对话、知识检索和报告产物连接起来的 Agent 应用。后端入口进入统一执行流，按知识增强开关、知识库加载状态和报告意图，选择轻量 RAG、报告子 Agent 流程或普通 ReAct。执行中通过事件展示进度，之后更新对话和记忆。我的实际工作是 `[个人负责模块与可定位改动]`。我最能讲清楚的是 `[一个具体机制]`；关于性能和部署，我只陈述 `[实际验证记录，或尚未验证]`。

这段回答先给用户目标，再给主链路，最后给个人边界。若还没有独立改动，可以把最后两句替换为：“我目前以这个公开版本做源码学习，重点追了路由、取消和记忆提交。我能解释实现与失败窗口，但不会把仓库整体功能算作我的个人成果。”

### KnowFlow：2–3 分钟介绍模板

> 这个项目想解决的不是只生成一句回答，而是让对话能够使用知识、执行工具，并在报告场景留下可继续使用的文档。比如用户问一个已有知识点，可以走轻量检索问答；用户要求形成报告，则需要检索、写作、审阅和文档产物之间的数据传递。
>
> 我会从实际请求讲起。`handler.go` 解析消息和 `use_rag`，流式入口调用 `ProcessStream`。它与非流式入口汇合到 `runOnce`：先 `prepare`，再 `dispatch`，最后 `finalize`。`routeDecide` 的实际条件是知识增强开启且 RAG 已加载时，再判断是否为报告意图；报告进入 `rag_agent`，普通问答进入 `rag`，其他情况进入 `react`。所以不能说“所有请求都经过多 Agent”，也不能因为 `dispatch` 有 `tool` 分支就说当前路由一定会选到它。
>
> 执行层最值得讲的是控制流和副作用。ReAct 可以规划任务图；固定实现遇到无效图会清除依赖后重建，这提高继续执行的机会，却可能破坏业务顺序。工具执行需要继续追到具体接口，图运行时优先传递 context，但旧 `Execute` 接口不能获得调用方的取消信号。流式也要分层：轻量 RAG 先拿完整结果，再发 `rag_result` 和一次包含完整答案的 `token` 事件，不能把这一路称为模型实时 token 流。
>
> 状态层同时有对话、偏好、长期记忆以及派生索引，不能把它们当同一个事务。长期记忆提交成功后再尝试更新本地缓存，缓存冲突时回读；回读失败可能仍返回已提交记录，因此“已持久化”与“当前实例已可见”要分开。我的实际贡献是 `[具体文件、改动动机、本人完成的验证]`。如果继续完善，我会优先验证 `[例如双请求取消范围或依赖失败时不得发布]`，这是下一步计划，不是已经上线的能力。

讲后续 `bd0230f…` 时，在执行流介绍中补上：“dispatch 成功且没有取消才进入 finalize；失败或取消显式发 error/done 结束，RAG 和单工具调用补了 ctx/error 传播。”不要把旧基线的单工具直调或失败收尾方式当作这个后续版本的现状。

### ResearchPilot：30 秒介绍模板

> ResearchPilot 把研究意图组织成任务计划，再按依赖和任务类型调度执行，前端通过事件观察过程。计划可以使用内存存储，配置文件存储后有单机快照与中断状态恢复。执行接口返回 202，任务使用独立于 HTTP 请求的后台 context；这意味着连接断开不必取消任务，但不等于进程重启后自动继续。我的实际工作是 `[个人负责模块]`，能提供的验证是 `[真实记录或尚未运行]`。

### ResearchPilot：2–3 分钟介绍模板

> ResearchPilot 的核心问题是把一个较长的研究需求拆成可执行、可观察、有产物的步骤。以论文复现或自定义评测为例，检索资料、准备数据、生成和运行代码、核验结果是不同任务；每个步骤都需要输入、输出和失败条件。项目里既有计划图，也有任务类型路由和具体 Agent 执行器，这几层不能统称为一个“大模型自动完成”。
>
> API 先创建并保存计划，执行接口再检查状态和进程内 `running` 表，启动带总超时的后台执行并返回 202。这样请求连接和长任务生命周期分开了。计划存储默认是内存；配置 `PLAN_STORE_PATH` 后尝试文件存储，初始化失败会降级到内存。文件存储采用临时文件、文件同步、替换和目录同步，但先改内存再持久化，错误返回不保证内存没变化。启动恢复会把中断的任务改回 pending 并清理旧执行身份，后续还需要调度入口，不能说重启自动续跑。
>
> 事件链路先订阅实时总线，再重放历史，用连接内指纹集合抑制重复，每十秒查历史补漏。这个设计考虑到了慢订阅者，但没有构成完整的游标续传协议：发送帧没有事件 `id`，没有消费 `Last-Event-ID`，指纹也没有包含 payload 的值。真实收到终态时会结束连接，因此仍要具体分析漏事件窗口。
>
> 我还会主动说明信任边界。共享 API token、计划 OwnerID 比较和可信的用户身份不是同一层；Docker 有资源限制和 capability 收缩，也不等于默认断网或非 root。评测方面，我复用已有 A41、A45、A46：任务完成、证据评估和指标可信度分别判断。我的个人贡献是 `[文件与实际工作]`，效果只能引用 `[可复现的数据与日志]`。没有这些记录时，我会明确说当前结论来自源码分析。

### “你到底做了什么”与“用了 AI 还算你的项目吗”

**可直接练习的回答：**“我把工作拆成需求判断、接口与状态设计、代码实现、验证四部分。`[某段代码]` 是 AI 帮我生成初稿，`[具体错误]` 是我根据调用链或测试发现并修正的。我能现场解释输入、状态变化和失败分支，也能在不调用 AI 的情况下实现其中的最小版本。没有亲自做过的模块，我会明确说是仓库已有实现。”不要把“我读懂了”改成“我独立从零完成”，也不要因为用了框架就否认自己可以解释和验证业务设计。

如果面试官要一个难点，用“场景—冲突—定位—选择—验证”组织：例如两个请求同时执行，用户取消其中一个，实际取消范围却是共享 runtime 中所有在途请求；先画出对象生命周期，再设计按用户与请求查找 cancel 的方案，最后用两个可控阻塞任务验证。只有本人实际修改并跑过时，才把这些动词说成过去式。单纯把文件名、框架名和模型名列出来，不能证明解决过问题。

### 方向 1：一次 KnowFlow 请求究竟走哪条链路

**口述答案。**“我先区分入口、路由和执行。HTTP 入口解析 message 与 use_rag，流式请求进入 `ProcessStream`，统一到 `runOnce → prepare → dispatch → finalize`。实际路由先看 `UseRAG && a.rag.Loaded`，成立时再按报告意图选 `rag_agent` 或 `rag`，不成立走 `react`。`rag_agent` 允许并强制子 Agent 流水线，普通 `react` 不允许子 Agent。分支名称多，不代表一次请求把所有能力都跑一遍。”

**具体机制与小例子。**假设知识库已加载，用户打开知识增强，问“定义是什么”，进入轻量 `rag`；同样条件下要求报告，是否进入 `rag_agent` 取决于报告意图判断；知识增强关闭时，即使文字像报告，也走 `react`。报告判断最终复用 `needsSubAgentPlan`，不能声称经过了训练好的语义分类器。`dispatch` 仍保留 `tool` 和默认聊天分支，但当前 `routeDecide` 直接返回的只有上述三类。阅读位置：[统一执行与路由](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/runtime_process.go)、[HTTP 入口](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/interfaces/http/handler/handler.go)。

**第一层追问：为什么不用所有问题都跑 Agent？**

示范答案：“能力足够时，简单路径更容易控制延迟、成本和失败面。轻量 RAG 的目标是检索后回答，报告流程还要组织研究、写作、审阅和文档产物。规划本身也会出错，多一次规划或工具调用就多一个依赖。这里是设计取舍，不能直接说轻量 RAG 一定更快或更准确；要固定同一模型、问题集和知识库比较完成率、证据质量、调用数与耗时。”

**第二层追问：打开知识增强却没有走 RAG，先查什么？**

示范答案：“先确认请求体的 `use_rag` 到达后端且解码正确，再看当前实例的 `a.rag.Loaded`，然后核对 route 事件和最终 `Response.Mode`。`Loaded` 是代码中的加载条件，不保证语料新鲜、召回正确或知识库对该问题有答案。我会继续分开查入库状态、文档与 chunk 标识、召回结果、送给模型的证据，最后才检查生成。如果直接换模型，可能完全绕过了真正的加载或过滤问题。”

**第三层追问：有人问 BM25、chunk 冲突或幻觉，怎样接回项目？**

示范答案：“先定位是词项匹配、语义召回、重排还是生成的问题。BM25 用词频、逆文档频率和长度归一化衡量词项相关性，适合精确术语，但不能直接代表语义理解；向量召回也不保证版本新或事实真。若两个 chunk 对同一配置给出不同值，我会保留文档版本、时间、权限与出处，先做有效性筛选，再判断是否可回答；无法消解冲突就说明冲突或拒答。评估时分别看证据召回与答案支持率，不能用回答流畅度代替检索正确性。具体公式和练习复用 [RAG 章节](../10-agent/02-rag-retrieval-and-reranking.md)，本次走读没有证明每条路由都执行了 BM25 或重排。”

**易错说法。**“所有请求都经过多 Agent”“知识库已加载就不会幻觉”“有 Elasticsearch 就证明这个请求走了 BM25”“路由到 RAG 就已经完成有效检索”。这些都把组件存在当成调用链证据。

**验证方法。**用可控的 RAG 加载标志、报告意图返回值和工具替身构造路由表；覆盖开关开/关、加载/未加载、报告/问答组合，断言 mode 和实际调用对象。失败样本另记录 query、候选 chunk ID、过滤原因和最终证据；不要只截一张回答页面。

**真实取舍。**关键词式意图识别易解释、易测试，但会误判省略或混合意图；引入模型路由会增加调用成本、版本波动与新的失败处理。更复杂的路由只有在固定任务集上证明收益，才值得引入。

**不知道时的诚实答案。**“我确认了路由条件和入口，但没有实测模型路由与关键词路由的效果差异。也没有证明这条请求用了哪一种检索器；我会先追 `QueryWithHistory` 的下游与实际配置再回答。”

<a id="direction-02"></a>

### 方向 2：界面看起来在流式输出，是否真的降低了首 token 延迟

**口述答案。**“SSE 是后端到客户端的事件传输形式，不保证上游模型逐 token 生成并即时转发。KnowFlow 的 `chatStream` 写 `event/data` 帧并尝试 Flush；但轻量 `rag` 分支先等 `QueryWithHistory` 完整返回，再发检索结果和一条包含完整答案的 token 事件。所以必须分别测首事件、首个答案内容和完整答案的到达时间。”

**具体机制与小例子。**教学时间线：0 秒发 `start`，0.1 秒发 `route`，3 秒检索与生成结束，随后发 `rag_result`、整段 `token`、`done`。页面很早有“正在处理”，但用户 3 秒才见到答案；把 0 秒称作答案首 token 延迟就是口径错误。此处数字只是示意。[SSE handler](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/interfaces/http/handler/handler.go) 与 [rag dispatch](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/runtime_process.go) 必须一起读。

**第一层追问：Flush 了，为什么浏览器还最后一起显示？**

示范答案：“先判断应用是否真的分多次产生内容。若上游只返回完整答案，Flush 不能制造真实增量。若应用确实逐步写，再查框架包装是否支持 Flusher、压缩或代理是否缓冲、客户端是否增量读取，以及前端是否等完整响应或把多次更新批量渲染。要在上游产出、服务端写出、客户端收到和界面渲染四处打时间点；只看服务器日志不能定位网络或前端的问题。”

**第二层追问：TCP 可靠，为什么还要处理 SSE 分帧？**

示范答案：“TCP 给字节流，不保留应用每次 write 的边界。一个 SSE 事件可能被拆成多次读取，多个事件也可能合并到一次读取。客户端需要缓存未完成片段，按 SSE 的空行结束规则解析，并正确处理跨块 UTF-8 字符，不能把一次网络 read 当一条 JSON。这里的 chatStream 是 POST；浏览器原生 EventSource 的使用方式与 POST fetch 读流不同，要看实际客户端，不能从后端 Content-Type 推断前端用了 EventSource。”

**第三层追问：如何证明一次流式改造有价值？**

示范答案：“我会固定问题集、模型版本、检索配置与并发条件，对比首个有用答案内容延迟、完整响应延迟、失败率和用户取消后的资源收尾。把冷启动与缓存命中分组，记录分位数而不是只报平均值。如果生成增量需要边输出边审核，还要定义修订或撤回语义：未核验内容不能提前说成最终事实。流式可能改善等待感受，但不必减少总计算量，也不能仅凭单次演示宣称 P95 提升。”

**易错说法。**“event 名叫 token 就是逐 token”“加 Flush 一定解决所有延迟”“SSE 保证断线不丢”“TCP 一次读取就是一个事件”。

**验证方法。**用可控替身延迟返回完整 RAG 结果，记录事件顺序；再用真正分段的替身比较。把一段含中文和多条事件的测试字节流按不同边界切块，验证客户端解析结果相同。代理路径测试应在获准的测试环境做，本专题没有改动真实网络配置。重连另见 [A25](../10-agent/04-streaming-and-reliable-execution.md#a25)。

**真实取舍。**一次返回完整答案更容易做整体校验；增量输出降低等待感，但增加分帧、断连、局部失败和内容修订处理。状态事件本身仍有价值，只是指标名称要准确。

**不知道时的诚实答案。**“我能确认轻量 RAG 的事件是在完整结果后发送；还没有测真实代理和前端的缓冲。我会先提供分层时间戳，再判断瓶颈，不能现在承诺具体提速比例。”

### 方向 3：取消是谁的取消，context 到底传到了哪里

本节比较的单工具 `Execute` 直调行为属于 `9afe774…`；后续 `bd0230f…` 已改为 `executeToolContext` 优先带 ctx 接口并在调用前后检查取消。拒收迟到结果仍不能强制停止正在运行的旧 Execute，也不能撤销已发生的外部副作用；按任务取消与共享状态隔离仍需分别核对，不能把接口修订推断成这些问题全部解决。

**口述答案。**“取消是协作信号，不是杀死 goroutine。KnowFlow 每个入口注册 cancel，结束时反注册；`Cancel()` 调共享 runtime 的 `cancelAll`，会触发该 runtime 当时登记的全部在途请求。HTTP 断连取消的是请求 context，但下游是否及时停止，要追具体调用接口。图运行时优先 `ExecuteStructured(runCtx)`，其次 `ExecuteCtx`，最后才回退无 context 的 `Execute`。”

**具体机制与小例子。**甲乙两个请求使用同一 UnifiedAgent，同时登记取消函数；甲调用 `/chat/cancel`，该接口不传请求 ID，最终遍历全部函数，因此乙也处在取消范围内。反过来，若某工具只实现无 context 的阻塞 `Execute`，ctx 已取消不代表工具已经返回。`mode_tool.go` 的单工具路径直接调用 `Execute`，但当前路由是否进入它要另行确认，不能把它推广成所有工具路径。[取消注册表](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/runtime_task.go)、[取消转发](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/infra_cancel.go)、[图工具执行](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/runtime_graph.go)、[单工具接口](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/mode_tool.go)。

**第一层追问：为什么 cancelAll 先复制函数再解锁调用？**

示范答案：“锁保护的是注册表结构。复制当时的函数集合后释放锁，可以避免在持锁期间执行外部行为，让注册和清理更快继续。它有一个明确边界：复制之后才登记的新请求，不在本次集合里。cancel 幂等不代表整个业务操作幂等，也不代表子任务已退出；如果接口要承诺‘已经停止’，需要等待受控任务收尾并区分正在取消与已取消。”

**第二层追问：怎样改成只取消自己的一个任务？**

示范答案：“建议用受认证身份和 request/task ID 定位运行句柄，取消入口先核对归属，再取出对应 cancel。注册、查询、删除要定义生命周期，任务结束后及时清理，重复取消返回一致状态。不能只把 map 的 key 改成用户传来的 ID 就算完成授权；还要防旧请求删除同 ID 的新句柄。若同一任务有多个子工具，统一用父 context 派生，各工具有自己的预算。”

**第三层追问：工具已在外部写入，随后取消，还能保证没发生吗？**

示范答案：“不能。取消通常只说明本地不再等待或请求被中断，外部服务可能已经执行。对于有副作用的工具，需要业务操作 ID、幂等或结果查询，结果未知时先核对状态，再决定是否重试。把旧无 context 函数塞进 goroutine 然后 select 超时，只能让调用者先返回，不能停止那个 goroutine，反而可能泄漏。要改底层接口、使用支持取消的 I/O，或在独立受控执行环境里定义终止和回收合同。”

**易错说法。**“context 会自动杀线程”“取消当前请求绝不影响别的请求”“所有工具都没有 ctx”“超时返回就代表下游没执行”。

**验证方法。**用两个阻塞替身任务，分别记录注册、ctx.Done、工具退出和清理时间；一个使用 ExecuteCtx，一个只使用 Execute。测试取消范围、完成后反注册、同时完成与取消，以及后注册请求的边界。用通道屏障控制交错，不能靠 sleep 猜时序；竞态检测只是补充，见 [G03](../30-go/01-concurrency.md#g03) 和 [A30](../10-agent/04-streaming-and-reliable-execution.md#a30)。

**真实取舍。**全部取消适合单用户“停止当前所有工作”的合同，按任务取消适合并发、多用户界面，但要增加身份、句柄和生命周期管理。保留旧接口方便兼容，却需要明确它的取消上限。

**不知道时的诚实答案。**“我确认共享 runtime 的取消范围和接口选择顺序，但没有证明每个具体工具都及时响应 ctx，也没有多用户并发实测。我的下一步是用可控工具替身验证这两个问题。”

### 方向 4：用了 RWMutex 和 snapshot，为什么还不能宣称请求隔离

**口述答案。**“工具注册表的 RWMutex 防护 map 的读写，snapshot/filter 返回新的 map 容器，解决遍历时被注册修改的问题。但这是浅拷贝，Tool 内部切片和函数闭包仍可能共享引用；安全成立需要内部字段不变或另有同步。任务 runtime 也只有一份 task 和 snapshots，`currentTask` 返回指针，锁住取指针不等于锁住以后对指针内容的访问。”

**具体机制与小例子。**把快照中的 `tools["search"]` 删除，不会删除注册表中的键；但 Tool 的 `Parameters` 是切片，直接修改共享底层数组的一个元素，可能影响另一份 Tool 视图。闭包捕获计数器也不会因为复制函数值而复制计数器。两个请求先后 `setTask`，后一个会替换 task 并清空 snapshots，即使每次赋值都持锁，仍可能发生业务串台。[工具注册表](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/tool_registry.go)、[Tool 定义](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/domain/tool/tool.go)、[共享运行状态](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/runtime_task.go)。

**第一层追问：浅拷贝到底复制了什么？**

示范答案：“新 map 有独立的键槽，value 按 Go 的赋值语义复制。字符串值通常可视为不可变，切片复制的是指针、长度和容量这些描述信息，指针仍指向原对象；函数值可引用同一闭包环境。因此容器独立与对象独立不同。若工具定义注册后不变、执行器本身并发安全，浅拷贝可能足够；我不会仅因发现引用字段就断言已经发生竞态，需要找实际写路径。”

**第二层追问：为什么没有 data race 也可能串请求？**

示范答案：“data race 关心未同步的并发内存访问，业务隔离关心甲读到的是不是甲的数据。假设甲 setTask 后释放锁，乙随后持锁 setTask，甲再持锁 currentTask，整个过程可以没有竞态，但甲拿到乙的任务。需要按请求或任务保存状态，查询同时校验归属；不能靠加一把更大的锁掩盖对象身份问题。”

**第三层追问：你会选深拷贝、不可变快照还是每请求实例？**

示范答案：“先划分共享配置与可变执行状态。工具描述可以注册时复制并在发布后不可变，执行器内部若有连接池可安全共享；task、步骤、快照则按任务持有。深拷贝适合需要独立修改的小数据，但函数闭包无法靠一般深拷贝获得独立资源，而且大图复制有成本。每请求新建整套 Agent 可能重复连接和模型资源，所以我倾向于共享无状态依赖、隔离运行状态，再用并发测试确认。”

**易错说法。**“有锁就线程安全且多租户安全”“snapshot 就是深拷贝”“没有 race 报告等于不会串用户”“所有引用共享都一定有 bug”。

**验证方法。**分别测试 map 键修改、切片元素修改、闭包可变状态，以及两个任务交错 set/read/append；断言任务身份和数据内容。竞态测试用于找内存同步问题，确定性交错测试用于找逻辑隔离问题，二者不能互相代替。

**真实取舍。**短时持锁复制可以缩短读写竞争，但有复制成本；不可变设计降低锁需求，却要求所有写入口遵守合同。面试时先解释共享范围，再讨论换锁类型，见 [G11–G12](../30-go/01-concurrency.md#g11)。

**不知道时的诚实答案。**“我确认这里是浅拷贝和共享 task 指针，但尚未核对所有 Tool 的可变字段写法，所以只能指出成立条件和风险，不能说已经复现数据竞争。”

### 方向 5：DAG 校验失败后清空依赖，是否是安全的降级

**口述答案。**“图无环只是调度合法性的一个条件，依赖还承载业务顺序。KnowFlow 的图 `Validate` 检查缺失依赖并用拓扑分层检查环；`runReAct` 校验失败时把全部 DependsOn 清空再构图。它可能让任务继续运行，却也可能让‘先取证、后写报告’变成并行执行。这个行为要明确说明，不能把‘有 DAG’等同于所有依赖约束都得到保证。”

**具体机制与小例子。**有 A 获取材料、B 基于材料写报告、C 审核后发布，正常是 `A → B → C`。若规划把 A 也设为依赖 C，形成环，清空依赖会允许三者同时就绪；C 不应仅因可以调度就获得发布授权。`NewTaskGraph` 用 map 注册 ID，重复 ID 会覆盖映射，不能把 map 自动去重当合法性校验；输入列表仍可能影响边构造。[runReAct](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/mode_react.go)、[图构建与校验](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/domain/graph/graph.go)。

**第一层追问：现场解释拓扑排序和复杂度。**

示范答案：“入度是未满足的前置依赖数。标准队列版 Kahn 先把零入度节点入队，每弹出一个节点就删除它的出边，新的零入度节点继续入队；处理数不足 V 表示有环。邻接表和常数均摊的队列操作下，每个节点和边处理一次，时间 O(V+E)、空间 O(V+E)。但本项目 `TopologicalLevels` 每一轮扫描整个 inDeg map，处理过的节点只标为 -1，没有移出 map。若有 L 层，这段分层为 O(LV+E)，链状图 L=V 时可达 O(V²+E)。不能仅看到 Kahn 注释就回答 O(V+E)。”

面试白板可用下面的独立教学伪代码说明标准队列版，不把它当作仓库已有修复：

```text
validate input IDs are unique and nonempty
create adj[id] and indegree[id] for every ID
for each node v:
    for each dependency u of v:
        reject if u does not exist
        add edge u -> v; indegree[v] += 1
queue = all IDs with indegree 0
visited = 0; levels = []
while queue is not empty:
    width = size(queue); level = []
    repeat width times:
        u = pop_front(queue); visited += 1; append u to level
        for v in adj[u]:
            indegree[v] -= 1
            if indegree[v] == 0: push_back(queue, v)
    append level to levels
reject if visited != number_of_IDs
return levels
```

**第二层追问：为什么图合法也可能执行出错？**

示范答案：“图只表达结构，不能自动保证产物有效。例如 B 依赖 A，A 返回空文本却被标记完成，B 仍可能拿不到需要的数据；还要有输入输出合同和成功判定。同一层 map 遍历顺序也不保证稳定；若只是展示想稳定，可以按 ID 排序，但按 ID 排序不是拓扑排序。增加排序还要把成本单独计算，例如各层排序的总成本是各层节点数乘对数的求和。对于副作用节点，我会校验必要依赖成功且产物可用，再允许执行。”

**第三层追问：动态重规划时 A 依赖同批新节点 B，会怎样？**

示范答案：“固定 `AddNodes` 按输入顺序逐个加入，依赖只保留当时已在图里的节点。如果 A 排在 B 前面，A 对 B 的依赖可能被丢掉，之后即使 Validate 通过也无法发现原始约束已经消失。它还跳过已存在的 ID、清空分层缓存，并根据当前入度标记判断依赖是否已处理；业务上仍要区分成功、失败和取消。建议先把整批候选 ID 与旧图合并校验，再原子接受或拒绝新增图；同时限制重规划次数、节点数和预算，验证不能只写在 prompt 里。”

**易错说法。**“无效图降级并行肯定更安全”“所有拓扑实现都是 O(V+E)”“ID 排序就是执行依赖顺序”“Validate 通过说明重复 ID、产物和授权也都正确”。

**验证方法。**最小集合包括空图、单节点、链、菱形、环、自环、缺失依赖、重复 ID、同批前向引用和失败前置。先数每轮扫描次数，再比较队列实现；复杂度推导不需要真实大压测。业务验证用替身记录节点启动条件，确保缺证据时发布节点不执行。相关算法完整推导见 [课程表](../80-hot100/problems/0207-course-schedule.md)。

**真实取舍。**拒绝无效计划会降低“总能给个答案”的表面完成率，却保留依赖含义；自动修复方便用户，但必须证明修复没有删除关键约束。只读、互不依赖任务的并行和写入、发布任务的顺序要求应分别讨论。

**不知道时的诚实答案。**“我能确认当前的清依赖降级与分层扫描成本，没有测它在真实规划样本中的触发比例。建议改成拒绝或受限重规划，但不能说这个建议已经实现或一定提升效果。”

### 方向 6：名字叫 MCPTool，能否证明标准协议互通

**口述答案。**“我会按实际请求合同解释。`NewMCPTool` 把参数 JSON 编码后 HTTP POST 到 endpoint，以响应 body 为工具结果，并提供结构化错误、带 ctx 接口和兼容旧接口。它有 30 秒 HTTP 客户端兜底超时，但这个函数名和 IsMCP 标志本身不能证明某一 MCP 版本的协议互通。要声明兼容，必须明确协议版本、请求响应格式、能力与传输语义，并给对应客户端的互通证据。”

**具体机制与小例子。**参数 `{ "query": "示例" }` 在该适配器中直接成为 POST body，不是从名称推断出来的完整协议报文。无 ctx 的 `Execute` 自己创建 Background 派生的 30 秒超时；图运行时调用 `ExecuteStructured` 时则能把节点 context 传入请求。响应成功时保留原始字符串，并尝试解析 JSON 对象；调用方仍需判断业务结果是否有效。[HTTP 工具适配器](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/infrastructure/tool/mcp.go)。

**第一层追问：HTTP 200 是否就是工具成功？**

示范答案：“200 只说明这层 HTTP 请求得到成功状态，不能保证业务产物正确。这个适配器对未落入错误分支的响应构造 Success=true，JSON 对象解析失败也可以保留为字符串。下游若预期搜索结果数组、文件 ID 或计算结果，还要验证输出合同。反过来，业务错误、协议错误和传输错误也应分开，不能全压成一句字符串，否则调度层无法决定重试、修参还是向用户解释。”

**第二层追问：当前重试分类有哪些细节？**

示范答案：“按实现，4xx 标不可重试、5xx 标可重试；请求 ctx 主动取消不可重试，但 deadline 分支的 retryable 是 true，网络错误也标可重试。这里注释和实际赋值要以执行代码为准。真实策略还要看总预算、剩余时间、服务端提示与副作用。比如 429 在当前简单分类里属于 4xx，不会因为我知道通用策略可能退避就说项目已实现了 Retry-After。timeout 也可能是外部写入成功、响应丢失，要先考虑幂等和结果查询。”

**第三层追问：你说兼容性不足，是不是因为没 initialize？**

示范答案：“不能脱离版本这样判断。旧版与 2026-07-28 的生命周期、能力发现和传输规则不同，初始化握手不是可以跨版本套用的唯一清单。我当前能确认的是这个函数直接 POST 参数 JSON，未在这条实现链里看到足以证明目标版本互通的完整协议处理。应先固定要支持的版本，再用对应客户端核对消息格式、工具发现与调用、错误和取消等实际合同。SSE 进度展示、MCP transport 与应用自己的后台任务事件也不是同一种协议。”

**易错说法。**“能发 HTTP 就是完整 MCP”“所有版本必须同一种初始化握手”“超时都不能重试/都可以重试”“30 秒超时意味着外部操作最多只执行 30 秒”。版本背景复用 [MCP 版本与集成](../10-agent/15-mcp-versions-and-integration.md)，不在这里另造一套规则。

**验证方法。**用本地假 HTTP 服务记录 method、body、headers，分别返回合法 JSON、纯文本、400、429、500、延迟和中断响应；断言结构化错误与 ctx 传播。标准协议互通另用固定版本客户端验证，不能把这个 HTTP 单测冒充协议认证。响应大小上限、日志脱敏和外部写入幂等属于需要继续核对的合同。

**真实取舍。**轻量 HTTP 适配器易接现有接口、便于教学和调试，但标准客户端的发现与互通能力需要额外实现或接入相应 SDK。更精细的错误分类有利于调度，仍不能自动解决业务重复执行。

**不知道时的诚实答案。**“我确认了这段代码的 HTTP 合同，没有跑目标 MCP 客户端互通测试，所以不会说已完整兼容，也不会仅凭函数里没某个握手就对所有版本下结论。”

<a id="direction-07"></a>

### 方向 7：长期记忆提交成功后，为什么当前进程还可能读不到

**口述答案。**“`commitMemory` 先调用 memoryTx.Create，得到已提交的变更，再把变更应用到本地长期记忆缓存。ApplyCommitted 冲突时它尝试 LoadActive 后替换缓存；如果回读也失败，会记日志并返回已提交 record 和 nil。因此成功返回强调主数据已提交，不等于本地缓存已经刷新。数据库提交、进程内可见性和派生索引可见性需要分开陈述。”

**具体机制与小例子。**教学时间线：数据库成功插入记忆版本 v2；本地 ApplyCommitted 冲突；LoadActive 因连接问题失败；调用者拿到 record,nil，但本地缓存仍可能是旧视图。不能告诉用户“失败了所以重新插入”，也不能因为 error 为 nil 就宣称每个读取路径已见 v2。[提交与缓存协调](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/mem_commit.go)。Outbox 与索引投影的完整讨论复用 [A44](public-repository-case-studies.md#a44)，此处聚焦提交到本地可见性的窗口。

**第一层追问：为什么不先写缓存，再写数据库？**

示范答案：“先写缓存可能让其他请求读到最终未提交的记忆，数据库失败后还要撤销可见状态。当前顺序把主数据提交放在前面，避免把未提交内容当权威，但代价是提交后缓存更新可能失败。两种顺序都不能凭空变成跨数据库与内存的原子事务；要先规定权威存储和读取合同，再选择失败时返回什么、如何修复。”

**第二层追问：数据库用了事务，为什么不能把缓存一起回滚？**

示范答案：“数据库事务保护它管理的读写，普通进程内对象不自动参加事务。事务提交后再回滚应用缓存，并不能撤销已经提交的主数据；反过来也一样。隔离级别讨论的是事务之间能看到什么，不会自动约束任意本地缓存。若要读己之写，可以在本次响应使用提交返回的 record，或者携带最小版本要求，读取时等待缓存追平或受控回源。具体采用哪种要考虑延迟、可用性和回源压力。”

**第三层追问：如果 error=nil 但缓存没更新，你会怎样设计接口？**

示范答案：“我会保留‘主数据已提交’的明确结果，另表达可见性未确认，例如状态字段或诊断事件，而不是把它伪装成完全未生效的失败。重复调用要有稳定业务身份，避免调用者盲目重试插入重复记忆。后台修复可以按版本回读、对账，读路径也可以检测版本落后；这些是改进方案。仅加更多重试会延长请求、放大故障时数据库压力，不能替代结果语义设计。”

**易错说法。**“nil error 说明所有缓存和索引都同步”“事务让所有组件一起原子提交”“缓存失败就代表数据库没写”“最终一致就是稍后一定自动好了”。

**验证方法。**用仓储与缓存替身覆盖 Create 失败、返回 upsert 数异常、ApplyCommitted 成功、冲突后回读成功、冲突后回读失败；同时断言返回 record/error 和缓存内容。若测试真实数据库，应分别记录提交状态与读路径结果，不把页面可见当作事务日志。数据库基础复用 [B13–B15](../40-backend/02-databases-and-sql.md#b13)。

**真实取舍。**提交后即返回有利于可用性，调用者需要接受短暂不可见；等待本地或派生视图追平更易理解，但会增加尾延迟并把缓存故障传到写接口。没有一个策略适合所有业务。

**不知道时的诚实答案。**“我确认了提交后缓存回读失败的返回分支，还没有在真实数据库环境注入过该故障，也没有测可见性延迟。当前只能给出可复验的时间线和测试设计。”

<a id="direction-08"></a>

### 方向 8：ResearchPilot 返回 202 后，断连与重启分别意味着什么

**口述答案。**“执行接口校验计划状态，用进程内 running map 避免同一 runtime 重复启动，然后从 Background 派生带总超时的 context，启动 goroutine 并返回 202。请求断连通常不会沿 HTTP context 取消这个任务，但进程退出会失去 goroutine。文件存储可恢复计划状态，启动恢复只是清理旧租约并改回 pending，不是自动再次执行。202、持久化和重启调度是三层不同保证。”

**具体机制与小例子。**任务运行到 B 时浏览器关页，只影响观察连接，后台任务仍受自己的 timeout 和取消接口控制；若进程退出，后续是否有状态可读取决于存储配置与成功持久化。`PLAN_STORE_PATH` 未设置使用内存，文件存储初始化失败也会降级内存。`FilePlanStore` 的 Save/Update 先更新内存，再持久化整个快照；错误可能发生在替换前，也可能发生在替换后目录同步阶段。[执行入口](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/api/plan_runtime.go)、[文件存储](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/store/file_plan_store.go)、[中断恢复](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/store/recovery.go)。

**第一层追问：202 和 200 的区别，能说‘任务成功’吗？**

示范答案：“这里的 202 表示执行请求被接受并启动后台处理，不代表最终任务成功，也不是已经进入持久消息队列的证明。客户端需要用 plan_id 查询状态或观察事件，区分 pending、running、成功、失败、取消等结果。若客户端没收到 202 就超时重试，还应考虑原请求已启动；running map 能覆盖当前进程的一部分重复启动，但不是跨进程持久幂等协议。”

**第二层追问：文件 rename 是原子的，为什么还要 fsync？**

示范答案：“原子替换关注观察者是否看到半份文件，持久化关注系统故障后数据和目录项是否保留。该实现有临时文件同步、rename 和目录同步；这些步骤的实际行为还依赖平台与文件系统。先改内存再落盘意味着返回错误后当前进程可能看到新状态，而重启后可能回到旧快照；若 rename 已完成、目录同步失败，磁盘与断电后状态也不能用一句‘没保存’概括。这是单机文件方案，不自动成为多个进程共享文件的事务存储。”

**第三层追问：重启后 pending 了，为什么不能直接从上次那一行继续？**

示范答案：“恢复的是持久状态，不是 Go 调用栈。`RecoverInterruptedPlans` 把进行中的计划和节点改回 pending，清理 ExecutionID、LeaseOwner 和租约时间；需要后续执行入口重新领取和调度。若外部工具在崩溃前已完成写入但本地没记成功，重跑会遇到结果未知和重复副作用，必须核对产物或使用幂等身份。改状态、重新调度、拒绝旧执行者结果和外部副作用去重各有职责，不能用一个‘支持恢复’概括。”

**易错说法。**“Background 保证任务一定完成”“202 说明已持久入队”“文件初始化失败会停止接收”“重启恢复会自动续跑”“有 epoch 就是分布式 fencing”。后两类身份问题见 [A39](public-repository-case-studies.md#a39)。

**验证方法。**先做不启动模型的 store 与 scheduler 替身测试：客户端取消后后台 ctx 是否仍有效、相同计划并发执行是否冲突、结束后 running 是否删除；再用独立临时目录验证保存/读取和不同错误阶段。恢复测试断言 pending 与旧身份清理，并额外记录有没有新的 ExecutePlan 调用，不能只看状态颜色。真实进程重启或断电实验须在专用测试环境另做。

**真实取舍。**内存回退提高启动可用性，却降低恢复承诺；若业务必须持久，应考虑启动失败时明确拒绝接收，而非静默提供较弱服务。单机全量快照实现简单，但写放大和并发扩展需要测量，不能凭源码报吞吐上限。

**不知道时的诚实答案。**“我确认了 202 的启动方式、存储回退和恢复函数，没有实际重启该项目验证外部任务续跑。因此我会说‘可恢复到待调度状态’，不会说‘具备完整可靠队列’。”

<a id="direction-09"></a>

### 方向 9：先订阅再重放，为什么仍不是完整的事件续传协议

**口述答案。**“ResearchPilot 的 streamPlanEvents 先订阅总线，再读历史，用连接内 seen 指纹集合去重，每十秒重读历史补可能漏掉的实时事件。顺序上考虑了‘读历史与开始订阅之间’的空窗，但没有持久游标：帧没有 id，也不读取 Last-Event-ID；指纹只组合计划、事件类型、任务、时间和 payload 的键名，不包含值。它是特定的重放补漏实现，不能直接承诺有序无漏或 exactly-once。”

**具体机制与小例子。**同一事件在订阅后写入历史，再同时从历史与实时通道到达，seen 可以抑制一份重复。另一种情况是两条事件的 PlanID、类型、TaskID、Timestamp 和 payload 键完全一样，但值分别是 10% 与 20%，当前指纹会相同。还有一种情况：中间事件没从总线到达，随后实时终态到了，代码会结束连接，未必等到下次十秒历史补漏。[事件流与指纹](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/api/plan_runtime.go)。

**第一层追问：先读历史再订阅有什么风险，先订阅就解决全部问题了吗？**

示范答案：“先读历史后订阅，事件可能恰好发生在两者之间，既不在旧历史里，也没被实时订阅接到。先订阅再读历史把这个空窗变成重叠窗口，需要去重；但它仍依赖历史可完整读取、实时缓冲行为、稳定事件身份和终态处理。seen 只活在当前连接里，重连后重新建立，不是客户端已经消费到哪条的持久记录，也不能单独定义跨连接顺序。”

**第二层追问：把 payload 值也加到 hash 里就够了吗？**

示范答案：“这可以减少某种碰撞，却不能创造业务事件身份。同一事件重试序列化时字段表示可能变化，两条独立但内容相同的事件也可能被误合并。更清晰的方案是持久事件 ID 或每计划递增序列，重放按游标读取，客户端按 ID 幂等应用。要规定顺序、保留期、游标过期与快照重建，以及终态前怎样补齐缺口。若用浏览器 EventSource，它的重连语义也依赖服务端 id；若用 fetch 自建读流，客户端重连与游标需要自己实现。”

**第三层追问：代码说心跳能补漏，什么时候这句话不成立？**

示范答案：“历史本身必须能提供缺失事件，而且连接要活到补漏轮次。scheduler 的 publishAndStore 忽略 AppendEvent 的错误后仍 Publish；文件存储又可能先改内存后持久化失败。当前进程中历史也许仍看得到，但重启后的持久历史不能保证完整。实时终态到达后立即返回也会缩短补漏机会。我要把事件产生、内存记录、持久化、实时送达和客户端应用分别打点，而不是仅把心跳从十秒改成一秒。”

**易错说法。**“先订阅就不会漏”“指纹就是唯一事件 ID”“SSE 自带 exactly-once”“十秒心跳意味着任何时候最多丢十秒数据”。[发布与存储顺序](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/scheduler/scheduler.go) 是回答的重要依据。

**验证方法。**用可控事件总线和 store 安排历史/实时重叠、缓冲丢弃、相同指纹不同值、实时终态提前到达、AppendEvent 返回错误和客户端重连。检查完整事件序列，不只检查终态。区分两个假设的下一项测量是“缺的那条在 store.ListEvents 中是否存在”：存在则查订阅/终态/客户端路径，不存在则查写入与持久化。先加大缓冲或缩短心跳都可能只是掩盖问题。

**真实取舍。**定期全量查历史简单直观，但历史增长会增加读取与 seen 集合成本；游标分段读取更适合长期运行，却增加持久编号、保留策略和客户端状态管理。允许丢弃的进度提示与必须保留的业务完成事件，也可以采用不同合同。

**不知道时的诚实答案。**“我确认了补漏与去重实现，但没跑慢消费者与重启组合测试。当前只能说它有历史补漏机制，不能说它已经实现可靠的跨连接游标续传。”

<a id="direction-10"></a>

### 方向 10：认证、计划归属、CORS 与 SSRF 分别保护什么

**口述答案。**“我会分四层：认证确定可信身份，授权决定身份能访问什么，CORS 控制浏览器跨源读取行为，SSRF 防护限制服务端替用户访问的网络目标。KnowFlow 的 RequireAuth 验证 Bearer token 并把 claims 写入 context；ResearchPilot 的 API_AUTH_TOKEN 是可配置共享 token，空值放行。ResearchPilot 虽有 OwnerID 比较，但 resolveUserID 优先接受 X-User-Id，其次匿名 cookie，所以归属字段比较不能直接当作强用户身份隔离证明。”

**具体机制与小例子。**两个客户端拥有同一个共享 API token，不代表服务器已经区分了两个人。若身份来源只是可设置的头部，OwnerID 比较保护的是当前声明值，不自动证明声明者就是本人。PDF 代理则是另一条边界：URL 限 http/https、拒绝 userinfo，初验解析地址；实际 DialContext 再解析和检查地址，然后拨号到已检查 IP，重定向也重新验证。[KnowFlow 认证](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/interfaces/http/middleware/auth_middleware.go)、[ResearchPilot 身份来源](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/api/cookies.go)、[API 认证与地址检查](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/api/security.go)。

**第一层追问：有 JWT 或 API token，为什么还要 owner 检查？**

示范答案：“认证通过只说明调用者满足入口凭证要求，不代表可以读取任意计划。资源访问还要比较可信身份与资源归属，或检查角色权限。KnowFlow 中间件把验证后的 claims 写入 ctx，是建立身份的一步，但仍不能从这一层推断所有 handler 都正确使用了 userID。ResearchPilot 的共享 token 更接近入口口令；若部署前有可信身份网关，还要证明它去掉外部伪造头并写入认证身份，不能假设不存在于源码证据里的网关。”

**第二层追问：CORS 禁止了陌生域名，能防别人直接调用吗？**

示范答案：“不能。CORS 是浏览器执行的跨源访问规则，不是服务端身份认证。非浏览器客户端不受同源策略约束，浏览器的某些请求也可能先发出再限制读取响应。这里要按实际配置看允许的 Origin、凭据和预检；不能把 Access-Control-Allow-Origin 当权限系统，也不能为了方便一律放开。敏感操作仍应依赖服务端认证授权，cookie 场景另考虑请求伪造与 SameSite 等实际条件。”

**第三层追问：URL 检查过公网地址，为什么拨号时还查一次？**

示范答案：“检查和使用之间可能发生 DNS 结果变化，或者重定向带去不同目标。当前实现不仅初验，还在 DialContext 解析并检查所有返回地址，再连接检查后的 IP，降低检查后重新解析到内部地址的风险；重定向限制次数并重新做 URL 验证。它阻止若干私有、本地和特殊地址类别，但不能凭此宣称完整网络隔离，还要考虑部署环境的路由、出口策略、响应大小与时间预算。HTTPS 保护链路身份与机密性，并不自动证明目标 URL 被业务允许。”

**易错说法。**“有 OwnerID 就强多租户安全”“共享 token 就是个人登录”“CORS 可以防所有客户端”“只检查字符串是不是 localhost 就防住 SSRF”“代码有检查就证明生产配置正确”。

**验证方法。**在隔离测试中构造缺 token、错误 token、不同 owner、空 owner 与不同身份来源的请求；分别验证认证与资源授权。网络检查用注入的 DNS/拨号替身模拟公网、私网、混合地址和重定向变化，避免向真实内网探测。下一项证据应是实际部署的身份信任边界与生效配置，而不是先加一个更复杂的 CORS 正则。[CORS 与重定向调用位置](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/api/routes.go)。

**真实取舍。**匿名身份便于本地体验，共享 token 易配置，但不适合直接承担强个人身份隔离；外部身份服务能加强边界，同时增加配置、失效和信任链管理。网络目标限制越严格，越可能影响合法 PDF 来源，需要用业务允许范围定义策略。

**不知道时的诚实答案。**“我确认了源码中的默认和比较逻辑，没有拿到部署网关与生效环境变量，所以不能声称实际系统已开启认证或已被利用。我会先核对可信身份从哪里产生。”

<a id="direction-11"></a>

### 方向 11：Docker 沙箱有哪些限制，哪些只是可选配置

**口述答案。**“ResearchPilot 的 sandboxserver 构造 Docker 参数时有 CPU、内存、PIDs 限制，设置 no-new-privileges 并丢弃全部 capabilities。默认网络是 bridge；容器 user 只有配置了才加，根文件系统只读只有开关为 true 才加。镜像允许列表为空时全放，非空时按前缀匹配。挂载路径会做绝对化、清理、符号链接解析并检查允许根目录，但这些措施不能合成一句‘容器绝对安全’。”

**具体机制与小例子。**固定代码默认 CPU 参数为 `2`、内存 `4g`、PIDs `256`；这些是资源配置，不是跑出的性能。允许前缀若写得太宽，会接受比预期更多镜像，不能当精确镜像 digest 白名单。根只读也不代表所有 bind mount 都只读；要继续检查挂载参数和产物目录合同。[沙箱参数与路径检查](https://github.com/minimoster/ResearchPilot/blob/8abe80150be6fc72359f2fe78acfd5960d664bdf/scholar-agent/backend/internal/sandboxserver/docker_security.go)。

**第一层追问：CPU、内存和 PIDs 限制分别解决什么？**

示范答案：“CPU 限额约束可用计算份额，内存限制约束容器内存使用，PIDs 限制约束进程或相关任务数量，减少无界创建对宿主的冲击。它们不直接限制所有磁盘增长、外部网络访问或业务费用，也不保证任务在某个时限完成。OOM、超时和正常非零退出需要保留不同结果，不能一律归为模型代码错误。具体限制是否生效，还受 Docker 与宿主支持影响。”

**第二层追问：为什么挂载目录不能只做 startsWith？**

示范答案：“字符串前缀可能把 `/work-safe-other` 当成 `/work-safe` 内部，也处理不好 `..` 和符号链接。代码先取绝对路径、检查目录、解析符号链接，再用相对路径判断是否逃出允许根，语义更接近真正的目录归属。但检查到 Docker 使用之间仍存在路径被替换的时间窗口，需要看目录所有权和是否允许不可信方改动。路径校验也不回答目录内容能否读写、是否含秘密，这些要另设合同。”

**第三层追问：你会怎么决定断网、非 root 与只读根？**

示范答案：“按任务必要能力最小化。纯计算或已准备依赖的任务可考虑断网；需要下载依赖的任务可分准备阶段和执行阶段，不能为了成功率一直开放全部出口。非 root 与只读根通常缩小风险面，但可能使现有镜像安装和缓存路径失败，需要为临时目录、产物目录定义可写位置。镜像应固定可信来源和版本，前缀匹配与严格 digest 控制不同。选型时比较隔离需求与兼容成本，而不是把 Docker 名称当安全证明。”

**易错说法。**“默认断网、非 root、只读根”“有 cap-drop 就没有逃逸风险”“PIDs 限制等于控制了所有资源”“镜像前缀列表就是严格白名单”“CPU=2 是项目吞吐测试结果”。

**验证方法。**先对参数构造函数做配置矩阵测试，检查默认与显式开关；在独立临时目录测试正常子目录、同名前缀目录、`..`、文件而非目录、符号链接。真正启动容器后的资源生效、网络行为和收尾要在专用测试环境另验，不能用字符串单测冒充系统隔离测试。不能拿现有业务容器做未经计划的破坏实验。

**真实取舍。**更严格的环境会增加依赖准备与调试成本，却让运行范围更可控；开放网络与宿主挂载提高兼容性，同时扩大外部影响。对不可信代码还需考虑更强隔离方案，但本篇没有替项目新增这些能力。

**不知道时的诚实答案。**“我确认了参数构造和默认值，没在目标部署中运行资源限制或逃逸测试。只能说它配置了这些约束，不能保证每项都已生效，更不能承诺绝对隔离。”

<a id="direction-12"></a>

### 方向 12：记忆检查挡住了内容，为什么仍要追缓存和所有写路径

**口述答案。**“记忆安全要看每个存储位置和调用顺序。KnowFlow 的 prepare 在有 userID 时先写短期对话；异步偏好路径先对整段输入预检，再由模型提取，但 Pref.SaveBatch 发生在逐条 inspectKVPair 之前。通过逐条检查的内容才继续偏好持久化和长期记忆提交。同步 ExtractAndSave 是另一条路径，finalize 还会触发用户消息与对话对抽取；commitMemory 本身负责提交和缓存协调，没有统一执行 poison 内容检查。因此不能说所有记忆在任何可见位置之前都经过同一闸门。”

**具体机制与小例子。**用户输入通过预检，但模型抽出一个应该被逐条检查拒绝的 k-v。固定异步路径已经先 SaveBatch 到偏好缓存，再在持久化循环中跳过该条；于是“没有进入长期库”与“没有进入偏好缓存”不是同一句话。`poison.go` 按 PII、注入、临时内容顺序匹配规则，匹配安全只表示没命中当前规则。对话对抽取还有主题约束 prompt 和较低 importance，但模型生成的事实不因此成为独立证据。[prepare 与 finalize](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/runtime_process.go)、[记忆抽取路径](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/mem_writer.go)、[规则检查](https://github.com/minimoster/KnowFlow/blob/9afe774372f2068eb7e57ecdf1c491965eace2e3/internal/application/chat/poison.go)。

**第一层追问：为什么不能只在模型 prompt 里写‘不要记敏感信息’？**

示范答案：“prompt 是对模型的指令，不是强制执行边界。模型可能误抽、输出不符合结构或把文档里的命令当内容。程序应验证结构、来源、身份、内容策略与写入目的；对低可信材料不能提升成高优先级指令。正则检查能低成本挡住一些明确模式，却会漏掉改写、编码或跨片段内容，也可能误伤正常文本。因此要报告误拒和漏检，不能说规则足够复杂就彻底解决提示注入。”

**第二层追问：如何证明检查覆盖所有路径？**

示范答案：“从实际 sink 反向枚举：短期记忆、偏好缓存、偏好持久化、长期主数据与派生索引分别有哪些调用者。再为每条路径记录检查发生在写入前还是后、身份从哪里来、失败是否阻断、日志有没有记录原值。prepare 的 SaveBatch 顺序和同步 ExtractAndSave 需要单独验，不能只测试 mem_writer 就宣布全覆盖。commitMemory 的事务成功表示写入事实，不表示内容安全；必须把检查合同与持久化合同分开。”

**第三层追问：怎样防‘模型错答—写成记忆—下次再次引用’？**

示范答案：“我会保留来源类型与原始证据，区分用户自述、文档证据和模型推断，限制模型推断直接成为权威事实。复用时检查适用对象、版本、时效和冲突，必要时回到外部证据核对；撤销或更新也要影响各读取路径。当前用户来源与 exchange 来源有不同 importance 和标签，但权重低不等于已经验证真伪。评测可设计原始答案错误、后续更正、过期配置和冲突事实的多轮样本，分别观察写入、召回与最终回答，而不是只看模型是否说‘已记住’。”

**易错说法。**“所有偏好缓存写入前都过 poison gate”“检查了长期库就没有短期或缓存泄露”“正则可以完全防提示注入”“降低 importance 等于内容已经可信”“模型回答过就是事实来源”。

**验证方法。**用模型替身返回合成 k-v，分别覆盖整段预检拒绝、单条拒绝、拼接拒绝和正常事实；断言每个 sink 的状态而不是只数长期记录。安全测试只用虚构标记，不放真实凭证。再检查日志字段是否会保留敏感候选的 key/value 或匹配片段。若出现污染，下一项测量是“首次出现在哪个 sink、走了哪条写路径”，先加大正则集或直接换模型都不足以定位覆盖缺口。

**真实取舍。**规则成本低、解释清楚，但覆盖范围有限；模型检查可理解更多表达，却增加延迟、成本和新的不确定性。统一写前合同便于审计，仍需按短期对话、偏好和长期知识的不同用途制定保留、可见与撤销策略。

**不知道时的诚实答案。**“我已确认 prepare 与 mem_writer 的检查顺序不同，也确认 commitMemory 不做统一内容检测；还没有穷尽全部写入口和真实攻击样本，所以不会承诺全路径安全或给出防护成功率。”

## 三、把源码追问变成诊断：先测什么，再改什么

### 召回了相关 chunk，为什么仍然答错

“相关”表示与主题相近，“充分”表示证据足以支持这一个答案，两者不同。问“版本 3 的上传上限是多少”，检索到“版本 2 的上传说明”可能很相关，却不能支持版本 3 的结论。以下均为教学故障样例，不是声称在项目生产环境中实际发生。

| 场景 | 容易误判的答案 | 正确诊断与下一项测量 | 两个过早修复 |
| --- | --- | --- | --- |
| 缺失：文档只说明支持 PDF，没有给大小上限 | “相似度很高，模型应该知道” | 对齐问题所需字段与证据实际字段；检查原文是否存在上限，再查解析与切块是否丢失表头/脚注 | 先换大模型；无条件增加 top-k |
| 冲突：两份文档给出不同上限 | “重排分高的那条就是真实值” | 对比版本、更新时间、适用环境与权威来源；若无消解依据，明确冲突并停止确定性结论 | 盲目调 chunk overlap；把两值平均 |
| 过期：新制度已发布，索引仍返回旧版 | “提示词要求最新即可” | 比较主文档版本、索引版本、删除/更新传播与实际过滤条件 | 只改回答 prompt；先把旧答案加入记忆 |
| 证据齐全但回答漏条件 | “检索器不好” | 保存最终送入模型的上下文，核对截断、排序、条件位置和引用对齐 | 先换向量模型；只增加召回数量 |

**可口述的完整答案：**“我会先保存这个问题、应回答的事实和实际引用，从解析、切块、召回、排序、上下文装配、生成到引用逐层核对。原文就没答案，是证据缺失；原文有但解析没了，是解析问题；块存在但没进候选，是召回或过滤；候选有但最终上下文没了，是排序或预算；上下文充分仍答错，才继续查生成与引用。每层用相同文档与问题固定对照，避免一次改模型、切块和 top-k 后无法归因。不能把 NaN、解析失败、无证据回答从统计分母里悄悄删掉。”

评测可信度与失败分类沿用 [A45](public-repository-case-studies.md#a45)、[A46](public-repository-case-studies.md#a46) 和 [A47](../10-agent/02-rag-retrieval-and-reranking.md#a47)。面试官如果追问 NaN，可答：“先看是样本为空、分母为零、预测解析失败还是数值溢出；检查逐样本记录和统计口径，非有限数单独作为评测失败处理，不能静默当 0 或删除后继续报高分。”独立评分、可信金标和样本完整性已有 [教学 scorer](../../examples/trusted_evaluation/scorer.py)，不能说它已经修复 ResearchPilot。

### 如何回答“你会怎么优化性能”而不编造压测

**示范答案：**“我现在没有可信的负载数据，先定义目标和测量口径。请求延迟拆成排队、路由、检索、模型、工具、提交与传输，记录首个有用内容和整体完成的分位数；任务侧记录在途数、失败率、重试数与资源收尾。若耗时集中在模型，先扩大数据库连接池没有依据；若队列已经饱和，单纯提高并发可能让下游更慢。先固定并发、样本、缓存冷热和模型版本做基线，再一次改变一个因素，同时观察正确率和成本。优化只有在同条件对照里成立，不能把一个快样例当吞吐能力。”

### 怎样嵌入后端基础，而不背另一套八股

从刚讲过的失败窗口追一层即可：SSE 分帧接 [TCP 字节流](../40-backend/01-network-and-streaming.md#b03)，后台执行接 [HTTP 状态码与幂等](../40-backend/01-network-and-streaming.md#b01)，记忆提交接 [事务与隔离](../40-backend/02-databases-and-sql.md#b13)，任务归属接可信身份，DAG 接 [拓扑排序](../80-hot100/problems/0207-course-schedule.md)。回答顺序是“这个基础机制解释了项目里的哪一个现象—它保证什么—它不保证什么—如何验证”，不用先朗诵完整定义再寻找联系。

例如面试官问“计划表如何查询某用户最近任务”，可以先提出教学 SQL：按可信 user_id 过滤，再按 created_at 和唯一 ID 稳定排序，分页时考虑复合游标；索引是否选 `(user_id, created_at, id)` 要看实际数据库、查询和 EXPLAIN。本项目这一路当前是内存/文件 store，不要把建议 SQL 说成已有实现。完整 SQL 九题仍在 [原练习](../70-practice/sql-nine-worked-problems.md)，不额外扩题。

## 四、60 分钟初级模拟：能讲链路、能解释失败

一人扮演面试官，一人回答；独练时录音并计时。前半程先不翻答案，卡住可以请求看函数片段。面试官不按背出函数名多少打分，而看能否把条件、状态和因果说对。每轮先让候选人完整讲，再选一层追问，不要一分钟塞完所有问题。

| 时间 | 面试环节 | 本轮应留下的证据 |
| --- | --- | --- |
| 0–5 分钟 | 项目与个人贡献 | 一个真实场景、一条主链路、贡献边界 |
| 5–13 分钟 | KnowFlow 路由与知识检索 | 三分支条件表、一个误路由排查顺序 |
| 13–23 分钟 | SSE 为什么最后一起显示 | 分层时间线、一次下一步测量 |
| 23–33 分钟 | 取消与两个并发请求 | 取消范围、ctx 传播与任务收尾区别 |
| 33–43 分钟 | 锁和 snapshot | 浅拷贝例子、无竞态仍串台的交错 |
| 43–53 分钟 | ResearchPilot 202 与重启 | 连接、进程、存储、调度四层边界 |
| 53–60 分钟 | 复盘与诚实边界 | 四维评分、一个优先补做的最小验证 |

### 0–5 分钟：项目介绍与贡献

**面试官原话：**“选一个你最熟悉的项目，先用 30 秒介绍，再用两分钟讲清你负责什么。若使用 AI 或框架，也一起说明。”

**参考回答：**“我选 KnowFlow。它把对话、知识检索、工具执行与报告产物串起来。请求经过统一执行流，根据开关、加载状态和报告意图分发。我本人完成的是 `[真实模块]`，其中 `[真实改动]` 有 `[提交或测试记录]`；其他模块是仓库已有实现。若当前只是学习，我会明确说我完成了源码走读，重点解释路由、取消与记忆提交，尚未证明部署规模或效果提升。AI 帮助了 `[真实部分]`，我负责核对接口与失败条件，可以现场解释和复现最小行为。”

### 5–13 分钟：路由与相关证据

### 13–23 分钟：流式诊断

**面试官原话：**“后端写了 SSE 并 Flush，但用户最后才看到整段答案。给两个可能原因，再说下一项测什么。”

**递进追问：**“一次 read 收到半个 JSON，怎么办？”

**面试官提示。**候选人能给“服务端产出与客户端接收”这个区分性测量，比只背 no-cache、keep-alive 更有价值。不要把首个 start 事件延迟误评为首个答案延迟。

### 23–33 分钟：取消范围

**面试官原话：**“两个用户正在运行任务，甲点取消，乙会怎样？cancel 后能立即释放所有资源吗？”

**参考回答：**“在共享同一个 UnifiedAgent runtime 的前提下，Cancel 转到 cancelAll，会对当时登记的所有在途函数发取消，所以乙也在范围内。是否真正停止取决于下游是否响应 ctx；GraphRuntime 优先结构化带 ctx 接口，其次 ExecuteCtx，最后才无 ctx 的 Execute。cancel 只是信号，已经发生的外部副作用不能因此撤销，结束状态还需要任务收尾证据。”

**递进追问：**“给一个最小测试，不要靠 sleep。”

**参考回答：**“准备甲乙两个替身工具，分别通过 started 通道报告进入，再阻塞等待 ctx.Done 或测试释放通道。确认两者都已注册后调用取消，观察哪个 ctx 被关闭、哪个工具退出，并等清理完成。另加一个无 ctx 的工具，验证调用者取消不代表工具已退出。用屏障控制交错，才知道断言检验的是取消行为而不是机器碰巧快慢。”

**面试官提示。**第一层能说清协作取消；第二层说清共享范围；第三层能给退出与副作用边界。不要要求初级候选人现场搭完整服务。

**现场代码练习（占本轮最后 3 分钟）。**写出按可信 owner 和 task ID 查找取消句柄的 10–20 行伪代码。下面是教学设计，不是仓库已经实现的改动；register 与 cleanup 使用句柄身份比较，避免旧任务清理掉复用同一 key 的新任务。授权信息必须来自可信认证层，不能直接相信请求头里的 owner。

```text
register(owner, taskID, cancel):
    key = (owner, taskID)
    lock registry
    if key already exists:
        unlock registry; reject duplicate task
    handle = new unique handle(cancel)
    registry[key] = handle
    unlock registry
    return handle
cancelTask(authenticatedOwner, taskID):
    lock registry
    handle = registry.get((authenticatedOwner, taskID))
    unlock registry
    if handle exists: handle.cancel()
    return cancellation_requested_or_already_finished
cleanup(owner, taskID, handle):
    lock registry
    if registry.get((owner, taskID)) is handle: delete registry[(owner, taskID)]
    unlock registry
```

代码评分看三件事：是否按可信身份和任务定位，是否在锁外触发取消，是否知道“已请求取消”不是“已退出”。若要允许任务 ID 复用，还应让取消请求携带运行代次并校验，避免迟到取消指向新一轮执行；这属于进一步的合同设计。

### 33–43 分钟：锁和对象所有权

**面试官原话：**“snapshot 返回新 map，为什么你还说可能共享？再解释没有 data race 的串台。”

**参考回答：**“map 键槽是新的，但 Tool value 内的切片和闭包可能共享底层对象。删快照中的键不会删注册表，改共享切片元素则可能影响另一份视图。taskRuntime 的情况是业务身份共享：甲持锁 setTask 后，乙持锁 setTask，再由甲持锁 currentTask，操作都有同步也能读到乙任务。修复需要按任务管理状态和归属，不只是换成 RWMutex。”

**递进追问：**“你现在就能断言有实际竞态吗？”

**参考回答：**“不能。浅拷贝意味着需要不可变或内部同步的合同，是否出现竞态还要找到并发写路径；逻辑串台则可以用确定性交错验证。race 检测只能覆盖被执行到的内存访问，不能证明所有业务隔离。我会把已确认的结构与待复现的现象分开。”

**面试官提示。**让候选人画两份 map 指向同一切片即可，不必考底层实现细节。能主动限定“在共享实例和可变字段条件下”，比绝对化结论更准确。

### 43–53 分钟：202 与恢复

**面试官原话：**“ResearchPilot 返回 202，关闭页面后任务继续，是否意味着它是可靠任务队列？重启后从哪里接着跑？”

**参考回答：**“不是。后台 context 从 Background 派生，能与 HTTP 断连解耦，但 goroutine 属于当前进程。存储默认内存，配置文件存储也可能初始化失败而回退。恢复函数能把中断计划和节点改回 pending 并清理旧执行身份，却不会在那段代码里自动调用 ExecutePlan。需要后续调度，还要处理外部操作已经发生、状态尚未记录的结果未知窗口。”

**递进追问：**“持久化返回错误，可以安全重试保存吗？”

**参考回答：**“要先看错误阶段与操作身份。FilePlanStore 先改内存再落盘，rename 后目录同步失败也可能返回错误，不能默认完全没生效。保存同一状态与重复执行外部任务是两回事；应对比当前内存、磁盘快照和重启读取，业务动作需要幂等或状态核对。此处我给的是源码时间线，没有实际重启该项目。”

**面试官提示。**只要能分清接受、执行、持久化、恢复与重新调度，初级目标就达成。fencing、跨进程竞争可以留到加深模拟。

### 8–23 分钟：DAG 白板

**面试官原话：**“写 10–20 行伪代码验证任务依赖并拓扑分层，解释当前实现复杂度。无效图能否删边继续？同批重规划节点怎样处理？”

### 47–60 分钟：事件重放

**面试官原话：**“用户看到完成，但中间一步缺了。代码先订阅后重放，还十秒补漏，为什么可能发生？怎么验证？”

**参考回答：**“可能是中间事件未实时送达，终态先到使 handler 立即结束；也可能是 AppendEvent 持久化失败、指纹误合并或客户端应用遗漏。先查 ListEvents 是否存在那条事件，再对照实时帧、指纹与客户端处理记录。存在于历史但没展示时，定位终态或客户端；历史也缺时，定位写入与存储。当前 publishAndStore 忽略 AppendEvent 错误仍发布，所以看到终态不证明持久历史完整。”

**递进追问与参考回答：**“完整游标方案应让每条持久事件有稳定身份，按游标读取并定义顺序、保留和过期恢复；客户端重复应用要幂等，终态前要有补齐策略。把 payload 值加进 hash 只能减少一个碰撞类型，不解决事件身份与跨连接消费位置。当前没有 SSE id 与 Last-Event-ID 支持，fetch 也不会自动替项目实现续传。”

**面试官提示。**让候选人给一个确定性的事件序列，例如 `e1 → e2丢实时 → e3终态`，再指出代码在哪里返回。没有具体序列的“最终一致会补回来”不算完整答案。

**现场代码练习（占本轮最后 4 分钟）。**写一个以持久事件为准、实时通知只负责唤醒的游标循环。以下是教学方案，假设 store 已提供“按计划原子分配递增 seq 并持久追加”和“按 seq 升序 readAfter”的合同，且序列顺序与可见提交顺序一致，不会出现客户端已读较大 seq 后较小 seq 才提交；仅有数据库自增 ID 不足以保证这一点。终态也按同一序列提交，不能越过尚未提交的必要业务事件，并约定终态后不会再追加本流必须消费的事件。当前 FilePlanStore 并不因此获得这些能力。

```text
append(plan, payload):
    begin transaction
    seq = allocate_next_sequence(plan)
    insert_event(plan, seq, payload)
    commit transaction
    notify_subscribers(plan)  # notification may be lost
stream(authenticatedUser, plan, cursor):
    authorize(authenticatedUser, plan)
    reject_or_send_snapshot_if_cursor_expired(cursor)
    while connection_is_open:
        batch = readAfter(plan, cursor, limit, ascending=True)
        for event in batch:
            if writeSSE(id=event.seq, data=event) failed: return
            cursor = event.seq
            if event is terminal: return
        if size(batch) == limit: continue
        wait_for_notification_or_bounded_timer()
```

参考说明：“通知丢失时定时读取仍可继续，但历史必须真的持久存在；客户端重连使用最后确认的游标并幂等应用，服务端一次 write 成功不代表客户端业务已处理。终态必须按持久序列读取，不能绕过前面的历史直接结束。事务失败、游标过期、分页和慢消费者也要明确处理。”评分重点是稳定事件身份、持久化先于通知、顺序与消费边界，而不是是否背出某个消息队列产品名。

### 60–72 分钟：安全边界

**面试官原话：**“有 API token、OwnerID、CORS 和 Docker，可以说安全上线吗？挑两个最需要核对的配置。”

**参考回答：**“不能用这些名词叠加代替威胁与配置核对。我先查 API_AUTH_TOKEN 是否非空、可信身份如何产生；共享 token 不区分用户，X-User-Id 与匿名 cookie 需要可信边界。然后查沙箱实际 network/user/readonly 配置：固定默认是 bridge，user 和只读根不是无条件开启。CPU、内存、PIDs 与 cap-drop 是一组约束，但不等于断网和文件隔离。CORS 只约束浏览器跨源行为，不能替代服务端授权。”

**递进追问与参考回答：**“PDF URL 初验后仍在拨号时解析检查并连接通过校验的 IP，重定向也重检，是为了缩小检查与使用之间的差异；不能只比较 hostname 文本。挂载路径解析符号链接并检查允许根，也是边界检查；还要考虑路径是否能在检查后被替换。验证用替身 DNS 和临时目录，不向真实内网或业务目录做破坏性试验。”

**面试官提示。**初级候选人可聚焦认证/授权两个概念；加深候选人应主动核对默认与配置、初验与使用、身份声明与可信身份。不要要求提供实际攻击步骤来证明理解。

### 72–82 分钟：记忆与评测

**面试官原话：**“poison gate 拒绝了一条偏好，为何缓存可能已有它？模型答案写入记忆后越来越自信，如何处理？评测出了 NaN 呢？”

**参考回答：**“prepare 的异步偏好路径先 SaveBatch 后逐条检查，拒绝后续持久化不能撤销已经发生的缓存可见。我要按 sink 枚举写路径，包括同步规则与 finalize 抽取；事务提交函数并不是统一安全闸门。模型派生内容应保留来源和证据，不能用低 importance 代替真实性判断。评测 NaN 要先查空样本、零分母、解析失败或数值异常，保留失败类别与样本完整性，不从分母里消失。相关 chunk、任务 completed 和可相信的最终结论也是三层不同状态。”

**递进追问与参考回答：**“下一项验证用合成模型输出：整段输入通过、单条 k-v 被拒绝，检查偏好缓存、偏好库与长期主数据三个 sink。先增加正则或换模型都不能修复检查顺序问题。关于质量，构造缺失、冲突、过期证据的固定问题集，分别测检索证据和最终回答，再决定是否改检索或生成，不能只报模型自评。”

**面试官提示。**答案应能说出至少两个不同写路径，并承认没有跑安全与效果测试。不要把“用了守门模型”当作通过标准。

### 82–90 分钟：方案排序与复盘

**面试官原话：**“只能做一项改进，你选什么？如何证明做对，而不是多写了代码？”

**参考回答：**“我先按业务影响和可验证性排序。在多用户并发场景，我会优先明确按任务身份的取消与状态归属；在单用户研究任务里，也可能先保证依赖失败不能触发发布。选定后写清不变量、最小失败时间线和对照测试，改动前复现、改动后验证，并检查其他正常路径。没有实际环境数据时，不把这个排序说成普遍最优，也不承诺完成分布式可靠性。最后给出未解决的外部副作用和恢复边界。”

**面试官提示。**方案越多不等于能力越强。看候选人能否选择一个问题、拒绝两个过早修复、定义一项有区分力的测量，并把结论限定在实际证据里。

## 六、四维 0–3 分评分与复盘方法

每一维独立给分，总分 0–12 只用于个人训练进步，不预测公司录用结果。不会某个框架名不自动扣分；编造个人贡献、生产效果或运行记录，应在第四维按实际表现记分，不能被前面技术表达掩盖。

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
| --- | --- | --- | --- | --- |
| 调用链准确度 | 关键分支与源码矛盾，无法说明输入输出 | 能列模块，但顺序、条件或状态混淆 | 能准确说出入口、分支和主要状态，指出一个边界 | 能追到具体执行接口与失败分支，区分可达路径、共享对象和版本 |
| 机制与取舍 | 只说框架自动保证、越复杂越好 | 能复述机制，缺少条件和替代方案 | 能解释机制为什么有效及其代价 | 能给反例、比较方案，在明确约束下做选择并说明剩余风险 |
| 失败与验证 | 没有可检验方法，靠“应该没问题” | 会说加日志/压测，但不知测什么 | 给出最小输入、预期结果与一次区分性测量 | 能控制交错或故障阶段，区分多个假设，说明验证未覆盖范围 |
| 事实与贡献边界 | 把仓库功能、建议或虚构指标当个人成果 | 偶尔说“未验证”，但事实和计划仍混杂 | 清楚区分源码事实、个人工作、实验与建议 | 主动校准不确定性，给出可定位证据，遇到反例能修正而不编造 |

### 一段回答怎么打分

回答：“用了 context，所以 cancel 会终止所有 goroutine；我项目压测很快，截图没留。”调用链和机制有明显错误，验证没有依据，贡献指标也无法支持，不能因为表达流利给高分。

回答：“Cancel 对共享 runtime 的在途函数发信号；图运行时优先带 ctx 接口，旧 Execute 不一定响应。我没做多请求实测，下一步用两个阻塞替身与通道屏障验证范围，并观察退出而非只看 HTTP 返回。”调用链可给 2–3 分，机制可给 2 分，验证可给 2–3 分，事实边界可给 3 分；若能进一步解释外部副作用和按任务授权的取舍，机制维度才更接近 3 分。

### 复盘只记录能改变下一次回答的内容

每轮写四行即可：

1. **我说错或说模糊的句子：**例如“恢复后自动继续执行”。
2. **准确替换：**“恢复函数清理旧身份并改回 pending；重新调度是另一步。”
3. **支撑位置或最小例子：**`RecoverInterruptedPlans` 与 `executePlan` 的职责区别。
4. **下一次验证：**用替身记录启动恢复后是否实际调用 ExecutePlan，分别断言状态恢复与执行触发。

初级训练优先把四维都练到稳定的 2 分：能讲对、能举例、能验证、能承认不知道。加深训练再追求反例、跨层失败窗口和方案选择。面试官继续追问时，先补条件再回答；发现自己误读代码，可以明确修正：“我刚才把状态恢复说成自动重执行，按这段调用链应该分开。”这种可检查的纠正，比坚持一个听起来更强的结论更可靠。
